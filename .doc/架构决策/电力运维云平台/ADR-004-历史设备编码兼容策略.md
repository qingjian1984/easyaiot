# ADR-004：历史设备编码兼容策略

> 状态：Accepted  
> 日期：2026-07-30  
> 决策范围：M1 电力对象编码  
> 关联：POWER-SPEC-001  
> 产品基线：平台功能计划 1.4.0 / 项目开发宪法 1.4.0

## 现状

`deviceIdentification` 已进入设备认证、MQTT Topic、Redis Key、TDengine TAG/子表映射、工单和外部接口，仓库主要模型将其定义为字符串；同时少数历史 VO 存在误声明为 `Long` 的不一致。对存量值统一小写、改正则或重编码会造成跨模块断链。

## 决策

采用“存量原值保留、新增业务编码严格校验、可选别名映射”策略。

- 存量 `deviceIdentification` 是不透明且区分大小写的字符串，永久保留原值；禁止 trim 后覆写、自动小写、数值化或重新生成。
- 新建 `siteCode`、`spaceCode`、`circuitCode`、`meteringPointCode` 和新 `propertyCode` 执行 SPEC-001 正则。
- M1 新建设备的 `deviceIdentification` 沿用现有平台校验和唯一范围，不强制套用电力业务编码正则。
- 若业务需要规范设备资产编码，新增 `assetCode`；`assetCode` 必须遵循 SPEC-001 新业务编码正则。若需兼容外部旧编码，新增租户内唯一的 alias 映射，最终仍解析到同一设备主键。
- 消息和 API 同时出现 `deviceId` 与 `deviceIdentification` 时，前者仅为内部数值主键，后者为稳定字符串标识。
- 少数 `Long deviceIdentification` VO 先登记、查调用方、增加兼容测试，再通过独立代码变更修复；不得借 M1 数据迁移强制转换存量值。

## 读写规则

1. 新 API 优先按原始 `deviceIdentification` 精确查询。
2. 精确查询无结果且入口声明支持别名时，再查询 alias；不得全局模糊匹配。
3. 返回结果必须返回 canonical `deviceIdentification`，并可返回命中的 alias；不静默改写用户输入。
4. 新建 alias 需校验租户内冲突、循环、权限并记录操作者、原因和时间。
5. 删除设备前必须由设备领域服务同步检查 alias 和历史引用；存在引用时拒绝物理删除并返回引用摘要，只允许停用/归档。数据库外键或受控引用表作为第二道保护，定时扫描只做补偿审计，不能替代删除事务前校验。停用 alias 不影响历史解析。
6. 二维码始终绑定不可变内部对象主键；新增、停用或修改 alias 不改变二维码目标，alias 仅参与声明支持别名的查询入口。

## 迁移和验收

- 先生成存量编码画像：字符集、大小写、长度、重复、数值型 VO 调用链。
- 迁移只补站点/空间/回路关系及可选 `assetCode`，不更新 `deviceIdentification`。
- 回归至少覆盖认证、MQTT 上下行、Redis、PostgreSQL/TDengine 两种 `TelemetryStore` 适配器、设备影子、告警、工单和二维码解析。
- 使用包含中文、下划线、大写、纯数字和前导零的样本验证原值不变。
- `iot-device` 模块负责人负责完成 `Long deviceIdentification` VO 调用链清单和修复方案，截止门禁为 TD-004 评审前；未确认兼容影响的 VO 不得直接修改。

## 后果

短期会同时存在历史设备标识与规范业务编码，但避免一次性破坏既有链路。所有新业务不得把 `assetCode`、`deviceIdentification` 和内部 `deviceId` 当作可互换字段。
