## 2. 已核对的仓库事实

1. M1 canonical telemetry 已提供 `messageId/tenantId/siteCode/deviceIdentification/collectedAt/quality/configVersion`；ConfigSnapshot 1.1 与不可变 `iot_collector_config_release` 可提供 `productIdentification/siteId/siteCode/workloadId/configVersion` 和设备成员关系。
2. M1 的 32 位无连字符历史 messageId 与 36 位 RFC 4122 UUID 可解析为同一内部 UUID；wire value 和既有 payload/envelope hash 不能改写。
3. 当前 `device_property_threshold` 是可变当前行，没有不可变 rule revision、历史快照或显式活动周期状态；恢复仍按设备+属性查询最新 OPEN。
4. 当前 `DeviceEventHandler` 使用后端生成的消息 ID、允许 `tenant=0` 和接收时 `now` 回退，落库没有 site、映射版本、稳定 correlation/cycle；`DeviceEventSubscriber` 捕获异常后只记日志。
5. 仓库没有经产品负责人批准的 `DEVICE_EVENT → alarm` 版本化 allowlist。
6. `AlarmSourceTransactionService.process()` 使用 `REQUIRES_NEW`；本 ADR 不改变该边界，也不修改 V011 候选表结构。

因此本 ADR 可以冻结目标合同和主补偿路径，但不能把缺失的来源事实或产品决策伪造成已存在。本版保持 `Proposed`。

## 4. 字段权威与冲突规则

### 4.1 THRESHOLD

| 目标字段 | 唯一权威来源 | 冲突/缺失处置 |
|---|---|---|
| `sourceMessageId` | M1 `TelemetryEnvelope.messageId`；32/36 位均解析为小写 36 位内部 UUID | 非 UUID、Topic/Envelope 设备冲突、同 ID 异 hash：fail-closed；不得改写原 wire/hash |
| `tenantId` | Envelope tenant，且必须经 product+device 权威注册反查得到相同 tenant | 零值、不一致、无匹配或多匹配：`ALARM_TENANT_AUTHORITY_CONFLICT` |
| `siteCode` | Envelope `siteCode` | 空值或与发布快照不一致：`ALARM_ROUTE_HISTORY_CONFLICT` |
| `siteId` | 投影事件必须携带受信 `workloadId`；以 `tenantId + workloadId + configVersion` 精确定位唯一曾 APPLIED 的不可变 release，再校验 siteCode 与设备成员 | 缺 workload 不允许按 siteCode 搜索；零/多 release 或成员冲突 fail-closed |
| `productIdentification` | 上述历史发布快照；并与 canonical Topic product 一致 | 不一致：`ALARM_PRODUCT_AUTHORITY_CONFLICT` |
| `deviceId` | canonical Topic device、Envelope device、发布快照成员三者完全一致 | 不一致：`ALARM_DEVICE_AUTHORITY_CONFLICT` |
| `occurredAt` | Envelope `collectedAt` | 缺失、无 offset、非法未来时间：隔离，不用接收时间补齐 |
| `quality` | Envelope `quality` | 未知枚举隔离；非 `GOOD` 的状态语义见 §6.3 |
| `propertyCode` | canonical telemetry property 项 | 空值/非法编码不评估；显示名不得代替 |
| `ruleId/ruleVersion` | 对该 telemetry 生效的不可变阈值规则快照 | 当前可变阈值行不能充当 rule version；缺失时 C1 停止 |
| `severity` | 不可变 rule revision 的固定输出 | 不接受 telemetry 或调用方自由严重度 |
| `recordedAt` | adapter 观察时间，仅用于审计 | 不参与 sourceId/cycleKey/eventId 或历史语义 |

历史发布解析还必须证明目标 release 曾成功 APPLIED，且 collectedAt 位于该版本在同 workload 的左闭右开应用窗口；历史 ROLLED_BACK 版本在原应用窗口内仍可验证 backlog。route evidence 保留 releaseId、payloadSha256、workloadId、appliedAt/nextAppliedAt。仅有当前 `siteCode → siteId` 或当前设备 assignment 不足以通过。

### 4.2 DEVICE_EVENT

| 目标字段 | 唯一权威来源 | 冲突/缺失处置 |
|---|---|---|
| `sourceMessageId` | 设备/协议原始事件实例 ID 或稳定 request ID，必须在上游重试中不变 | 后端生成 `IotDeviceMessage.id` 不合格；缺失时只保留 legacy `device_event`，不生成统一告警 |
| `tenantId` | canonical Topic product+device 经权威注册唯一解析 | payload tenant 只可交叉校验；0、冲突、歧义均 fail-closed |
| `siteId/siteCode` | 事件 `occurredAt` 落入 `power_device_assignment [valid_from, valid_to)` 的唯一历史分配 | 无事件时间、零匹配、多匹配或只能查当前分配：`ALARM_ROUTE_HISTORY_NOT_UNIQUE` |
| `product/deviceId` | 直连 canonical event Topic，并与权威注册事实一致 | Topic 缺段或注册冲突隔离；SUB_EVENT 当前只有网关身份，固定 `DEVICE_EVENT_SUBJECT_UNRESOLVED` |
| `occurredAt` | 受版本合同约束的设备事件时间，必须携带 offset | 不使用 subscriber 接收时间或 `now` 回填；缺失/非法时不转告警 |
| `quality` | 固定 `GOOD`，前提是 identity、时间、route 和 mapping 全部验证通过 | 任一验证失败时没有 AlarmSourceEvent，不用 `UNKNOWN` 绕过 |
| `sourceAction` | allowlist 中 raised/recovered matcher | 自由 `eventType/level/status` 不得直接映射 |
| `severity` | allowlist 固定值 | payload severity 只可作为匹配条件，不能覆盖映射值 |
| `ruleId/ruleVersion` | `null` | DEVICE_EVENT 不伪造规则引用；mappingVersion 进入 source identity |
| `recordedAt` | adapter 观察时间，仅用于审计 | 不参与稳定 identity |

## 5. 确定性 identity 规范

### 5.1 UUID namespace 与规范化

固定 namespace：

```text
16303fbb-2516-5e21-b4d3-a5a6d557d55f
```

该值由 DNS namespace 对 UTF-8 名称 `easyaiot.local/alarm-source/v1` 计算 UUIDv5 得到，后续实现直接使用上述常量，不在运行时重新派生。

每个 UUIDv5 name 使用以下编码：

```text
<domain>\n
<fieldName>=<UTF-8字节数>:<fieldValue>\n
...
```

规则：字段顺序严格按本节公式；字符编码固定 UTF-8；换行固定 LF；不得 trim、大小写折叠或 Unicode 再规范化；输入不得为 null；正整数使用无前导零十进制；UUID 先解析再输出小写 36 位 canonical 形式。长度前缀按 UTF-8 字节数而非字符数计算。任何不能规范化的输入均 fail-closed。

持久化时必须同时保留可复核的 canonical identity 或其 `sha256:` 摘要；若同一派生 UUID 对应不同 canonical bytes/hash，稳定结果为 `ALARM_IDENTITY_COLLISION` 并终态隔离，不得用后到内容覆盖首次证据。UUIDv5 用于确定性寻址，不替代 Inbox 的 envelope hash 冲突判定。

### 5.2 `sourceId`

THRESHOLD：

```text
domain = alarm-source-identity-v1
sourceType, tenantId, siteId, deviceIdentification,
propertyCode, ruleId, ruleRevision

sourceId = "threshold:v1:" + UUIDv5(namespace, canonicalName)
```

DEVICE_EVENT：

```text
domain = alarm-source-identity-v1
sourceType, tenantId, siteId, productIdentification,
deviceIdentification, alarmTypeKey, mappingVersion

sourceId = "device-event:v1:" + UUIDv5(namespace, canonicalName)
```

`alarmTypeKey` 是同一 raised/recovered 对共同使用的稳定告警族键，不等同于某个原始 eventIdentifier。显示名、阈值文本、当前值、接收时间和 payload 全文不得进入 sourceId。

### 5.3 `cycleKey`

THRESHOLD 在 `NORMAL/RECOVERED → ACTIVE` 的 CAS 胜者使用首次 breach 的 canonical `sourceMessageId`：

```text
domain = alarm-source-cycle-v1
sourceType, sourceId, firstSourceMessageId

cycleKey = "threshold-cycle:v1:" + UUIDv5(namespace, canonicalName)
```

后续 breach occurrence 与 recovery 必须从持久化活动状态读取并复用该 cycleKey，不得重新按当前时间生成。

DEVICE_EVENT 使用 allowlist 指定 JSON Pointer 取得并规范化的稳定 correlation key：

```text
domain = alarm-source-cycle-v1
sourceType, sourceId, correlationKey

cycleKey = "device-event-cycle:v1:" + UUIDv5(namespace, canonicalName)
```

raised/recovered 不能取得同一 correlation key 时禁止映射；不得按相近时间、最新 OPEN 或当前状态猜测。

### 5.4 AlarmSourceEvent Envelope `messageId`

```text
domain = alarm-source-event-v1
sourceType, sourceMessageId, sourceId, cycleKey,
contractVersion, sourceAction

messageId = UUIDv5(namespace, canonicalName)
```

THRESHOLD 的 `contractVersion=threshold-adapter-v1`；DEVICE_EVENT 的 `contractVersion=device-event-mapping-v1`。同一来源事实重放得到同一 messageId；不同规则、映射、周期或 action 得到不同 messageId。Envelope hash 仍按既有 AlarmSourceEvent 合同计算，不由本 ADR 改写。

### 5.5 Golden fixtures

| 场景 | 输入摘要 | 期望输出 |
|---|---|---|
| THRESHOLD source | tenant=100, site=200, device=`meter-01`, property=`voltage-a`, rule=300, revision=1 | `threshold:v1:3473b230-adce-544f-8a5a-390d0ad33ed5` |
| THRESHOLD cycle | 上述 source，first message=`11111111-2222-4333-8444-555555555555` | `threshold-cycle:v1:1d5d7808-1cce-5487-a267-1234c1b9c5bb` |

| 同一输入改为 RECOVERED | 只把 action 改为 `RECOVERED` | `06694a77-e02c-516e-9fca-bbe4a4cff3b0`，必须与 RAISED 不同 |
| DEVICE_EVENT source | tenant=100, site=200, product=`product-meter`, device=`meter-01`, alarmTypeKey=`thermal-overheat`, mapping=1 | `device-event:v1:ef4a67d7-e4fd-52dc-b69e-428a9fbb9aa0` |

## 6. THRESHOLD 周期状态机

### 6.1 状态与转换

每个不可变 `tenantId/siteId/device/property/ruleId/ruleRevision` 规则实例至多一个活动周期：

| 当前评估状态 | 输入 | 原子结果 | AlarmSourceEvent |
|---|---|---|---|
| `NORMAL` 或已 `RECOVERED` | GOOD 且 breach | CAS 创建新活动周期，保存 firstSourceMessageId/cycleKey/stateVersion | `RAISED` |
| `ACTIVE` | GOOD 且仍 breach | 复用 cycleKey，更新 lastOccurred/occurrence；不创建第二周期 | `RAISED`，统一域按 messageId 幂等记录 occurrence |
| `ACTIVE` | GOOD 且 recovery predicate 成立 | 按显式活动 cycleKey CAS 为 `RECOVERED` | `RECOVERED` |
| `NORMAL/RECOVERED` | recovery | 无状态变化 | 不产生事件；记录低基数 no-op 指标 |
| 任意 | 重复 sourceMessageId | 零状态变化 | 重放同一确定性事件或零新增 |
| 任意 | 乱序旧 event time | 不得覆盖较新状态 | 稳定拒绝/隔离，不能恢复当前周期 |

同一规则实例的并发创建通过持久化唯一活动键与 `stateVersion` CAS 保证只有一个胜者。恢复请求必须携带已读取的显式 cycleKey；禁止 `selectLatestOpen`。静默、维护、通知抑制和告警处置状态不切割来源周期。

### 6.2 Rule revision

rule revision 必须是发布后不可修改、可回溯到完整 predicate、迟滞、持续时间、severity、quality policy 和生效范围的快照。修改阈值必须发布新 revision；旧 revision 保留用于历史重放和活动周期恢复。当前 `device_property_threshold` 不满足该条件，因此必须先形成版本化迁移与既有活动周期处置方案；在此之前 THRESHOLD adapter 保持关闭。

新 revision 生效时，旧 revision 立即停止创建新周期，但其已存在的 ACTIVE 周期继续使用旧 predicate 处理后续 GOOD 数据，直到真实 recovery 后关闭；不得因配置发布伪造 RECOVERED，也不得把旧 cycleKey 搬到新 revision。新 revision 独立评估并使用自己的 sourceId/cycleKey，短暂并存必须在对账和 UI 中按 revision 明示，不能按设备+属性静默合并。

### 6.3 Quality

C1 默认只允许 `GOOD` 改变阈值周期。`BACKFILLED/TIMEOUT/COMM_ERROR/DECODE_ERROR/UNKNOWN` 均保留来源与质量证据，但不创建、更新或恢复活动周期，稳定结果为 `THRESHOLD_QUALITY_NOT_EVALUABLE`。其中 `BACKFILLED` 若未来需要历史规则重算，必须由新 rule revision policy 和独立 replay/backfill 任务授权；不得在实时 C1 中静默启用。

## 7. DEVICE_EVENT allowlist 合同

默认策略是 `DENY_ALL`。批准条目至少包含：

```text
mappingId, mappingVersion, lifecycle,
productIdentification/modelScope, alarmTypeKey,
raisedMatcher(eventIdentifier + payloadPredicate),
recoveredMatcher(eventIdentifier + payloadPredicate),
severity, correlationJsonPointer, occurredAtJsonPointer,
oneShotPolicy, contractMajor, effectiveFrom, approvedBy
```

约束：

1. `mappingId + mappingVersion` 不可变；升级发布新版本，不改变已处理历史事件；
2. `raisedMatcher` 与 `recoveredMatcher` 必须共同映射到同一 `alarmTypeKey` 和 correlation；映射升级后，已有活动周期继续绑定原 mappingVersion，恢复匹配先按 correlation 查找唯一活动周期并使用其原版本；旧版本在活动周期清零前不得删除；
3. severity 只允许 `INFO/NORMAL/IMPORTANT/EMERGENCY` 固定值；payload 自由等级不能覆盖；
4. C1 的 `oneShotPolicy` 只允许 `REJECT`。若产品未来批准一次性事件，必须先给出自动闭合或人工处置语义并另行评审；
5. 未映射、多个条目命中、未知主版本、缺 correlation、非法时间或非法等级分别返回稳定错误：`DEVICE_EVENT_NOT_ALLOWLISTED`、`DEVICE_EVENT_MAPPING_AMBIGUOUS`、`DEVICE_EVENT_CONTRACT_UNSUPPORTED`、`DEVICE_EVENT_CORRELATION_MISSING`、`DEVICE_EVENT_TIME_INVALID`、`DEVICE_EVENT_MAPPING_INVALID`；
6. fail-closed 结果可以保留 legacy 设备事件和安全审计，但不能生成 AlarmSourceEvent，也不能用默认严重度或永久 ACTIVE 代偿。

当前仓库没有任何已批准条目，所以本 ADR 不附示例生产 allowlist；伪造示例产品事件会错误关闭产品门禁。

allowlist 的机器合同固定为 [device-event-alarm-allowlist-v1.schema.json](../../技术设计/电力运维云平台/assets/c1p-g1/device-event-alarm-allowlist-v1.schema.json)，产品填报起点为 [空白模板](../../技术设计/电力运维云平台/assets/c1p-g1/device-event-alarm-allowlist-template.json)。空数组、`DRAFT` 和 `approval=null` 明确表示零事件获批，不能作为启用输入。

## 8. 原子、补偿与通知 owner

### 8.1 选择：来源侧 Outbox

拒绝把旧写与 `AlarmSourceTransactionService.REQUIRES_NEW` 伪装成同一事务。主路径固定为：

```text
来源事实/评估状态 + source-event outbox（来源本地同事务）
  → 可重放 relay
  → AlarmSourceEvent Inbox
  → AlarmSourceTransactionService.REQUIRES_NEW
  → alarm_record/action/outbox（告警本地同事务）
```

THRESHOLD 分两段：M1 Store 成功后由 TD-003 的可靠 projection event 驱动阈值 evaluator；evaluator 在单个 PostgreSQL 事务中提交不可变 rule revision 引用、周期 CAS 结果和告警 source-event outbox。不得在 Store 前评估，也不得由旧 `evaluateAndAlarm` 直接双写统一告警。

DEVICE_EVENT 在同一 iot-device 事务中提交 legacy `device_event` 与完整 source-event outbox；只有事务提交成功才允许 transport ACK/offset 提交。当前原始 identity/time/route 和 source outbox 均不完备，且 subscriber 吞异常，所以此路径尚未具备实现前置条件。

source-event outbox 的字段、claim/lease、重试、终态和 relay 语义由 G1 合同冻结；物理 Schema、迁移编号、repository、容量参数和运行证据仍须独立实现评审。不得复用 `kafka_sent` 表示其状态，不得修改 V011 来夹带来源 outbox。

G1 已在 [来源事件 Outbox 与 Relay 合同](../../技术设计/电力运维云平台/assets/c1p-g1/G1-OUTBOX-来源事件Outbox与Relay合同.md)冻结三层可靠事实：TD-003 projection outbox、iot-device source-event outbox、V011 alarm outbox 各自独立；两类来源共用 source outbox/local relay，但使用独立 ingress Inbox。候选表必须位于 V011 之后的独立迁移。

### 8.2 失败矩阵

| 场景 | 来源侧结果 | 统一告警侧结果 | 重试/处置 | 通知 |
|---|---|---|---|---|
| 权威/映射校验失败 | legacy 来源可按原合同保存；不写 source outbox | 无 | 稳定错误+审计，非瞬时错误不热循环 | 旧 owner 按观察期合同；新链无通知 |
| 来源事实或周期事务失败 | 全部回滚 | 无 | transport 不 ACK/不提交 offset，按预算重试 | 无新链通知 |
| 来源事务提交后进程崩溃 | outbox 留存 | 无或稍后产生 | relay 恢复 claim，确定性 messageId 重投 | 由当前唯一 owner 决定 |
| relay/告警入口瞬时失败 | outbox 保持可重试 | 告警事务回滚 | 指数退避；不改来源周期 identity | 无重复通知 |
| 同一消息重复 | 同一 outbox identity 或幂等 no-op | Inbox `PROCESSED` 零新增 | ACK 成功 | 零新增通知 |
| 同 messageId 异 hash | 保留首次证据 | Inbox `QUARANTINED` | 终态隔离，人工使用新 messageId 重驱 | 禁止通知冲突正文 |
| RECOVERED 先于 RAISED | 来源状态拒绝乱序或保留待决证据 | 不得按 latest OPEN 猜周期 | 稳定隔离/对账 | 无新链通知 |
| relay 重试耗尽 | outbox 终态隔离且可审计 | 可能缺失 | 进入差异清单；授权后以原 identity 重驱 | 不切 owner |
| 旧链成功、新链未到达 | legacy 有事实，source outbox 可追 | 暂缺 | 对账按 source identity 补投 | 观察期仍仅旧 owner |
| 新链成功、旧通知失败 | 统一事实存在 | 已处理 | 通知重试由唯一通知 outbox 管理 | 不回滚告警 |
| 对账发现身份/周期差异 | 两边均保留证据 | 不自动覆盖 | fail-closed，人工裁决；禁止切读 | 维持当前 owner |

### 8.3 通知所有权切换

观察期：旧阈值/设备事件通知链是唯一 owner，统一告警通知 relay 强制关闭。切换发布必须以同一受控 capability generation 同时证明 `oldOwner XOR unifiedOwner=true`，先阻断旧 owner，再启用统一 owner；预检失败则整体不切换。切换后回滚反向执行并保留统一告警事实，不允许同周期双发，也不把旧 `kafka_sent` 当作统一通知完成证据。

## 9. 被否决方案

1. **直接调用统一告警并声称同事务**：`REQUIRES_NEW` 会独立提交/回滚，不能保证旧来源事实原子性。
2. **只读扫描当前旧表**：阈值行可变、DEVICE_EVENT 缺稳定 identity/site/cycle，历史投影会随当前数据漂移。
3. **用当前 assignment 补历史 siteId**：设备迁站后会把历史告警写入错误站点，存在跨租户/站点风险。
4. **用 telemetry messageId 直接作为所有阈值事件 ID**：同一消息命中多规则时碰撞，且 RAISED/RECOVERED 不隔离。
5. **继续 latest OPEN 恢复**：并发、重开和乱序时无法证明恢复的是同一周期。
6. **全量 thing.event.post 转告警**：把普通业务事件伪造成告警且无法闭合。
7. **数据库写后直发 Kafka/双通知**：数据库提交与 broker 确认非原子，并破坏单一通知 owner。

## 10. 安全、兼容与回滚

- tenant、product、site、device 任一权威冲突均 fail-closed，不允许 `tenant=0`、默认站点或跨租户 fallback；
- 日志和指标只记录低敏 identity、稳定错误码和哈希，不记录完整事件 payload、凭据或隐私字段；
- source outbox/Inbox 重放必须保留原 occurredAt、timezone、offset、quality 和 payloadHash；接收时间只作审计；
- 观察期不改变旧读、旧通知和旧处置 owner；未完成全量+增量对账不得切读；
- 回滚优先关闭新 relay/capability，保留已写的追加事实和 outbox，不删除 V011 或历史证据；
- mini 在构建、Spring 装配、任务、迁移、Topic/consumer group 和 capability 上均必须证明无残留。

## 13. 后果

正向后果：来源重放、同消息多规则、恢复关联和跨事务失败都有确定性身份；历史路由不受当前设备状态漂移；通知 owner 可证明唯一。

成本与限制：需要新增不可变阈值版本/周期状态和来源 outbox 设计，DEVICE_EVENT 依赖产品清单及上游事件身份升级；在这些前置关闭前，旧告警链继续运行，统一告警 C1 不能提前接入。
