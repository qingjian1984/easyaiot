# ADR-012：产品根属性与服务参数单一事实

> 状态：Proposed / In Review  
> 日期：2026-08-04  
> 决策范围：现有产品 TSL 运行表与 M1 电力物模型模板绑定  
> 关联：SPEC-002、ADR-009、TD-005 1.0.4  
> 证据：[TD-005 目标数据库与现有实现画像报告](../../技术设计/电力运维云平台/TD-005-目标数据库与现有实现画像报告.md)

## 1. 背景

目标数据库 `iot-device20` 中：

- `product_properties` 表示产品根级属性，不存在 `service_id`；
- `product_commands_requests` / `product_commands_response` 已表示服务输入和输出参数；
- `ProductPropertiesMapper`、API VO 和旧 TSL 导入/导出调用仍残留 `service_id` 语义；
- `findAllByServiceId` statement 被注释，`selectPropertiesByServiceIdList` 查询目标库不存在的列；
- 直接为 `product_properties` 增加可空 `service_id` 会形成“根属性与服务参数共表/分表并存”的双事实。

该问题影响现有非电力产品兼容、模板实例化、产品绑定快照、服务调用和删除链，不能仅在 Mapper 修复中隐式决定。

## 2. 候选决策

建议采用单一事实：

| 业务成员 | 唯一运行事实 | 禁止 |
|---|---|---|
| 产品根级遥测/配置属性 | `product_properties`，按 tenant + product/template scope + propertyCode 标识 | 使用 `service_id` 表示服务参数 |
| 服务定义 | `product_services` | 在属性表复制服务身份 |
| 服务命令 | `product_commands` | 用属性记录代替命令 |
| 服务输入参数 | `product_commands_requests` | 同时写入 `product_properties` |
| 服务输出参数 | `product_commands_response` | 同时写入 `product_properties` |

由此产生的实现约束：

1. 不向 `product_properties` 新增 `service_id`；
2. 移除或迁移 `findAllByServiceId/selectPropertiesByServiceIdList` 及其调用点；
3. 服务参数的导入、导出、详情、版本快照和差异统一读取 command request/response；
4. 产品根属性 DTO 不再暴露无法兑现的 `serviceId`；若兼容窗口需要，使用独立 legacy DTO 并标记废弃期限；
5. 模板成员和运行表成员通过 `model_binding_id/model_member_fingerprint` 或独立映射表关联，不复用 `service_id` 推断来源；
6. standard/full 复用同一实现，mini 不启用电力模板能力。

## 3. 备选方案

### A. 为 `product_properties` 补回 `service_id`

不推荐。若评审选择该方案，必须同时冻结：

- 根属性如何表达以及 `service_id` 是否允许为空；
- `(tenant_id, service_id, property_code)` 与根属性唯一键；
- service 与 property 的同租户外键；
- 历史数据回填和双读期限；
- command request/response 与属性表之间谁是服务参数唯一事实；
- 删除、升级和回滚的级联顺序。

仅增加一个可空列不构成完整方案。

### B. 新建统一 TSL member 表立即替换所有运行表

M1 不采用。一次替换现有属性、事件、服务和命令链的回归面过大，会把模板版本控制与运行时重构耦合。后续可独立 ADR 评估。

### C. 保留现状并在不同 API 中选择不同来源

否决。该方案无法定义发布 hash、绑定快照、差异和回滚的唯一事实，也会继续保留确定性的 BindingException/SQL 缺列路径。

## 4. 兼容与迁移候选

1. 先建立非电力产品 TSL 导入、导出、详情、编辑和服务调用回归基线；
2. 枚举 `findAllByServiceId/selectPropertiesByServiceIdList` 全部调用者并按 command 参数链改写；
3. 修复 `ProductPropertiesMapper.insert` 列值数量不一致及裸 `jdbcType=BIGINT}`；
4. 清理 Mapper `Base_Column_List/insertOrUpdate` 的无效 `service_id` 依赖；
5. 将 API 中的 `serviceId` 从根属性 DTO 迁出，保留兼容适配层而非污染新 DTO；
6. 对旧 JSON 导入/导出执行双向 golden，确保非电力格式兼容或给出版本化迁移错误；
7. 完成后重跑 TD-005 画像，确认缺列 SQL 和 statement 缺失路径为 0。

## 5. 接受门禁

ADR 转为 `Accepted` 前必须具备：

- 所有旧调用点、API 和前端消费者清单；
- 至少一个含根属性、服务、命令、输入和输出参数的非空产品 fixture；
- 旧格式导入 → 运行表 → 导出 round-trip golden；
- 根属性与服务参数新增、编辑、删除、产品删除和失败回滚合同测试；
- tenant `1/2` 交叉访问和写入隔离测试；
- standard/full 相同结果、mini 无入口测试；
- 数据迁移和应用回滚步骤。

## 6. 当前限制

本 ADR 仍为 `Proposed`。在评审接受前：

- TD-005 可以引用它作为待决策门禁；
- 不得据此删除旧 API、修改生产表或编写依赖该决策的模板绑定 migration；
- 不影响 Java/TypeScript JCS golden、恶意导入 fixture 等独立证据准备。
