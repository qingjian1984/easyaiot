## 1. 设计结论

统一告警域落在 `DEVICE/iot-device`。所有来源先转换为版本化 `AlarmSourceEvent`，经告警专用 Inbox 幂等后，在同一数据库事务中更新 `alarm_record`、动作历史和告警 Outbox。来源模块保留不可变来源证据，不再写统一处置状态。

本 TD 只形成可评审设计；DDL、生产双写和 API 切换在 OPEN 关闭前不得执行。

## 2. 现状画像

- `device_threshold_alarm` 只有 `OPEN/CLEARED`，不足以承载确认、处理、忽略、误报和升级；静默窗口还会产生并行 OPEN，恢复只清理最新一条。
- `iot-sink`、`iot-message` 与 VIDEO 各自存在 `alert` 记录和消费链，ID/状态语义不统一。
- `PowerModelOutboxService` 与相关迁移候选可复用可靠事件原则，但 power-model Inbox 的表和幂等域不能直接复用。
- WEB/APP 的旧告警接口必须经兼容层转调，不能继续形成第二写入口。
- 旧评估请求缺少 messageId、tenant/site、事件时间和质量码，且新告警把 tenant 写为 0；不得直接接入新规则引擎。

## 3. 目标模块结构

```text
iot-device-api
└─ alarm/contract         事件 envelope、DTO、错误码、枚举
iot-device-biz
└─ alarm
   ├─ controller          /api/v1/device/alarms/**
   ├─ application         状态转换、规则发布、查询、迁移编排
   ├─ domain              AlarmRecord、AlarmRuleVersion、状态策略
   ├─ infrastructure      Mapper、Inbox、Outbox、来源适配器
   └─ scheduler           忽略到期、持续窗口、升级触发、对账
```

禁止在 `iot-message`、`iot-sink` 或 VIDEO 新增处置状态写逻辑。

## 4. 逻辑数据模型

| 表 | 用途 | 关键约束 |
|---|---|---|
| `alarm_record` | 唯一告警周期主记录 | `alarm_id` PK；来源周期唯一；`version` 乐观锁 |
| `alarm_source_mapping` | 旧/来源 ID 到 `alarm_id` | `(tenant_id,source_type,source_id,cycle_key)` UNIQUE |
| `alarm_action_log` | 状态、升级、抑制、维护动作追加历史 | `(alarm_id,sequence_no)` UNIQUE；不可更新业务字段 |
| `alarm_false_alarm_review` | 误报提议与独立复核 | 同一告警最多一条 PENDING；提议人与复核人分离 |
| `alarm_rule` | 规则稳定身份 | 租户+规则编码唯一；软删除受引用保护 |
| `alarm_rule_version` | 不可变规则版本 | `(rule_id,version_no)` UNIQUE；发布后禁止覆盖 |
| `alarm_maintenance_context` | 维护范围、时段与批准事实 | 范围 JSON 仅存受控 DSL；有版本与审计 |
| `alarm_source_inbox` | 告警专用消费者 Inbox | `message_id` UNIQUE；仅保存 `RECEIVED/PROCESSED/QUARANTINED`、envelope hash 和隔离错误；不承担 lease/退避 |
| `alarm_outbox` | 告警领域事件 | `event_id` UNIQUE；有限重试、死信、租户/分区键 |

所有表继承租户字段、创建/修改审计和逻辑删除约定；状态事实表不得由普通业务删除。最终 DDL 必须提供中文 `COMMENT ON TABLE/COLUMN`、索引依据、外键/软约束决策和 down/forward-fix 策略。

### 4.1 主记录关键字段

`alarm_record` 至少含 `alarm_id/tenant_id/site_id/source_type/source_id/cycle_key/source_object_id/device_id/property_code/rule_id/rule_version/severity/status/version/last_action_sequence/occurrence_count/escalation_level/last_escalated_at/first_occurred_at/last_occurred_at/recovered_at/closed_at/maintenance_context_id/ignored_from_status/ignored_until/ignore_generation/timezone/original_offset`。

`status` 只允许 `ACTIVE/ACKNOWLEDGED/PROCESSING/RECOVERED/CLOSED/IGNORED/FALSE_ALARM`；升级级别不得写入状态列。

V011 采用仓库数据库命名约定：`alarm_record.id → alarmId`、`row_version → version`、`device_identification → deviceId`、`source_timezone → timezone`、`source_offset → originalOffset`。这是持久化映射，不改变公共 JSON 字段名；Mapper/DTO 必须显式映射，禁止直接暴露数据库实体。升级事实由 `escalation_level + last_escalated_at` 共同表达。

## 5. 事务与并发

### 5.1 来源事件进入

1. 消费者校验 envelope、版本和租户，并对规范消息字节计算 `envelopeHash`；`payload.payloadHash` 只表示来源证据摘要。
2. 插入 `alarm_source_inbox`；重复同 `envelopeHash` 返回 `DUPLICATE`，不同 hash 以 `QUARANTINED + ALARM_SOURCE_HASH_CONFLICT` 持久化隔离并保留首次 hash。
3. 根据来源周期唯一键锁定/创建 `alarm_record`。
4. 追加 `alarm_action_log`，写 `alarm_outbox`。
5. 同一事务提交后才确认消息位点。

Inbox 状态有意保持三态：`RECEIVED` 表示已进入同一业务事务但尚未完成，`PROCESSED` 表示业务事实与 Outbox 已原子提交，`QUARANTINED` 表示不可自动覆盖的终态裁决。Inbox 不增加 `RETRY_WAIT`、重试次数、下次重试时间或处理 lease；数据库异常、CAS/依赖瞬时异常和事务内任一步失败都回滚整个事务，调用方不得 ACK/提交 offset。物理 transport adapter 负责有界重试、退避、毒消息 DLQ 和 ACK，具体预算、Topic、consumer group 与 DLQ 名称仍须在 C2 专项评审冻结后实现。

`QUARANTINED` 对同一 `messageId` 不可回退、不可改写为 `RECEIVED/PROCESSED`。未知主版本、final Schema 错误和同 `messageId` 异 hash 均进入隔离；hash 冲突必须保留首次 `envelopeHash`，不得以冲突正文覆盖原事实。人工重驱必须经过授权和审计，使用新的 `messageId`，并在重驱证据中关联原 Inbox 记录；不得重置原行或复用原 `messageId`。

### 5.2 状态动作

所有写 API 提交 `expectedVersion` 和 `Idempotency-Key`。应用服务执行权限/数据范围检查，再使用 `WHERE alarm_id=? AND version=?` 更新。更新行数为 0 返回 `ALARM_VERSION_CONFLICT`，不得最后写入覆盖。

忽略到期任务必须携带领取时的 `expectedIgnoreGeneration`，并只对 `status=IGNORED + expectedVersion + ignoredUntil<=now + ignoreGeneration=expectedIgnoreGeneration` 做 CAS；若期间已恢复、关闭、主动解除忽略或再次进入忽略，任务结束为无操作并记录指标。每次进入 `IGNORED` 单调递增 `ignoreGeneration`；离开忽略状态可保留最后代次，仅清除当前忽略窗口字段。

### 5.3 动作序号分配

`alarm_action_log.sequence_no` 不得从 `row_version` 推导，也不得通过无锁 `MAX(sequence_no)+1` 计算。`row_version` 只表达主记录状态 CAS；动作序号由 `alarm_record.last_action_sequence` 独立分配，初值为 0。每个需要写入动作历史的事务在动作追加前执行单行原子分配：

```sql
UPDATE public.alarm_record
SET last_action_sequence = last_action_sequence + 1
WHERE tenant_id = :tenantId
  AND site_id = :siteId
  AND id = :alarmId
RETURNING last_action_sequence;
```

首次创建告警时先插入主记录，再分配得到序号 1；已有告警先完成适用的状态 CAS，再分配并追加动作。原子更新利用 PostgreSQL 单行锁串行化同一告警的分配，不把 `row_version` 放入分配条件，避免无状态动作与状态版本耦合。分配、动作追加、主记录/映射和 Outbox 必须处于同一事务；追加失败时分配递增随事务回滚，不形成已提交序号空洞。幂等请求唯一约束独立于序号分配；重复请求必须零新增动作、零已提交序号消耗。

来源发生/恢复、人工状态动作、升级、忽略到期、维护/抑制和误报复核只要形成动作历史，都必须调用同一分配端口。状态 CAS 失败者不得分配；不改变状态的并发动作由原子分配器串行化。来源发生/恢复已按 [P02-M2-02R1A 独立动作序号任务](./P02-M2-02R1A-独立动作序号与并发合同任务单.md)完成本地验收；后续动作生成器仍须复用该端口并补测试。本节不授权数据库执行或来源接入。

## 6. 规则执行

- 解析器只接受 SPEC-005 声明式 DSL，发布时完成类型、单位、测点、质量和复杂度校验。
- 已发布版本编译为不可变执行计划并以 `tenantId/ruleId/version` 缓存；缓存失效事件只携带版本身份。
- 规则内容发布后不可原地修改；回滚在单事务内退役当前 `PUBLISHED` 版本并重新激活历史 `RETIRED` 版本，依赖 `(tenantId,ruleId) WHERE lifecycle='PUBLISHED'` 部分唯一索引保证并发下同一规则只有一个已发布版本。
- 单测点持续/迟滞状态使用有界窗口状态；复合规则按站点与分区处理，事件时间水位来自 SPEC-004。
- 超时、通信、解码和未知质量不转换为 0；规则超预算进入隔离，不能阻塞消费分区。
- standard 只注册 core evaluator；full 在 capability 检查通过后注册 composite、suppression-decided 和 maintenance evaluator。
- 维护模式开始和结束不得切割告警 `cycleKey`。维护结束且同一评估周期仍满足条件时，只允许同 cycle `SOURCE_RAISED` 更新 `occurrence/lastOccurred`，并发布 `device.alarm.occurrence-recorded.v1` 与 `device.alarm.suppression-decided.v1(decision=REEVALUATED)`，不得发布 `created` 或创建新 `alarmId`；仅在显式 `SOURCE_RECOVERED` 结束周期后，后续再次发生使用新 `cycleKey` 创建新告警。

## 7. 来源适配与事件合同

统一输入 `AlarmSourceEvent.v1` 的 Envelope `eventType` 固定为 `device.alarm.source-event.v1`、`source` 固定为 `iot-device`，`tenantId` 位于 Envelope；payload 包含 `sourceAction/sourceType/sourceId/cycleKey/siteId/sourceObjectId/deviceId/propertyCode/ruleId/ruleVersion/severity/occurredAt/timezone/originalOffset/quality/payloadRef/payloadHash`。`sourceAction` 只允许 `RAISED/RECOVERED`。

适配器：

- 现有阈值：`OPEN → SOURCE_RAISED`，`CLEARED → SOURCE_RECOVERED`；对外领域事件统一使用 `created`/`recovered` 命名。
- VIDEO/AI/RUNTIME：必须提供稳定来源 ID 与周期；不能根据相近时间猜测合并。
- 设备事件：从物模型事件身份生成周期；重复上报按 messageId 幂等。

输出 `device.alarm.created.v1`、`device.alarm.occurrence-recorded.v1`、`device.alarm.recovered.v1`、`device.alarm.status-changed.v1`、`device.alarm.escalated.v1` 和 `device.alarm.suppression-decided.v1` 放在 `iot-device-api`。首次创建沿用平台功能计划的 `created` 命名，不再发布历史同义事件；维护抑制只通过版本化决策事件表达，生产者与消费者执行当前/上一主版本合同测试。

## 8. API 与兼容

新 API 固定 `/api/v1/device/alarms/**`。旧阈值告警查询在一个发布周期内内部转为统一查询；旧写动作不存在明确等价语义时返回稳定不支持错误，禁止双写处置状态。

分页默认 50、硬上限 500；查询必须带租户条件并在服务端应用站点/设备数据权限。跨租户不存在与无权访问采用统一防枚举响应。

## 9. capability 与启动门禁

- `mini`：不创建告警 Bean、路由、消费者、调度任务和电力初始化数据。
- `standard`：仅 `power.alarm.core`，依赖数据库迁移版本、TelemetryStore、权限 Seed 和事件 transport 就绪。
- `full`：`power.alarm.advanced` 额外依赖规则配额、维护模式权限和复合执行容量基线。
- 任一依赖缺失时 capability 为 unavailable；不得降级成“接口成功但忽略行为”。

## 10. 迁移、对账与回滚

1. 只建新表与只读画像，不切流量。
2. 可重跑 backfill 写来源映射；歧义条目进入人工清单。
3. 开启来源双写，统一记录仍不作为主读。
4. 按租户/来源/等级/状态/时间全量与增量对账，缺失和重复为零后切读。
5. 阻断旧处置写，观察一个发布周期后停旧表业务写。

回滚切回旧读、停止新消费者，但不删除新表、Inbox、映射和审计。告警已在新域发生处置后不得恢复旧写以制造分叉。

## 11. 验证矩阵

- 单元：状态转换全矩阵、紧急忽略拒绝、误报双人、DSL 复杂度、质量与迟滞。
- 数据库：唯一周期、Inbox 重复/冲突、乐观锁、租户索引、中文注释检查。
- 合同：输入/输出事件当前与上一主版本、旧 API 兼容。
- 集成：阈值/VIDEO 来源重复与乱序、事务回滚、Kafka 重投、死信恢复。
- 安全：越权、跨租户、防枚举、恶意 DSL、超大分页。
- 档位：mini 无 Bean/路由/任务；standard 高级能力稳定拒绝；full 依赖不足 fail-closed。
- 迁移：backfill 可重跑、双写对账、切读与回滚演练。
