## 4. Mapper、实体与调用链对照

| 位置 | 当前事实 | 风险 |
|---|---|---|
| `ProductPropertiesMapper.xml` | `Base_Column_List` 包含目标库不存在的 `service_id` | `selectByPrimaryKey`、按 ID/服务查询可直接 SQL 失败 |
| Mapper `BaseResultMap` | 未映射 `service_id` | 即使未来补列，当前实体投影仍不闭合 |
| `ProductProperties` | 无 `serviceId` / `tenantId` 字段 | 与 API VO 和 Mapper 语义分裂；租户依赖拦截器隐式注入 |
| Param/Result VO | 都声明 `serviceId` | API 暴露了当前持久化事实无法承诺的字段 |
| Mapper `insert` | 16 个目标列对应 17 个 value；`propertyName` 后出现裸 `jdbcType=BIGINT}` | SQL 语法和列值数量均错误；不是单纯缺少参数前缀 |
| Mapper 其他 insert | `insertSelective`、`batchInsert` 的列值绑定成对；`insertOrUpdate` 的 UPDATE 分支又引用缺失的 `service_id` | 问题限定在具体 statement，仍需逐方法合同测试 |
| `findAllByServiceId` | Java 调用仍存在，但 XML statement 被注释 | 旧 TSL/模板导出路径存在 BindingException 风险 |
| `selectPropertiesByServiceIdList` | Java 调用仍存在，SQL 查询缺失列 | 旧聚合路径存在 SQL 失败风险 |
| 多租户 | `TenantLineInnerInterceptor` 默认启用，产品表不在 ignore 列表 | 方向正确，但 INSERT/CRUD 必须用集成合同证明，不能只凭配置关闭门禁 |
| 产品批量删除 `deleteProductByIds` | 只显式清理 services/properties，且注释与调用名称相反 | 未覆盖 events，也未通过服务 helper 清理 commands/requests/responses |
| 服务级联 `ProductServiceThingModelHelper.deleteCascade` | 覆盖 commands/requests/responses 后删除 services | 不处理产品属性或 events，不能替代产品级删除事务 |
| 单条删除 | 直接删除 product | 历史孤儿数据证明删除链风险不是理论问题；清理存量不等于修复删除链代码 |
| legacy release | 只校验产品标识并返回“发布成功” | 无版本、hash、快照、审计或 Outbox，继续按 TD-005 拒绝假成功 |

## 5. `service_id` 差异 ADR 候选

该问题影响整个 TSL 事实模型，不由本画像报告直接形成架构决策。已建立 [ADR-012：产品根属性与服务参数单一事实](../../架构决策/电力运维云平台/ADR-012-产品根属性与服务参数单一事实.md)，当前状态为 `Proposed / In Review`。

ADR 候选方向是：M1 标准属性作为产品根级遥测/配置属性，服务入参与出参由 `product_commands_requests/response` 表达。候选约束如下：

1. `product_properties` 继续作为产品根级属性表，不新增含义重叠的 `service_id`；
2. 服务参数统一落在 command request/response 链；
3. 盘点并迁移旧 `findAllByServiceId/selectPropertiesByServiceIdList` 调用，禁止保留“有时查属性表、有时查命令参数表”的双事实；
4. 删除 API VO 中无法兑现的 `serviceId`，或仅在独立 legacy DTO 中保留并明确废弃期；
5. 决策必须由非电力 TSL 导入/导出回归证明，不能只按新电力功能修改。

在 ADR-012 转为 `Accepted` 前，上述内容只用于门禁讨论，不授权删除 API、修改运行表或编写模板绑定 migration。如果评审决定补回 `product_properties.service_id`，则必须同时定义外键、租户一致性、根级属性表示方式、唯一键和历史数据回填；仅增加一个可空列不能关闭问题。

### 7.1 `@TenantIgnore` 使用点核对

当前 `iot-device` 共发现 5 个 `@TenantIgnore` 注解位置，而不是笼统的“6 处”：

| 位置 | 操作 | 是否直接触达模板版本表 | 处置 |
|---|---|---|---|
| `ProductMapper.selectByProductIdentification` | 跨租户按产品标识查询 | 否，但会影响产品绑定前置查询 | P0：禁止新模板绑定链复用；另建租户内查询 |
| `DeviceMapper.updateDevice` | 设备更新 | 否 | 保留现状，纳入设备回归 |
| `DeviceMapper.updateDeviceBySys` | 系统设备更新 | 否 | 保留现状，限制系统调用者 |
| `DeviceServiceImpl.findOneByDeviceIdentification` | 跨租户设备标识查询 | 否 | 不得作为模板租户授权依据 |
| `DmPackageController.uploadPackage` | OTA 包上传 | 否 | 与 TD-005 无直接关系 |

新增系统标准模板的跨租户只读必须使用 TD-005 §8 的专用仓储：即使进入 tenant-ignore 上下文，SQL 仍硬编码 `owner_scope='SYSTEM' AND tenant_id=0`；不得复用上述任一通用忽略点，也不得提供忽略租户的模板写方法。

## 8. 评审意见（2026-08-04）

### 8.1 总体评价

**画像报告质量：高。** 本报告是 TD-005 §23 门禁 1 的对应证据，定位清晰（"目标库事实采集，不自动代表生产存量"），结论克制（"画像已执行，发现阻断项"，而非宣称门禁通过），可复现命令、机器摘要 JSON、只读事务边界三要素齐备。§3/§4 的 8 项事实声明全部经本评审对照仓库代码逐条核对：

| 报告声明 | 代码核对 |
|---|---|
| `product_properties.service_id` 不存在 | ✅ PostgreSQL `information_schema.columns` 查询已证；`ProductPropertiesMapper.xml` 的 `Base_Column_List`（L30）、`insertOrUpdate` DO 分支（L525）、`selectPropertiesByServiceIdList`（L989）仍引用该列，运行时会报 column 不存在 |
| `BaseResultMap` 未映射 `service_id` | ✅ L4–24 无对应 `<result>`；`selectByPrimaryKey` 投影将缺字段 |
| `ProductProperties` 实体无 `serviceId` / `tenantId` | ✅ `ProductProperties.java` 字段列表不含二者；`tenantId` 完全依赖 `TenantLineInnerInterceptor` 隐式注入 |
| Param/Result VO 声明 `serviceId` | ✅ `ProductPropertyParamVO.java:48` `@NotNull Long serviceId`；`ProductPropertyResultVO.java:49` `Long serviceId` |
| `insert` 含 `#{propertyName},jdbcType=BIGINT}` 可疑绑定 | ✅ `ProductPropertiesMapper.xml:70` 第 3 个 value 为 `#{propertyName},jdbcType=BIGINT}`，缺少 `#{` 前缀，`insert` 路径在目标库会解析失败 |
| `findAllByServiceId` Java 调用存在但 XML 被注释 | ✅ Mapper 接口 L83、Service L45/L85、`ProductTemplateServiceImpl:130` 与 `ProductServiceImpl:382` 仍调用；XML L692–701 整段注释 → 运行时 BindingException |
| `selectPropertiesByServiceIdList` Java 调用存在但 SQL 缺列 | ✅ Mapper 接口 L128、Service L89/L150、`ProductServiceImpl:568` 仍调用；XML L989 使用 `service_id IN (...)`，目标库无该列 → SQL 失败 |
| 批量删除只显式清理 services/properties，未覆盖 events/commands/parameters | ✅ `ProductServiceImpl.deleteProductByIds`（L452–458）只调用 `productServicesService.deleteByTemplateIds` 与 `productPropertiesService.deleteByTemplateIds`，无 events/commands 清理；`ProductServiceThingModelHelper` 服务级联清理路径覆盖 commands/requests/responses，但同样遗漏 events |
| 单条删除直接删 product | ✅ `ProductServiceImpl.deleteProductById`（L468–469）直接调用 `productMapper.deleteProductById`，无任何级联 |
| 已出现 4 条孤儿属性 | ✅ SQL `ORPHAN_PROPERTY` 查询逻辑正确；JSON 中 2 组 `productIdentification`（`8700054938017792` / `9030000000000001`）各 2 条，均来自单条删除路径未级联 |

### 8.4 结论

**画像报告可采纳。** 8.1 的 10 项事实声明全部核对通过，可复现证据（SQL + JSON + 容器名）齐备，结论克制（"Open / Remediation Required"，未宣称门禁通过）。

TD-005 冻结路径建议：

1. **先 ADR**：把 §5 的"根属性 vs 服务参数单一语义"独立为 ADR-012 候选，先决策再实施；
2. **再清理 Mapper**：删除 `findAllByServiceId` / `selectPropertiesByServiceIdList` 的 Java 声明与调用点，或把调用迁移到 `product_commands_requests/response`；修复 `insert` 的 `#{propertyName},jdbcType=BIGINT}` 绑定；
3. **后清孤儿**：4 条孤儿属性按 R1–R7 建议形成可审计迁移清单 + 回滚脚本；
4. **再补门禁**：完成上述三步后再跑一次画像，对比 JSON 差异，门禁 1 才能判 PASS；
5. **不得**先创建 `power_model_template*` 新表而后补救运行表基础契约。

在 1–4 步完成之前，TD-005 不得进入 migration 编写阶段。
