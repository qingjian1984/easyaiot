# TD-006 附件：事件与 capability 合同

> 版本：0.1.2
> 日期：2026-08-25
> 状态：In Review / Freeze Candidate / Capacity Values OPEN
> 双基线：平台功能计划 1.5.0、EasyAIoT 项目开发宪法 1.6.0

## 1. 事件命名裁决

平台功能计划 1.5.0 使用 `device.alarm.created.v1`。因此统一告警首次创建事件固定为 `device.alarm.created.v1`，不再同时发布历史同义事件。重复发生使用 `device.alarm.occurrence-recorded.v1`，避免消费者把 occurrence 当成新 alarmId。

领域事件集合：

- `device.alarm.created.v1`
- `device.alarm.occurrence-recorded.v1`
- `device.alarm.recovered.v1`
- `device.alarm.status-changed.v1`
- `device.alarm.escalated.v1`
- `device.alarm.suppression-decided.v1`

输入来源合同为内部 `device.alarm.source-event.v1`。来源 Envelope 的 `eventType` 固定为 `device.alarm.source-event.v1`，`source` 固定为 `iot-device`；来源动作 `RAISED/RECOVERED` 只能出现在 `payload.sourceAction`，不得再作为 Envelope 的 `eventType`。Topic 名和 consumer group 在 transport 评审时冻结；业务 Schema 不绑定 broker 物理名称。

## 2. Envelope

所有事件包含：

| 字段 | 类型 | 规则 |
|---|---|---|
| `eventId` | UUID string | 全局唯一 |
| `eventVersion` | string | 当前为 `1.0` |
| `eventType` | string | 完整版本化事件名称；来源动作不放在此字段 |
| `tenantId` | decimal string | 不接受 JSON number |
| `occurredAt` | ISO 8601 offset string | 来源发生时间 |
| `recordedAt` | ISO 8601 offset string | 平台记录时间 |
| `source` | string | 当前告警合同固定为 `iot-device` |
| `correlationId` | string | 业务追踪；不得携带凭据 |
| `traceId` | string/null | 可选链路追踪 |
| `payload` | object | 按事件版本校验、限制大小 |

ID 在 JSON 中全部使用字符串，数据库数值 ID（包括 `alarmId`、`tenantId`、`siteId`、`ruleId`、`policyId` 和 `maintenanceContextId`）必须使用正十进制字符串；时间必须带 offset。消费者忽略未知可选字段，但拒绝未知主版本和缺失必填字段。

对外领域事件的 `alarmId` 是 Envelope 的逻辑必填事实，但唯一位置为 `payload.alarmId`；不得新增顶层 `alarmId`，来源事件在映射生成统一告警前不携带 `alarmId`。

## 3. 来源事件必填事实

`payload` 至少包含 `sourceType/sourceId/cycleKey/sourceObjectId/siteId/deviceId/severity/occurredAt/sourceAction/payloadHash`，规则来源另含非空 `propertyCode/ruleId/ruleVersion/quality`。`sourceAction` 只允许 `RAISED/RECOVERED`。`payload.payloadHash` 是来源证据摘要，不代表 Inbox 对规范消息正文计算的摘要；`messageId` 使用 Envelope `eventId`，同 ID 同 `envelopeHash` 为重复，不同 `envelopeHash` 隔离。

`tenantId/siteId/deviceId` 必须由受认证入口与设备权威事实核对，不能只信任 VIDEO/AI 或请求正文。

## 4. 领域事件最小 payload

- created：`alarmId/status/severity/sourceType/sourceId/cycleKey/siteId/deviceId/propertyCode/ruleId/ruleVersion/firstOccurredAt/occurrenceCount`。
- occurrence-recorded：`alarmId/status/occurrenceCount/lastOccurredAt/sourceMessageId`。
- recovered：`alarmId/fromStatus/status/recoveredAt/version`。
- status-changed：`alarmId/action/fromStatus/status/operatorId/reasonCode/version`；敏感自由文本只放受控引用。
- escalated：`alarmId/status/fromLevel/toLevel/policyId/policyVersion/escalatedAt/version`。
- suppression-decided：`alarmId/status/decision/maintenanceContextId/policyId/policyVersion/reasonCode/decidedAt/version`；`decision` 只能为 `SUPPRESSED`、`NOT_SUPPRESSED` 或 `REEVALUATED`，维护上下文、策略和原因在不适用时可为空；通知域只执行该决策，不自行评估告警。

输出事件不携带通知接收人、手机号、媒体 URL、原始大 payload 或规则完整 DSL。上述数据库数值 ID 均为正十进制字符串；仅在本节明确标注“可为空”的字段允许 `null`。

## 5. Schema 存放与兼容

设计候选 Schema 位于 `assets/td006-events/`，已按来源事件和六个领域事件分别形成独立文件：`device.alarm.created.v1.schema.json`、`device.alarm.occurrence-recorded.v1.schema.json`、`device.alarm.recovered.v1.schema.json`、`device.alarm.status-changed.v1.schema.json`、`device.alarm.escalated.v1.schema.json`、`device.alarm.suppression-decided.v1.schema.json`。`alarm-domain-event-v1.schema.json` 仅是评审联合校验候选，严禁直接复制为单一生产 Schema。实现时必须将六个独立 Schema 按事件拆分到生产者 `iot-device-api/src/main/resources/events/{event-name}/v1.json`，并对当前和上一主版本执行生产者/消费者合同测试。

v1 允许新增可选字段；删除/改类型/收紧必填/改变枚举语义必须创建 v2，执行消费者先行、双发、对账、清零积压和回滚。

### 5.1 Inbox、Outbox、hash 与 ack 最小合同

- `payload.payloadHash` 仅表示来源证据摘要；`envelopeHash` 由 Inbox 对规范化事件字节计算，格式固定为 `sha256:` 加 64 位小写十六进制。规范化版本和参与摘要的字节边界必须固定，不能依赖 Map/JSON 字段偶然顺序；若 transport 同时声明摘要，则与本地计算不一致时必须拒绝并进入隔离。Outbox 的 `payload_hash` 对生产者最终序列化正文计算，不能复用来源证据摘要。
- 来源消费必须在一个本地数据库事务内完成 Inbox 首次写入/重复裁决、来源映射或 `alarm_record` 创建/更新、动作审计和领域 Outbox 入列；事务提交前不得产生业务副作用或确认消息位点。
- 消费者使用手动 offset/ack：事务提交成功后才 ack；同 ID 同 `envelopeHash` 的重复、已持久化的隔离或已持久化的 DLQ 终态可以 ack；锁竞争、临时故障、retryable 错误和 DLQ 投递失败不得 ack，必须重投。
- 同一 `messageId/eventId` 同一摘要返回 `DUPLICATE`；同 ID 不同摘要进入 critical quarantine，保留首次事实、不修改告警，并产生可行动指标。Inbox 在同一业务事务内完成，不另建后台领取租约；Outbox 必须有全局唯一事件 ID、有限 attempts、租约恢复、下次重试时间和脱敏错误摘要。
- retryable 错误使用有界次数、退避、抖动和上限；Schema 非法、未知主版本、不可恢复业务错误进入 DLQ/quarantine。DLQ 写入成功且处置已持久化后才可 ack；DLQ 写入失败必须保留原 offset。DLQ 深度、隔离、重复、冲突、重试和积压必须可观测。
- 告警来源 Inbox 与 `power_model_event_inbox` 独立；不得复用后者表或幂等域。Outbox 领域事件只在包含告警状态/动作事实的本地事务提交后异步发送。

## 6. capability key 与 quota key

固定复用 ADR-011 已登记的：

- `power.alarm.core`
- `power.alarm.advanced`

core quota key 冻结为：

- `maxRulesPerTenant`
- `maxRulesPerSite`
- `maxActiveAlarmsPerTenant`
- `maxAlarmQueryDays`
- `maxRuleEvaluationsPerSecond`
- `maxAlarmConsumerConcurrency`

advanced quota key 冻结为：

- `maxCompositeRulesPerTenant`
- `maxRuleLeafConditions`（不得高于协议 16）
- `maxRulePoints`（不得高于协议 8）
- `maxRuleWindowSeconds`（不得高于协议 86400）
- `maxMaintenanceContextsPerTenant`

具体 standard/full 数值必须来自目标规模和压测。未冻结前不得修改正式 manifest，也不得以草案值做销售承诺。

## 7. capability 依赖候选

- core requires：`iot-device`、`iot-sink`、`postgresql`、`kafka`、`power.device.model`。
- advanced requires：core + `power.telemetry.history`。

依赖名必须与安装器/manifest 可识别的稳定标识对齐后才能写入正式 JSON；任何依赖缺失均 fail-closed，不返回伪成功。
