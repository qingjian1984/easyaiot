## 4. 执行步骤（获批且前置闭环后）

1. 记录审批单号、窗口开始时间、操作者和 canary 租户/workload；只记录标识，不记录密钥。
2. 显式创建并回查主 Topic/DLQ；核对分区、保留期、复制因子和 ACL/TLS 现状。
3. 以 API=false、事件=false、release-port=true 启动 `iot-device`；启动保护器必须通过，健康检查必须通过。
4. 核验 profile、capability 和第四端口 Bean；数据库四类积压仍须为 0。
5. 开启事件链并滚动重启；核验 listener/四处理器、消费组在线、lag=0、DLQ=0、Outbox relay 无异常。
6. 通过运行时密钥设施注入 HMAC secret，只输出 `configured=true` 和 UTF-8 字节长度是否合格，不输出值或摘要。
7. 开启绑定 API并滚动重启；对指定的一个租户、一个 workload 执行一次 canary。
8. 验证 binding、domain audit、Outbox、PUBLISHED release、ACTIVE projection、Inbox PROCESSED、coordination audit 的同事件一致性；重复同请求只允许幂等重放。
9. 观察期内持续核对 API 错误率、Outbox backlog、consumer lag、DLQ depth 和数据库状态，不扩大租户范围。

## 5. 停止与回滚

出现启动保护失败、处理器缺失、消费组离线、lag/DLQ 非零持续增长、事务事实不一致、projection CAS 失败、密钥不合格或未知错误时立即停止扩大范围，并按顺序：

1. 关闭绑定 API；
2. 等待并确认 Outbox `PENDING/PUBLISHING` 排空；若无法排空，保留事实并停止后续关闭，不得删除行或手工提交 offset；
3. 关闭事件链；
4. 关闭第四端口；
5. 保留数据库、Kafka、日志和指标证据，禁止直接 DROP、清 history、删 Inbox/Outbox 或回退版本号。

已成功发布的配置采用新版本补偿/回滚，不原地修改 PUBLISHED 快照和 ACTIVE 投影历史。
