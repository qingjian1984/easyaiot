## 1. 验收结论

P02-M2-02R1A 通过本地无数据库验收。候选 V011、持久化端口、JDBC 单语句分配器和来源事务已经统一使用独立动作序号；首次发生、再次发生和恢复均不再从 `row_version` 推导 `sequence_no`。

交付状态最多为 `Verified-Local / No Database Execution`。本轮没有执行 V011/U011、没有连接 PostgreSQL、没有调用 Docker 或读取 `.env`，因此不构成真实行锁、真实迁移、生产容量或上线证据。

## 2. 变更范围

实现严格落在任务单允许的七个文件：

1. V011 为 `alarm_record` 增加 `last_action_sequence BIGINT NOT NULL DEFAULT 0 CHECK (last_action_sequence >= 0)` 及中文注释；
2. V011 静态合同把列注释计数从 149 更新为 150，并增加字段与注释断言；
3. `AlarmSourcePersistencePort` 增加单一用途的动作序号分配端口；
4. `JdbcAlarmSourcePersistence` 使用 `tenant_id/site_id/id` 范围内的单行 `UPDATE ... RETURNING last_action_sequence`，0 行稳定 fail-closed；
5. `AlarmSourceTransactionService` 在首次创建后分配序号 1，在已有记录 CAS 成功后分配下一序号，再追加动作；
6. 应用测试增加序号从 1 开始、告警间隔离、确定性 fake 并发、幂等零消耗、CAS 失败零分配和事务回滚复用未提交序号；
7. JDBC SQL 合同拒绝 `MAX(sequence_no)`、`row_version` 条件和版本算术耦合。

未增加 listener、producer、scheduler、Controller、配置、capability、来源 adapter 或运行时建表逻辑。

## 3. Sol 独立代码复核

| 检查项 | 结果 |
|---|---|
| 状态 CAS 顺序 | `recordRaisedCas/recordRecoveredCas` 成功后才调用分配器；CAS 失败立即抛错并回滚 |
| 首次创建顺序 | 主记录/映射建立后分配序号，再追加动作、Outbox 和 Inbox `PROCESSED` |
| SQL 数据范围 | 分配语句同时包含 `tenant_id=:tenantId`、`site_id=:siteId`、`id=:id` |
| 原子性 | 单条 `UPDATE last_action_sequence=last_action_sequence+1 ... RETURNING`；不执行读后写 |
| 版本解耦 | 分配 SQL 不含 `row_version`；Java 动作路径无 `rowVersion()+2` |
| 错误处理 | 0 行返回 `ALARM_ACTION_SEQUENCE_TARGET_NOT_FOUND`；异常使外围 `REQUIRES_NEW` 事务回滚 |
| 回滚语义 | fake 事务快照覆盖 counter/action/outbox/inbox；失败后下一成功动作复用未提交序号 1 |
| 范围控制 | 仅七个允许文件；U011、runner 主体、transport、来源和配置均未修改 |
