# EasyAIoT 项目开发宪法

> 版本：1.6.0
> 状态：正式  
> 适用范围：EasyAIoT 仓库内所有新功能、重构、缺陷修复、数据库变更、接口变更与部署变更  
> 目标：保证云、边、端各模块在持续演进中保持边界清晰、数据可信、部署兼容、安全可控、可测试和可回滚

## 一、效力与解释

### 1.1 规则强度

- **必须（MUST）**：不可省略。违反时不得合并，除非经过书面例外审批。
- **应该（SHOULD）**：默认遵守。偏离时必须记录理由、风险和补偿措施。
- **可以（MAY）**：按功能需求和模块惯例选择。

### 1.2 指令优先级

发生冲突时，按以下顺序处理：

1. 安全、隐私、数据完整性和生产事故处置要求。
2. 本宪法。
3. 仓库根目录 `AGENTS.md`。
4. 模块内规则，例如 `APP/.cursor/rules/`、构建指南和模块 README。
5. 具体需求文档、设计稿和实现计划。
6. 既有代码惯例。

低优先级规则不得覆盖高优先级规则。若本宪法与实际代码或已批准架构决策不一致，应先核实并修订文档，不得静默绕过。

### 1.3 宪法目标

所有变更必须同时服务于以下目标：

- 每项产品能力必须声明适用部署档位；不要求同一业务功能覆盖 `mini`、`standard`、`full` 全部档位。
- 控制面、数据面、媒体面和推理面职责清晰。
- WEB、VISUALIZE、APP 通过稳定接口消费后端能力，不复制核心业务逻辑。
- 新功能可观测、可测试、可部署、可升级、可回滚。
- 不以破坏安全、数据一致性或边缘资源约束为代价换取短期交付速度。

## 二、不可违反的核心原则

### 第二条之一：业务价值先于技术实现

新功能开始前必须明确：目标用户、使用场景、业务问题、主流程、异常流程和验收标准。不得仅以“增加一个页面、接口或数据表”代替业务目标。

最小需求定义必须包含：

- 功能目标与非目标。
- 使用入口及目标端：WEB、VISUALIZE、APP、设备端或开放 API。
- 角色与权限。
- 状态流转、业务规则和失败处理。
- 涉及的数据、接口和模块。
- `mini` / `standard` / `full` 的适用性；不适用档位必须明确排除。
- 可验证的验收标准。

### 第二条之二：架构边界不可绕过

- `DEVICE` 必须作为业务控制平面和对外 API 中枢。
- WEB、VISUALIZE、APP 必须通过 DEVICE 的 HTTP/WebSocket API 访问业务能力；任何情况下不得直接连接业务数据库、Redis 或 Kafka，也不得持有 MinIO、Milvus、AI、VIDEO 的服务凭据。
- 已知允许的直连仅限：客户端使用 DEVICE 签发的短时、限对象、限操作预签名 URL 上传/下载 MinIO 对象，以及播放器使用 VIDEO/DEVICE 签发的短时媒体播放地址。签发、鉴权、租户范围和审计仍由后端负责。
- 新增其他直连例外必须由 Accepted ADR 明确协议、数据范围、凭据、有效期、审计、撤销和替代方案，并经安全评审；ADR 不得授权前端直连数据库、Redis 或 Kafka。
- AI 负责推理、训练、自动标注和模型服务，不承载用户、权限、设备台账等控制面业务。
- VIDEO 负责摄像机、视频流、抓拍、告警媒体处理及人脸/车牌视频业务，不成为通用业务数据库入口。
- NODE 负责工作节点注册、心跳和工作负载生命周期，不承载中心业务数据。
- `EDGE/` 已退役，不得作为新功能、部署或验收依据；历史 EDGE 配置或协议迁移必须通过 Accepted ADR，不得静默映射。
- RUNTIME 只承载对性能敏感的本地推理、编解码与计算任务，不复制 Java/Python 控制面逻辑；设备采集、补传和应用 ACK 仍归 `iot-sink collector`。
- 跨 Java 模块依赖必须通过 `iot-*-api` 或 `iot-common-*`，不得直接依赖其他模块的 `biz` 实现。

### 第二条之三：部署档位与产品能力边界

每项新功能必须说明在以下档位中的行为：

| 档位 | 最低内存 | 宪法要求 |
|---|---:|---|
| `mini` | 4 GB | 仅承载部署清单明确允许的原有轻量能力；不默认承接新增领域平台功能 |
| `standard` | 16 GB | 支持 AI、视频或园区级主要能力；资源消耗必须可配置 |
| `full` | 20 GB | 支持完整 IoT、视频、AI、管理和展示能力 |

若功能只适用于部分档位，必须通过能力探测、配置开关或明确的不可用状态处理，禁止启动后才以异常暴露缺失依赖。

#### 电力运维平台专项边界

- 电力运维平台仅支持 `standard` 和 `full`；`mini` 明确不支持，且不进入电力功能的需求、设计、实现和验收范围。
- 禁止为了让电力运维功能运行于 `mini` 而新增 mini 专用采集协议、时序存储、告警、能源、运维、SCADA 或报表实现。
- 电力相关服务、菜单、路由、后台任务、初始化数据和设备采集工作负载在 `mini` 必须不部署或保持关闭。
- 电力 API 在 `mini` 不得返回伪造空数据表示支持；若共享网关仍暴露入口，必须返回统一的“当前部署档位不支持”错误。
- 电力功能设计只需给出 `standard/full` 的资源预算、依赖、降级和验收；对 `mini` 只需验证能力未启用、无资源占用、无残留任务和无错误菜单。
- 已有非电力功能仍按各自产品计划声明档位，不得把本专项边界扩大解释为所有新功能都排除 `mini`。

#### standard 与 full 分级原则

- `standard` 是电力核心运维版，必须形成“采集—存储—监控—告警—处置—基础运维”的可用闭环，不得成为只能演示页面的残缺版本。
- `full` 是完整电力平台，包含 standard 全部能力，并增加多站点指挥、TDengine 高频时序、VISUALIZE/FUXA SCADA、事故追忆、高级能源、完整运维和经营报表。
- 档位差异 MAY 体现在规模、保留期、高级分析、编辑器、流程深度和集群能力，不得削弱认证、授权、租户隔离、遥控联锁、复核、审计、幂等、数据质量或回滚要求。
- standard 中开放的遥控能力必须满足与 full 相同的安全门禁；若依赖不完整，应整体关闭遥控，不得提供低安全版本。
- full 专属功能在 standard 必须通过统一能力清单关闭菜单、路由、API、后台任务和消费者，禁止仅靠前端隐藏。
- 同一公共 API 在两个档位均可用时必须保持契约一致；档位差异通过能力发现、配额和明确错误表达，不得维护两套不兼容接口。
- standard/full 的功能归属以《平台功能计划》的功能矩阵为准。变更归属属于产品与架构基线变更，必须同步更新 Spec、ADR、安装配置和验收用例。

#### standard/full 禁止重复开发

- `standard` 与 `full` MUST 使用同一代码主线、共享核心模块和公共契约；禁止建立两套独立分支或复制同功能代码长期维护。
- full MUST 是 standard 的严格能力超集：共享能力直接复用，full 只通过可选模块、扩展策略、更高配额或更强基础设施增加能力。
- 禁止以档位名复制 Controller、Service、Mapper、DTO、前端页面、组件、API、MQTT Topic、Kafka 事件或数据库表；确需差异时必须先证明语义不同，并通过 ADR 决策模块边界。
- 前后端、部署脚本、菜单和许可证 MUST 使用统一 capability manifest，禁止分别硬编码 `if standard`、`if full` 形成漂移规则。
- capability manifest 的 Schema、仓库位置、运行时 API、灰度与 CI 门禁遵循 ADR-011；实现不得另建第二份能力事实源。
- 存储后端差异 MUST 封装在稳定接口之后；业务规则、权限、质量码、幂等和查询语义不得因 PostgreSQL/TDengine 选型而复制。
- 公共数据库迁移必须向前兼容；full 专属模块可拥有独立表，但不得复制共享主数据形成第二事实源。
- standard/full 共享功能必须复用同一测试用例；CI 必须验证 standard 能力是 full 能力的真子集，并阻断 capability 清单与实际服务、菜单、API 不一致的变更。
- 代码评审发现同语义重复实现时必须阻止合并，除非已有 Accepted ADR 说明隔离原因、退出条件和消重计划。

### 第二条之四：兼容性优先

- 公共 API、消息结构、数据库字段、MQTT Topic 和环境变量的修改必须优先保持向后兼容。
- 删除、重命名或改变语义属于破坏性变更，必须提供迁移方案、兼容期和回滚方式。
- 新增字段应允许旧消费者忽略；不得让未同步升级的节点或客户端立即失效。
- 云端与边缘端可能独立升级，协议设计必须考虑版本协商和混合版本运行。

### 第二条之五：安全默认开启

- 所有新接口必须明确认证、授权、租户隔离和数据权限策略。
- 服务端必须实施权限校验；前端隐藏按钮不能作为权限控制。
- 不得在代码、文档、测试数据、日志或镜像中提交真实密码、Token、密钥、摄像机凭据或私有地址。
- 凭据和端口必须通过环境变量或配置中心管理，并同步维护 `env.example`。
- 文件上传必须校验类型、大小、名称、存储路径和访问权限。
- 外部输入必须校验；SQL、命令行、模板、路径、URL 和反序列化入口必须防止注入与越权。
- 日志必须脱敏，不得记录密码、完整 Token、身份证、人脸特征向量等敏感信息。

## 三、模块职责与技术约束

| 模块 | 职责 | 新功能必须遵守 |
|---|---|---|
| `DEVICE/` | 设备、用户、权限、任务、告警、数据集、节点等控制面 | Java 17+；遵循 API/BIZ 分层、Lombok、MapStruct、MyBatis-Plus；保留 `project.build.outputTimestamp` |
| `DEVICE/iot-sink` | MQTT/TCP/HTTP/工业协议适配、设备消息汇聚、collector 和可靠遥测投影 | 协议适配后进入统一物模型；collector 与中心复用契约；存储适配遵循 ADR-006；不得成为第二业务控制面 |
| `WEB/` | 管理控制台和指挥中心 | Vue 3 Composition API + TypeScript + Ant Design Vue；复用既有 API、权限、路由和组件模式 |
| `VISUALIZE/` | 大屏编辑器和 Web SCADA | Vue 3 + TypeScript + Naive UI；图表与组件配置必须可序列化、可迁移 |
| `APP/` | H5、小程序和原生 App | 必须先读取 `APP/.cursor/rules/`；遵守 UniApp 生命周期、条件编译、rpx、UnoCSS 和 Wot Design 约定 |
| `AI/` | 推理、训练、SAM、LLM | Flask 服务化；本地与 Docker requirements 严格分离；GPU/CPU 能力必须可探测和降级 |
| `VIDEO/` | 摄像机、流媒体、抓拍、告警、人脸/车牌 | 内部异步流程优先通过 Kafka；观看链路与算法链路保持解耦 |
| `NODE/` | Worker 节点与工作负载编排 | 保持端口 9100 控制职责；容器和子进程操作必须幂等并上报状态 |
| `RUNTIME/` | C++ 高性能本地执行引擎 | C++17；承载推理、编解码及实时/抓拍/轮巡执行；优先 RAII，不得新增硬编码绝对路径，不承载采集补传或控制面事实 |
| `.scripts/` | 安装、部署、诊断和初始化 | 脚本必须幂等、可诊断、支持目标平台与三档配置，不得硬编码凭据 |

## 四、新功能标准流程

### 4.1 阶段一：发现与边界确认

编码前必须完成：

1. 阅读相关模块 README、局部规则和同类功能实现。
2. 搜索可复用的 Controller、Service、DTO、组件、Hook、API、消息和数据表。
3. 确认当前工作区状态，保护用户已有未提交改动。
4. 输出影响范围：模块、接口、表、消息、配置、部署档位和测试。
5. 识别风险：权限、租户、并发、幂等、数据迁移、边缘离线、资源使用和兼容性。

### 4.2 阶段二：设计

跨模块或中高风险功能必须形成简要设计，至少包含：

- 业务流程与状态机。
- 模块归属和调用方向。
- API 契约和错误码。
- 数据模型、索引、保留周期和迁移方式。
- 同步/异步边界与失败补偿。
- 权限与租户模型。
- 适用档位的部署行为和资源预算；不适用档位的关闭与拒绝行为。
- 可观测性、测试和回滚方案。

禁止先写页面再倒推接口和数据模型，也禁止以跨层直连规避合理设计。

### 4.3 阶段三：实现

- 变更必须小而聚焦，不得夹带无关格式化、重命名或大规模重构。
- 优先复用现有抽象；只有两个以上明确消费者或稳定共性出现时，才提取公共抽象。
- 配置必须有安全默认值、说明和示例。
- 新增后台任务、消息消费者和设备指令必须支持幂等、超时、重试上限和失败记录。
- 长耗时操作不得阻塞请求线程；应返回任务标识并提供状态查询或事件通知。
- 资源必须有明确生命周期：线程、连接、流、文件、GPU 显存和临时文件必须释放。

### 4.4 阶段四：验证

开发者必须执行与改动范围匹配的最小充分验证：

- 正常路径。
- 权限拒绝与租户隔离。
- 输入边界和非法输入。
- 重复提交、并发与幂等。
- 外部依赖超时、断连和恢复。
- 混合版本或旧数据兼容。
- 对应档位构建或配置验证。
- 相关模块的编译、类型检查、单元测试或集成测试。

不能运行的验证必须在交付说明中列出原因、风险和建议执行命令，不得宣称“已通过”。

### 4.5 阶段五：交付

交付说明必须包含：

- 完成的功能和用户可见变化。
- 变更文件及模块范围。
- 数据库、配置、端口、依赖或部署变化。
- 已执行的验证及结果。
- 未验证项和已知限制。
- 升级、回滚或运维注意事项。

## 五、接口与通信规范

### 5.1 HTTP 与 WebSocket

- 外部业务 API 统一经 `iot-gateway` 暴露。
- URL、请求方法、DTO、分页、返回结构和错误码应沿用所在业务域惯例。
- Controller 只负责协议适配、校验和授权；业务逻辑进入 Service。
- DTO、VO、DO 不得混用；禁止直接将数据库实体作为公共 API 契约。
- 列表接口必须考虑分页、排序、过滤和最大返回量。
- WebSocket 消息必须包含类型、版本、时间和关联标识，支持断线重连后的状态恢复。
- 新公共 HTTP API 默认使用 `/api/v1/{domain}/...` 或由网关统一映射到等价 v1 路径；同一业务域不得混用路径版本和无版本路径。
- 在同一主版本中新增可选请求/响应字段、增加新端点或放宽校验属于兼容变化；删除/重命名字段、改变类型/语义、收紧必填、改变状态码语义属于破坏性变化，必须发布新主版本。
- 新主版本采用“消费者兼容 → 双版本运行 → 迁移监控 → 下线旧版”，旧版下线前必须发布弃用时间、调用方清单和回滚方案。

### 5.2 Java 微服务调用

- 同步跨服务调用使用 API 模块定义的 OpenFeign 契约，并提供合理的超时与降级。
- 高频、广播、耗时或无需即时结果的流程应优先使用消息总线。
- 禁止跨服务直接查询对方数据库。
- 分布式流程不得假设数据库事务能够跨服务生效；必须设计幂等、最终一致性或补偿机制。

### 5.3 MQTT 与设备指令

- Topic、QoS、消息版本、设备标识、租户标识和时间戳必须明确。
- 指令必须具有唯一请求标识，并定义确认、超时、重复消费和离线补发行为。
- 遥测与控制消息不得混用同一语义。
- 协议适配后应进入统一物模型/消息模型，避免上层业务绑定厂商私有格式。

### 5.4 Kafka 与异步事件

- 事件必须有稳定名称、版本、事件 ID、发生时间、来源和关联业务 ID。
- 消费者必须可幂等处理重复消息。
- 必须明确重试、死信、积压监控和失败恢复方式。
- 事件发布成功与数据库提交之间必须考虑一致性，关键流程应使用 Outbox 或等价机制。
- 事件 Schema 必须进入生产者 API 模块并版本化；兼容变化保留主版本，破坏性变化创建新 Topic/事件主版本。
- 破坏性升级必须消费者先行、生产者双发、逐消费者切换并对账；双发至少跨一个完整发布周期，旧版本积压和死信清零后方可停止。
- CI 必须对当前和上一主版本运行生产者/消费者合同测试与 Schema 兼容检查。

### 5.5 媒体与 AI 链路

- 观看链路（约 6500 Kbps）与算法链路（约 3500 Kbps）保持独立配置和故障隔离。
- 视频帧、快照、模型和数据集通过既定服务与 MinIO 交换，避免在服务间传递无界大对象。
- 推理请求必须声明模型版本、输入来源、超时和结果关联 ID。
- GPU 不可用时必须明确拒绝、排队或 CPU 降级策略，禁止静默卡死。

## 六、数据规范

### 6.1 存储选型

- PostgreSQL：关系型业务数据、配置、状态和审计。
- TDengine：设备遥测与时序数据。
- Redis：缓存、短期状态、分布式协调，不作为唯一事实来源。
- MinIO：模型、数据集、快照、录像等对象。
- Milvus：人脸等向量检索。
- Kafka：异步事件，不作为长期业务查询库。

### 6.2 数据模型

- 数据按业务域归属，不得建立跨服务共享表。
- 新表和关键查询必须设计必要索引，并评估数据增长规模。
- 状态字段应使用清晰枚举，记录创建/更新时间；需要审计的业务记录操作者。
- 多租户数据必须包含并执行租户隔离；不得仅依赖调用方传入的租户 ID。
- 时间统一明确时区和精度；跨系统传输优先使用 ISO 8601 或明确的 epoch 单位。
- 服务端时间事实优先使用 `Instant`/`OffsetDateTime` 或明确 UTC epoch 毫秒；禁止使用服务器默认时区解释跨系统时间。统计窗口必须声明 IANA 时区及 `[start,end)` 边界。
- Java 金额、计费、倍率、累计量和需精确十进制的比例 MUST 使用 `BigDecimal` 并明确 scale/roundingMode；整型最小单位可使用 `long`，但字段名和契约必须标明单位。
- JavaScript/TypeScript 对超过安全整数范围的 ID/数值 MUST 使用字符串；金额、倍率和计量运算使用十进制库或由服务端返回计算结果，禁止直接依赖 `Number` 浮点比较和累计。
- 坐标和模型置信度 MAY 使用浮点，但必须定义容差；数据库列精度、JSON 表达和前后端舍入规则必须一致。
- 新表、新字段和迁移脚本中的 DDL MUST 提供中文 `COMMENT ON TABLE` / `COMMENT ON COLUMN`（或等价数据库元数据描述），说明业务语义、取值约束、不可变/审计规则和事实来源；全量 dump、增量迁移与测试库 Schema 必须同步保留注释，禁止以无注释 DDL 或纯英文缩写交付。

### 6.3 数据库迁移

- Schema 变更必须提供可重复执行的迁移脚本，不得要求人工修改生产库。
- 迁移应优先采用“扩展—迁移—收缩”：先兼容新增结构，再迁移数据，最后移除旧结构。
- 大表迁移必须评估锁表、耗时、磁盘和回滚风险。
- 删除列、表或数据前必须有备份、保留期和明确审批。

## 七、前端与交互规范

- 页面必须覆盖加载、空数据、错误、无权限、禁用和成功反馈状态。
- 表单必须在前端提供即时反馈，但服务端仍必须完整校验。
- 危险操作必须二次确认，并明确对象和影响范围。
- 长任务必须显示进度或状态，不得让用户依靠重复点击判断结果。
- 权限点、菜单、路由和按钮权限必须与后端授权一致。
- API 类型应明确，禁止无理由使用 `any`。
- 复用项目现有布局、组件、请求封装、字典、国际化和错误处理机制。
- WEB/VISUALIZE 提交前至少运行 lint、构建和适用的类型检查；APP 运行 lint、type-check 和目标端构建。

## 八、可靠性与可观测性

- 所有跨网络调用必须设置连接和读取超时。
- 重试只用于可重试错误，并采用退避、抖动和次数上限；非幂等操作不得盲目重试。
- 服务和 Worker 必须提供健康、就绪和关键依赖状态。
- 日志应结构化并携带 trace/request/task/device 等关联标识。
- 关键业务必须记录成功率、失败率、耗时、队列积压和资源使用指标。
- 告警必须可行动，包含服务、环境、影响和定位线索，避免无上下文重复告警。
- 外部依赖故障不得造成无限等待、线程泄漏、无限队列或重启风暴。

## 九、性能与资源预算

- 新功能必须识别 CPU、内存、GPU、显存、磁盘、网络和数据库查询成本。
- 禁止无界队列、无界缓存、无界批量查询和一次性加载大型文件。
- 设备、视频和告警列表必须分页；批处理必须分片并支持恢复。
- RUNTIME 变更必须验证目标节点 CPU/GPU、内存、显存、码率和断流恢复预算，避免无界缓存与重复模型加载。
- 视频处理必须限制并发、帧率、码率和缓存长度。
- AI 模型加载必须避免重复占用显存，并定义卸载与模型切换策略。
- 性能优化必须基于测量，不得以牺牲正确性和可维护性为代价进行猜测式优化。
- 默认列表页大小不超过 50，服务端硬上限 500；批处理默认单批不超过 500 条，单次同步导出超过 100,000 行必须改为异步任务。业务 Technical Design 可基于压测调整，但必须设置有限上限。
- 新 API 必须声明目标吞吐、P95/P99 延迟、最大请求/响应体和超时；未给出领域指标时，普通查询 P95 目标不高于 500 ms，写操作 P95 不高于 1 s（不含明确异步任务）。

## 十、依赖、配置与部署

### 10.1 依赖治理

- 新依赖必须说明必要性、许可证、维护状态、体积和安全风险。
- 能用标准库或现有依赖解决时，不新增功能重叠依赖。
- AI/VIDEO 的本地 `requirements.txt` 与 Docker `requirements-docker.txt` 不得混用。
- 不得无范围升级框架或锁文件；依赖升级必须独立验证兼容性。

### 10.2 配置治理

- 环境差异通过 `.env`、Nacos 或部署配置表达，不得写死在代码中。
- 新配置必须包含名称、用途、类型、默认值、是否必填和示例。
- 敏感配置不得提供真实默认值。
- 配置变更必须兼容旧部署或给出明确升级说明。
- 功能开关必须有 owner、默认值、作用域、创建原因、审批单、启用/失效时间和删除期限；永久产品能力使用 capability manifest，临时灰度开关使用 Nacos/部署配置中心。
- 灰度范围只能使用租户、站点、节点或明确白名单；实验数据必须带实验标识并遵守相同租户隔离，禁止跨租户混合对照。
- 安全、权限、审计、数据完整性和遥控联锁不得作为 A/B 变量。灰度失败必须可一键回退并保留配置审计，前端本地存储不得作为功能开关事实源。

### 10.3 部署治理

- Docker Compose、Dockerfile 和安装脚本变更必须考虑 Linux、macOS、ARM、麒麟及适用的 Windows 路径。
- 安装和启动脚本应幂等；重复执行不得损坏已有数据。
- NODE Agent 与 RUNTIME 的 Host 原生进程边界不得被容器化变更意外破坏；`iot-sink collector` 的容器/Windows 受控进程边界遵循 ADR-007。
- 新服务必须定义端口、健康检查、依赖顺序、资源限制、日志和持久化卷。
- 不得随意改变已有端口；确需改变时必须同步网关、Nginx、Compose、示例配置和文档。

## 十一、代码质量规则

- 命名表达业务语义，避免无意义缩写和 `temp/new/final2` 等临时名称。
- 函数和类保持单一职责；复杂条件应拆分为可测试的领域规则。
- 注释解释“为什么”和约束，不重复代码表面行为。
- 禁止吞掉异常；必须转换、记录或向上返回具有业务语义的错误。
- 不得提交调试输出、临时代码、生成缓存、日志、大型模型或构建产物，除非仓库明确要求。
- 不得删除或覆盖不属于当前任务的用户改动。
- 不得使用破坏性 Git 操作清理工作区。
- 修复缺陷时应补充能够复现该缺陷的测试或验证步骤。

## 十二、测试与质量门禁

### 12.1 分层测试

- 领域规则、映射、校验和工具函数：单元测试。
- 数据库、消息、缓存和服务协作：集成测试。
- 跨模块关键流程：契约测试或端到端测试。
- 视频、设备、AI 和边缘流程：提供可复现的样例、模拟器或测试夹具。
- OpenFeign/HTTP 公共 API 必须对当前主版本运行提供者与消费者合同测试；破坏性升级同时覆盖旧/新版本迁移窗口。
- Kafka/MQTT 公共消息必须使用版本化 Schema/夹具验证生产者、消费者、未知字段、重复消息和前一主版本兼容性。

### 12.2 模块最低门禁

| 模块 | 最低验证 |
|---|---|
| DEVICE | 受影响 Maven 模块编译；相关 JUnit；权限拒绝、租户隔离、输入边界、幂等/重复提交、依赖超时测试；跨模块 API/事件变更执行合同测试；必要时 `-am` 验证依赖模块 |
| WEB | `pnpm lint`、`pnpm type:check`、`pnpm build` |
| VISUALIZE | `pnpm lint`、`pnpm build`；类型检查能力存在时必须执行 |
| APP | `pnpm lint`、`pnpm type-check`、至少一个目标端构建 |
| AI / VIDEO / NODE | 相关 pytest；导入/启动检查；依赖和配置校验 |
| RUNTIME | CMake 配置与构建；相关平台测试或最小推理样例；消息上报与 VIDEO/NODE 调度合同 |
| 部署脚本 | Shell 语法检查、Compose 配置解析、目标档位 dry-run 或等价验证 |

上述是最低命令门禁，不替代 §4.4 的场景门禁；改动涉及的 §4.4 场景必须有自动化测试或可复现验收证据。

涉及新表/字段的 DDL 或迁移脚本必须包含中文表/字段注释，并在评审 diff 中核对；无中文注释的数据库结构变更不得通过最低门禁。

纯文档改动可以免除代码构建，但必须检查链接、命令、版本和示例与代码一致。

### 12.3 合并阻断条件

存在以下任一情况不得合并：

- 验收标准未满足。
- 构建、类型检查或相关测试失败。
- 出现越权、凭据泄漏、注入或租户隔离缺陷。
- 数据迁移不可回滚且未获批准。
- 公共接口发生未声明的破坏性变更。
- 新服务无健康检查、关键配置或部署说明。
- 已知高风险问题没有责任人、处置计划和明确批准。

## 十三、Git 与评审规范

- 新功能从团队当前集成基线创建功能分支，目标合并到开发集成分支；紧急修复从生产基线创建，并同步回开发分支。
- 分支名称应表达类型和功能，例如 `feature/device-batch-import`、`fix/video-stream-timeout`、`hotfix/auth-bypass`。
- 提交应小而完整，一次提交表达一个逻辑变化。
- 提交信息推荐使用 Conventional Commits：`feat`、`fix`、`refactor`、`test`、`docs`、`build`、`chore`。
- 合并前必须检查 diff，确认没有凭据、调试代码、无关格式化和生成物。
- 中高风险变更至少需要一名了解相关模块的评审者。
- 评审顺序：正确性与安全 → 架构边界 → 数据与兼容性 → 测试 → 可维护性 → 风格。

仓库远端默认分支和分支保护规则是基线事实源。受保护默认/集成分支禁止直接推送，所有变更必须经功能分支和 Pull Request 合并；紧急修复也必须补 PR、评审和向集成分支回合。若仓库未配置默认分支或保护规则，维护者必须先记录并配置，开发者不得自行选择目标分支。

## 十四、文档同步

以下变更必须同步文档：

- 新增或修改公共 API、WebSocket、MQTT Topic、Kafka 事件。
- 新增数据库、表、字段、索引或数据保留策略。
- 新增服务、端口、中间件、环境变量或部署步骤。
- 修改模块职责、调用关系或三档部署能力。
- 修改用户操作流程、权限、状态机或运维方式。

架构事实优先维护在 `.doc/架构设计/`，操作规范维护在 `.doc/开发规范/`，模块使用说明维护在对应模块 README。宣传材料不得作为技术实现的唯一依据。

## 十五、完成定义（Definition of Done）

一项新功能只有同时满足以下条件才算完成：

- [ ] 目标用户、业务价值、范围和验收标准明确。
- [ ] 模块边界、接口、数据和异步流程设计合理。
- [ ] 权限、租户、输入校验和敏感数据处理完整。
- [ ] 正常、异常、边界、并发和依赖故障场景已处理。
- [ ] 适用部署档位已明确；不适用档位已验证功能关闭且无残留资源与任务。
- [ ] standard/full 共享能力使用同一实现与合同测试，未出现按档位复制的 API、服务、页面、表或消息契约。
- [ ] 数据库、配置、依赖和部署变更具备升级与回滚说明。
- [ ] 相关测试、编译、类型检查和构建通过。
- [ ] 日志、指标、健康检查和故障定位能力满足运维需求。
- [ ] 公共契约和用户/开发/部署文档已同步。
- [ ] Diff 中不存在凭据、调试代码、无关改动或不应提交的产物。
- [ ] 交付说明列出验证结果、限制和风险。

## 十六、例外与修宪机制

### 16.1 临时例外

无法遵守某条 MUST 时，必须在实现前记录：

- 违反的条款。
- 业务原因和替代方案评估。
- 风险、影响范围和安全边界。
- 临时补偿措施。
- 责任人、到期时间和消除技术债计划。

安全、租户隔离、凭据保护和数据不可逆删除原则不得以普通进度压力申请例外。

### 16.2 修宪

修改本宪法必须：

1. 说明修改动机与受影响模块。
2. 给出迁移期和对既有代码的影响。
3. 由项目维护者审阅批准。
4. 更新版本号和修订记录。
5. 必要时同步 `AGENTS.md`、模块规则和 CI 门禁。
