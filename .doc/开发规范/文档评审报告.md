## 二、总体评价

两份文档质量较高，体现了系统性的架构思维和严格的工程治理意识。

- **平台功能计划**——业务层面的详细实施蓝图，功能分级、阶段划分和风险识别扎实，主要短板在于部分技术细节（时序存储抽象、capability manifest、事件版本协议）的定义不够落地，以及缺少时间维度。
- **开发宪法**——工程层面的坚实治理框架，规则体系、优先级链、流程管控和例外机制设计成熟，主要短板在于个别条款存在过大的例外口子、§4.4 与 §12.2 门禁不一致、关键基础设施有制度要求无技术规范。

两份文档的交叉引用和一致性整体良好，与 CLAUDE.md 描述的架构高度一致。

## 三、优点总结

### 3.1 平台功能计划

1. **架构决策务实**：明确"不重建底座"，复用既有模块，新增 `iot-energy` 和 `iot-maintenance` 两个领域模块
2. **standard/full 单一实现原则**清晰：禁止两套分支/复制同语义代码，full 是 standard 的严格超集
3. **mini 排除策略完整**：从需求、设计、实现、安装、菜单、路由、API 多维度明确
4. **阶段划分合理**：P0→P6 遵循"先数据→再安全→再运维→最后分析"的递进逻辑
5. **Mermaid 图表丰富**：7 张图覆盖功能脑图、架构图、序列图、流程图等关键视角
6. **状态机设计完整**：告警、巡检、缺陷、工单四个核心状态机逻辑自洽
7. **事件契约要求完备**：五要素 + 消费者幂等，符合分布式系统最佳实践
8. **风险识别到位**：7 项风险均有对应控制措施
9. **MVP 范围合理**：聚焦"单站点配电房无人值守"，避免了范围蔓延

### 3.2 项目开发宪法

1. **规则强度分级（MUST/SHOULD/MAY）+ 优先级链**清晰可执行
2. **架构边界约束准确**：DEVICE 为中枢，各模块职责与 CLAUDE.md 完全一致
3. **完成定义（DoD）清单**12 项可操作，可直接用于 PR 评审
4. **例外与修宪机制**防止"静默绕过"
5. **附录模板（立项 + ADR）**为后续 Technical Design 提供标准化输入
6. **修订记录完整**：4 个版本变更清晰可追溯

## 四、发现的问题（按严重程度排序）

### 4.1 CRITICAL（合并前必须修复）

| 编号 | 文档 | 问题 |
|---|---|---|
| C1 | 功能计划 §8.4 / §8.7 | **遥控操作统一入口未明确**。`device:control:switch` 和 `device:control:approve` 权限归属不清——申请/审批走 `iot-energy` 还是 `iot-device`？实际执行通过哪个模块的物模型服务？存在控制逻辑分散风险，违反宪法"DEVICE 必须作为业务控制平面和对外 API 中枢"原则 |

### 4.2 HIGH（强烈建议修复）

| 编号 | 文档 | 问题 |
|---|---|---|
| H1 | 功能计划 §1.4 + 宪法 §2.3 | **时序存储抽象层（TimeSeriesAdapter）缺少设计锚点**。要求"存储后端差异封装在稳定接口之后"，但未定义接口方法签名、standard 在高频写入下的性能边界、standard→full 升级时的数据迁移路径 |
| H2 | 功能计划 §8.3 | **告警状态机缺少"误报/忽略"分支**。当前 `ACTIVE→ACKNOWLEDGED→PROCESSING→RECOVERED→CLOSED` 缺少运维人员判定误报的路径和临时忽略的中间状态，影响告警数据质量统计 |
| H3 | 功能计划 §4.1 第5行 | **时序存储描述存在矛盾**。§4.1 称"standard 使用 PostgreSQL 分区时序表**或经批准的 TDengine 配置**"，与 §1.3 "standard 默认不部署 TDengine"存在潜在冲突，"经批准"的审批标准未定义 |
| H4 | 功能计划 §8.2 | **能源模型缺少计量点倍率约束定义**。`MeteringPoint` 未说明 CT/PT 倍率是否为必填、倍率变更是否有历史追溯、抄表值计算公式是否在模型层面固化 |
| H5 | 功能计划 §1.3 + §4.2 | **`iot-sink collector` 的架构归属不清晰**。"M1 由 NODE 部署 `iot-sink collector profile`"，但 collector 是 `iot-sink` 的新 profile 还是独立进程？NODE 如何管理其生命周期？standard 档位的边缘采集完全依赖此 collector，设计延迟会阻塞 M1 |
| H6 | 功能计划 §8.3 + 现有代码 | **新告警状态机与现有 `iot-sink` 告警实现的衔接未说明**。是扩展现有 `AlertDO` 还是新建表？现有"未恢复告警"查询逻辑如何兼容？§11 已识别"新旧告警两套入口"风险但未给出解法 |
| H7 | 功能计划 §8.5 + 宪法 §5.4 | **Kafka 事件版本升级协议缺失**。事件名使用 `v1` 后缀，但两份文档都未定义版本升级策略（如何从 v1 迁移到 v2、是否并行消费） |
| H8 | 宪法 §2.3 | **capability manifest 数据结构未定义**。功能计划 §1.4 和宪法 §2.3 均要求统一 capability manifest，但 schema、存储位置、读取方式、CI 校验规则均未定义——这是 standard/full 单一实现的核心基础设施 |
| H9 | 宪法 §2.2 | **"经批准的专用架构设计"例外口子过大**。WEB/VISUALIZE/APP 不得直连数据库/Kafka/MinIO，"除非存在经批准的专用架构设计"是一个过大的例外，建议明确列举已知例外（如 MinIO 直连用于文件上传下载） |

### 4.3 MEDIUM（建议迭代优化）

| 编号 | 文档 | 问题 |
|---|---|---|
| M1 | 功能计划 §8.6 | 能源核算对时间精度未统一定义——冻结值时间点精度、时区处理策略、统计周期边界均未明确 |
| M2 | 功能计划 §4 | 阶段 4 目标"形成可信的用能数据"过于乐观，MVP 仅要求"自动抄表"但未包含"可信"验证 |
| M3 | 宪法 §4.4 vs §12.2 | 验证要求与门禁不一致——§4.4 要求验证权限拒绝、租户隔离、幂等等，但 §12.2 门禁只要求"相关 JUnit"，明显低于 §4.4 |

| M5 | 宪法 §10.2 | 功能开关未定义灰度发布规范——开关值存储位置、审批流程、A/B 测试数据隔离均未说明 |

| M7 | 功能计划 §8.2 | 领域模型只列出聚合名称，未说明聚合之间的关联关系（外键方向、引用关系） |
| M8 | 功能计划 §10 | 里程碑 M1-M6 只有验收条件，缺少时间估算或工期参考 |
| M9 | 功能计划 §8.9 | 人员轨迹隐私合规设计偏弱——授权粒度、数据最小化实现、法律依据未说明 |

## 七、综合改进建议

### 7.1 立即行动（进入 Technical Design 前必须完成）

#### 1. 产出 3 份 ADR

| ADR | 核心内容 |
|---|---|
| `ADR-TimeSeriesStorageAbstraction` | 时序存储抽象接口、standard 配额上限、升级迁移路径 |
| `ADR-AlertModelMigration` | 新旧告警状态机合并策略、数据迁移方案 |
| `ADR-CapabilityManifest` | capability manifest 的 JSON schema、存储位置、前后端消费方式、CI 校验规则 |

#### 2. 修复 C1：明确遥控操作统一入口

申请/审批走业务模块（`iot-energy` 或 `iot-maintenance`），实际执行必须通过 `iot-device` 的物模型服务调用机制。

#### 3. 修复 H2：告警状态机补充"误报/忽略"分支

```text
ACTIVE → ACKNOWLEDGED → PROCESSING → RECOVERED → CLOSED
   └──────────────→ ESCALATED
   └──────────────→ IGNORED（带Reason）
   └──────────────→ FALSE_ALARM（不可逆）
```

#### 4. 修复 H4：能源模型补充计量点倍率约束

- `MeteringPoint` 必须包含：`currentRatio`、`voltageRatio`、`calculationFormula`
- `MeterReading` 必须包含：`rawValue`、`appliedRatio`、`calculatedValue`
- 提供倍率变更历史表 `MeterRatioHistory`

#### 5. 修复 H3：统一时序存储表述

明确 standard 的默认时序方案为 PostgreSQL 分区表，TDengine 仅作为"经架构评审批准的替代方案"并列出审批条件。

### 7.2 迭代优化（M3 前完成）

6. 宪法 §12.2 补充契约测试要求，与 §4.4 验证要求对齐
7. 宪法模块职责表补充 `iot-sink`
8. 功能计划补充 collector 部署拓扑图
9. 定义 Kafka 事件版本升级协议
10. 功能计划为里程碑添加时间维度
11. 收窄宪法 §2.2 的例外口子，列举已知例外

### 7.3 后续完善

12. 建立电力领域术语表
13. 宪法 §6.2 补充精度类型指引
14. 宪法 §9 补充量化基准参考值
15. CLAUDE.md 补引 standard/full 单一实现原则
16. 功能计划补充聚合关系图
