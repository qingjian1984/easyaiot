## 二、总体评价

### 2.1 突出优点

1. **核对记录的「修正自己上一轮结论」是治理链中罕见的诚实操作**。C0 验收记录曾把 M1 identity/route 表述为「没有最终冻结且已提交证据」；本轮核对发现该表述过时（ADR-017 已 Accepted、LC02-06 已 SOL-ACCEPTED），显式修正为 `CLOSED-CONTRACT / RUNTIME OPEN`，同时明确「合同关闭 ≠ 运行就绪 ≠ C1 解锁」三层区分——这正是宪法「未获得实际证据的事项继续标记 OPEN」的反向正确应用：**获得了证据的事项应及时关闭，而不是永远保守**。
2. **五项关键代码事实经交叉验证全部属实**（本报告评审方法列）：`TelemetryDeviceAuthorityResolutionDTO` 确实只有 `product/device/status/tenantId` 四字段无 siteId；`selectLatestOpen(deviceIdentification, propertyCode)` 确实存在且被恢复路径使用；`kafkaSent` 字段 + Kafka 成功后更新确实构成非原子直发链；`AlarmSourceTransactionService:42` 确为 `REQUIRES_NEW`；`DeviceEventSubscriber:87-91` 确实 catch 后仅记日志。核对记录没有为了让 C1 显得 ready 而美化任何一项。
3. **「不可直接复用」清单（§4.2）质量极高**。五条禁令各自堵住一个真实的高危捷径：`IotDeviceMessage.id` 后端生成不能当 eventId、单一 telemetry messageId 不能当多规则告警的身份、siteCode≠siteId、authority 不证明站点、REQUIRES_NEW 不能静默嵌入旧事务。这五条与 02C §6 身份决策表的缺口列严丝合缝。
4. **C1P 任务单的「确定性 eventId」条款是全链防重放的核心**。显式排除随机 UUID/数据库序列/接收时间/当前时间，要求 UUIDv5 必须冻结 namespace + canonical name 字段序 + golden fixture——这把 M1 侧 JCS/canonical 的纪律完整平移到了告警域，避免了两个域身份语义分叉。
5. **C1P-04 三方案取舍框架正确**。同事务/源侧 Outbox/只读投影三选一并冻结失败矩阵，且特别点名「不得只在外层加 @Transactional 后声称原子」——这正是本评审验证过的 REQUIRES_NEW 陷阱的直接防呆。

### 2.2 主要短板

1. **ADR 索引更新时机的表述自相矛盾**（D-01）：任务单 §1 说「完成验收并经决策所有者接受后才能更新 ADR 索引和转 Accepted」，但白名单 §4 又允许改 README「仅在 ADR Accepted 后」——两处一致，但 §6 验收标准却给出「`ADR Accepted / C1 Contract Gate Closed`」作为合法终态之一，未说明该终态下 README 是否必须同步更新、由谁更新。若验收时 ADR 已 Accepted 而 README 未更新，索引与实际状态漂移。
2. **「C1 Contract Gate Closed」的量化标准未定义**（D-02）：验收标准允许终态二选一（Proposed 或 Accepted/Closed），但「Contract Gate Closed」对应 C1 前置门禁核对记录 §3 表中 4 项 OPEN 全部关闭，任务单未显式逐项映射这 4 项到 C1P-01～04 的交付物，验收者需自行推断对应关系。
3. **处置记录 1.2.0 的覆盖声明停在 R1A**（D-03）：处置记录状态行为「N-01/N-03 Closed / N-02 Closed-Local」，其 §1 已提及 C1P 核对与任务单，但未把这两份新文件纳入「评审输入」清单的正式版本管理；本轮评审报告（本文件）成为它们的第一份独立评审，处置链需要一次衔接声明，避免出现「C1P 两文件从未被任何评审处置记录覆盖」的断档。

## 三、问题清单

### DOC（建议处置，不阻断 C1P 执行）

#### D-01｜ADR-019 索引更新责任与终态一致性

- **事实**：任务单 §4 白名单允许改 `架构决策/README.md`（仅 ADR Accepted 后）；§6 验收标准终态含「ADR Accepted / C1 Contract Gate Closed」。两处组合下，「Accepted」终态出现时 README 更新是隐含必须还是可选未定义；若 Sol 验收在决策所有者接受**之前**执行，README 处于「白名单允许但前置条件未满足」的悬空窗口。
- **建议**：C1P 交付时在任务单或 ADR-019 头部显式一行「README 索引行由决策所有者接受的同一变更更新，不由 Sol 验收变更更新」；或将 README 移出本任务白名单、留给接受后独立小提交。
- **处置建议**：采纳，随 ADR-019 起草时关闭。

#### D-02｜「C1 Contract Gate Closed」与核对记录 §3 四项 OPEN 的显式映射缺失

- **事实**：核对记录 §3 列出 C1 解锁 6 项条件，其中 4 项 OPEN（tenant/site/device 权威、THRESHOLD 周期、DEVICE_EVENT 映射、原子/补偿）。C1P 任务单四个子任务 C1P-01～04 与之一一对应，但任务单 §6 验收标准未写明「Closed 判定 = §3 四项 OPEN 全部落入 ADR-019 的冻结决策」。验收者可能只对照 C1P 自身交付物而漏查上游门禁表。
- **建议**：验收标准补一行「`C1 Contract Gate Closed` 逐项对应核对记录 §3 的 4 项 OPEN 并在 ADR-019 附关闭映射表」。
- **处置建议**：采纳，任务单 1.0.1 微修订；若不改任务单，则在 ADR-019 附录自带该映射亦可。

#### D-03｜处置链断档：本轮两份文件未进入任何处置记录的评审输入版本链

- **事实**：`PRD-02-P02M2-02新功能方案评审处置记录` 停在 1.2.0（输入为该评审报告 1.0.0，对象止于 02C0/C1P 前）；本报告是 C1P 核对记录与任务单的第一份独立评审。若后续 ADR-019 评审发生争议，回溯「这两份文件依据哪份评审处置」会出现空指针。
- **建议**：随本报告出具处置记录（1.3.0 或新文件），显式声明「C1P 核对记录 1.0.0 + C1P 任务单 1.0.0 评审通过，D-01～D-03 处置如下」。
- **处置建议**：采纳，本报告处置记录随同提交。

### 亮点确认（无需处置，仅记录）

- 核对记录 §2「不读取工作区未提交 M1 文档作为冻结证据」的隔离声明，与本评审时工作区实际存在未提交 M1 文档改动的事实互相印证——该隔离是真实执行而非纸面声明。
- 任务单 §5 停工条件第 3 条（阈值无可版本化 rule identity 时停止）与核对记录 §5.1「现有阈值记录能提供规则主键候选，但缺不可变规则版本」的判断衔接准确：把「可能需要先迁移数据模型」设为停工而非静默扩权，正确。
