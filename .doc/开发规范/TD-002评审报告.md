## 一、总体评价

TD-002 工程质量极高，是目前文档链中最完备的技术设计之一。从 SQLite Schema（含 STRICT 表、CHECK 约束和索引设计）到容量保护状态机、崩溃恢复验收、导出迁移流程，形成了完整的可靠 outbox 实现方案。单写者架构避免了 WAL 锁竞争，同事务 gap 写入杜绝了静默数据丢失。

主要亮点：

1. **单写者架构精确**——所有写操作（采集、ACK、claim、清理、gap）共享唯一 writer，通过有界 MPSC 命令队列提交，避免 WAL 锁竞争。
2. **SQLite Schema 工程化**——STRICT 表、CHECK 约束、版本化 migration、PRAGMA 锁定，运行时校验 SQLite 版本。
3. **Envelope V1 字节契约**——落库与发送复用同一份 canonical JSON 字节，重试不刷新 `sentAt`，保证端到端字节一致性。
4. **容量保护状态机完整**——NORMAL → WARNING → PROTECTING → EXHAUSTED 四级保护，淘汰顺序固定，同事务 gap 写入。
5. **崩溃恢复验收覆盖 8 个崩溃点**——入队前、BEGIN 后、COMMIT 前后、claim 前后、MQTT 前后、ACK 前后、gap/死信之间、清理/checkpoint 之间。
6. **SPEC-004 追踪矩阵扩展至 DQ-020**——覆盖全部原始需求并补充了实现层必要的衍生需求。
7. **导出/导入/迁移流程完整**——manifest + JSONL + SHA-256 + 签名，幂等导入，单 owner 迁移。
8. **冻结门禁 7 条可操作**——覆盖接口一致、Schema 评审、TD-003 协同、驱动证据、容量参数和运维评审。

主要短板：

1. **DQ-016～DQ-020 为 TD 层新增需求，未在 SPEC-004 中定义**——虽内容合理，但存在规格基线漂移风险。
2. **TD-003 尚未冻结，多项关键参数依赖 TD-003**——ACK 等待超时、发送批量、MQTT topic 和投影细节均未锁定。
3. **DEAD_LETTER 保留期限未定义**——长期积压的人工处置队列可能占用大量磁盘。

### 2.3 §6 Envelope V1

#### 优点

- 落库与发送复用同一份 canonical JSON 字节，避免重试时字节不一致。
- `tenantId` 使用十进制字符串，解决了 SPEC 评审 S1-01/S4-01 识别的精度隐患。
- `messageId` 使用 RFC 4122 UUID v4，明确"不承载时间顺序"。
- `sentAt` 在首次本地持久提交前取值并保持不变。
- 单 envelope 上限 64 KiB，超限返回 `ENVELOPE_TOO_LARGE`。

#### 发现的问题

| 编号 | 严重度 | 问题 |
|---|---|---|
| T02-04 | **HIGH** | **§19 追踪矩阵引用了 DQ-016～DQ-020，但 SPEC-004 1.4.0 只定义到 DQ-015**。这 5 个需求（tenantId 字符串、单 writer、中心乱序窗口、中心封账、稳定 ACK 分类）内容合理，但未在 SPEC-004 中定义。若作为 TD 层实现需求，应标注为"TD-002 衍生"而非与 SPEC-004 需求混排；若作为产品需求，必须先更新 SPEC-004 版本。建议在追踪矩阵中显式区分"SPEC 原始需求"和"TD 衍生需求"，并在评审冻结前确认 SPEC-004 是否需要 MINOR 版本更新 |

| T02-06 | **MEDIUM** | **`siteCode` 在 envelope 中必填，但 ADR-004/SPEC-001 允许旧设备无 siteCode**。TD-002 §7 schema 中 `site_code TEXT NOT NULL`，与旧设备兼容存在冲突。建议确认：旧设备在 outbox 中的 `site_code` 使用什么值？空字符串？还是需要一个兼容值（如 `"unassigned"`）？ |
| T02-07 | LOW | **canonicalization 规则引用 TD-001 "版本化 JCS 等价规则"，但 TD-001 1.0.0 中未给出具体规则定义**。建议在 TD-001 或本 TD 附录中给出 canonical JSON 的排序规则和空白处理策略 |

### 2.4 §7-8 SQLite Schema 与 PRAGMA

#### 优点

- 使用 STRICT 表，类型安全。
- `data_priority` 和 `priority_rank` 双字段冗余存储，应用层双重校验。
- `delivery_class` 区分 REALTIME 和 BACKFILL，支持调度策略。
- 4 个索引覆盖调度、in-flight 回收、清理和序列查询。
- `telemetry_gap` 与 `telemetry_outbox` 在同一库，支持同事务写入。
- PRAGMA 配置完整：WAL + FULL + busy_timeout + 禁用 auto checkpoint。

#### 发现的问题

| 编号 | 严重度 | 问题 |
|---|---|---|
| T02-08 | **MEDIUM** | **`idx_outbox_dispatch` 索引包含 6 个列（status, delivery_class, priority_rank, next_retry_at_ms, created_at_ms, id）**。SQLite B-tree 索引在列数过多时效率下降。建议评估：`created_at_ms` 和 `id` 是否必要？`id` 作为 rowid 已隐含排序。若 `created_at_ms` 只用于 FIFO 排序，可用 `id` 替代（AUTOINCREMENT 保证单调） |
| T02-09 | **MEDIUM** | **`last_error_detail` 最大 512 字节——对某些异常堆栈可能不够**。例如 Java NullPointerException 的完整堆栈（含类名、行号）可能超过 512 字节。建议确认：512 字节是硬限制还是软限制？超限时的截断策略是什么（截断头部？截断尾部？附加 `[truncated]` 标记？） |
| T02-10 | LOW | **`telemetry_gap.dedup_key TEXT NOT NULL UNIQUE`——dedup_key 的生成规则未定义**。是 `tenant_id + device_identification + property_code + sequence_start + sequence_end`？还是包含时间范围？建议在 schema 注释或 TD 正文中定义 |

### 2.5 §9 本地提交与并发

#### 优点

- `appendBatch` 原子性：全部成功或全部回滚，不支持半批。
- 有界命令队列（4096 命令/16 MiB）+ 背压机制。
- writer 聚合策略：最多 500 envelope 或 10 ms。
- SAVEPOINT 隔离逻辑批次，单批 collision 不影响其他批次。
- ACK/claim/清理与控制命令共享 writer，调度保留槽。

#### 发现的问题

| 编号 | 严重度 | 问题 |
|---|---|---|
| T02-11 | **HIGH** | **Poller 等待本地提交的超时为 2 秒，但 writer 聚合等待 10 ms + 实际 SQLite 事务提交时间。若命令队列已满（4096），Poller 等待 2 秒后抛 `OutboxBackpressureException`——此时数据处于"不确定状态"**。TD 说"调用方必须保留原 messageId 重试"，但若数据已经入队但 Poller 未收到响应，重试会导致同一 envelope 被提交两次。虽然 `messageId` 唯一约束会返回 `DUPLICATE`，但 Poller 需要正确处理这种情况——是视为成功（数据已入库）还是视为失败（需要上层告警）？建议明确：背压超时后的重试语义和告警策略 |
| T02-12 | **MEDIUM** | **writer 聚合"最多 500 个 envelope 或等待 10 ms"——这两个参数的压测依据未说明**。500 个 envelope × 64 KiB 上限 = 32 MiB 单事务，可能超过 SQLite 默认 `limit`。10 ms 等待在高吞吐场景下可能产生过多小事务。建议标注为"首轮候选"并给出压测调整策略 |
| T02-13 | LOW | **"不同 `appendBatch` 可以合并为一个物理事务"——合并策略对上层可见吗？** 若 Poller A 和 ACK consumer 的命令被合并为同一事务，A 的 collision 回滚 SAVEPOINT 是否影响 ACK 命令？TD 说"单批 collision 不能回滚其他批次"，但实现上需要确保 SAVEPOINT 粒度正确 |

### 2.6 §10 状态机与 ACK

#### 优点

- 状态机完整覆盖所有 ACK 结果码。
- 迟到 ACK 处理策略精确：`PENDING/IN_FLIGHT` 可转 `ACKED`，`DEAD_LETTER` 只记录审计。
- DEAD_LETTER 重放后的 gap 处理：标记 `resolved_at_ms/resolution_code=REPLAY_ACCEPTED`，缺口事实保留。
- 同事务 gap + 死信更新，任一步失败整体回滚。

#### 发现的问题

| 编号 | 严重度 | 问题 |
|---|---|---|
| T02-14 | **HIGH** | **"未知 ACK 连续 12 次后同事务进入死信"——12 次的计数基准未定义**。是每个 messageId 独立计数？还是每个 collector 实例全局计数？若是前者，大量未知 messageId 各自累计到 12 次才进死信，可能产生大量死信。若是后者，单个频发的未知 ACK 可能把正常消息推入死信。建议明确计数维度并给出默认阈值推导依据 |
| T02-15 | **MEDIUM** | **DEAD_LETTER 保留期限未定义**。DEAD_LETTER "不自动清理"，但长期积压（数月）可能占用大量磁盘。建议定义：① DEAD_LETTER 磁盘占比告警阈值；② 超过 N 天的 DEAD_LETTER 触发人工处置提醒；③ 最大保留期限（如 90 天），超期后需审批才能继续保留 |
| T02-16 | MEDIUM | **"已知 retryable、网络失败和 ACK timeout 不设置总次数上限，持续退避直到恢复或容量保护介入"——在极端场景下（中心不可用数周），IN_FLIGHT 数据会持续增长直到触发容量保护**。虽然容量保护会按优先级淘汰，但这意味着 SAFETY/ALARM 数据可能因容量不足被保留而 NORMAL_TELEMETRY 被大量淘汰。建议确认：这种"因长期断网导致的优先级淘汰"是否符合产品预期？是否需要在 WARNING 阶段就限制 IN_FLIGHT 增长速率？ |
| T02-17 | LOW | **默认租约 5 分钟——与 ADR-002 `IN_FLIGHT` 超时一致，但 TD-003 的 ACK 等待超时尚未冻结**。若 TD-003 最终定义的 ACK 超时 > 5 分钟，租约必须相应上调。建议在冻结门禁中增加"TD-003 ACK 超时 ≤ 租约"的约束确认 |

### 2.7 §11-13 调度、容量与清理

#### 优点

- 实时与补传加权轮询（默认 4:1），补传等待超 5 分钟提升权重。
- 容量保护按优先级淘汰，SAFETY 不可自动淘汰。
- "预计可用时长"使用 EWMA 计算，样本不足报告 unknown。
- checkpoint 策略合理：PASSIVE 30 秒，WAL > 64 MiB 缩短到 10 秒。
- DEAD_LETTER 清理需审批，保留审计清单和哈希。

#### 发现的问题

| 编号 | 严重度 | 问题 |
|---|---|---|
| T02-18 | **MEDIUM** | **§12 容量保护中"PROTECTING：≥95% 或预计 30 分钟内耗尽"——EWMA 使用 15 分钟窗口，但预测 30 分钟**。窗口小于预测范围时，预测精度显著下降。突发流量（如大量设备同时上线）可能导致 EWMA 低估增长速率，实际耗尽时间远早于预测。建议：① 在高增长速率下使用更短的预测窗口（如 5 分钟）；或 ② 增加"瞬时增长速率"辅助指标作为安全网 |
| T02-19 | **MEDIUM** | **"每删除 10000 行且 backlog 低于 20% 时执行受限 incremental_vacuum"——"backlog 低于 20%"的计算基准是什么？** 是 20% 的容量预算（2 GiB × 20% = 400 MiB）？还是 20% 的当前使用量？若为前者，在低负载场景下可能长期不触发 vacuum；若为后者，在高负载场景下可能过于频繁。建议明确基准并标注为"首轮候选" |
| T02-20 | LOW | **导出功能未定义速率限制和并发控制**。大规模导出（如节点迁移时导出数百万条 DEAD_LETTER）可能阻塞 writer 或消耗大量磁盘 IO。建议明确导出是否使用只读连接、是否需要限速 |

### 2.8 §14-16 恢复、升级与迁移

## 六、综合改进建议

## 八、复核与最终处置（2026-07-31）

### 8.1 复核结论

评审对并发歧义、锁、死信治理、容量预测、迁移合并和健康聚合的风险判断总体合理，已在 [TD-002](../技术设计/电力运维云平台/TD-002-SQLite-Outbox与恢复迁移.md) 1.0.1 处置；1.0.2 仅与 TD-003 对齐 `schemaVersion/requestId/canonicalizationVersion`。但原报告基于不完整的 SPEC 读取形成了三项错误判断，不能据此放宽已冻结契约：

1. SPEC-004 1.4.0 实际已定义 `DQ-001～DQ-020`，因此 T02-04 所述“DQ-016～020 为 TD 新增需求”不成立，无需升级 SPEC。
2. SPEC-004 的 Envelope 示例和精度规则已定义 `valueEncoding=decimal-string`；T02-05 仅“枚举与缺值语义需细化”成立，“SPEC 没有字段”不成立。
3. SPEC-001 OBJ-012 与 SPEC-004 DQ-016 均要求电力遥测 `siteCode` 非空，未绑定站点的历史设备不得启用电力 collector。T02-06 建议的空值或 `unassigned` 会绕过站点权限，明确不采纳。

此外，T02-14 建议的 collector 全局未知 ACK 次数会产生跨消息污染：一个异常 messageId 可能推动其他正常消息进死信。最终采用每 messageId 独立计数，全局未知 ACK 比率只影响健康和告警。

### 8.3 状态决定

本轮已关闭原报告可由文档设计关闭的问题，但 TD-002 **仍保持 In Review，不直接冻结**，原因不是原报告所述的 DQ 漂移，而是以下证据门禁尚未完成：

- TD-003 尚未冻结 ACK timeout、Topic、批量和稳定错误码；
- dispatch 索引、队列/事务候选参数和未知 ACK 12 次阈值尚无合同测试与压测证据；
- SQLite JDBC/JDK/目标文件系统的 `WAL + FULL` 掉电、ENOSPC、恢复和 7 天稳定性证据尚未形成。

完成上述证据并复核 TD-002 第 21 节门禁后，方可转为 `Approved / Frozen`。
