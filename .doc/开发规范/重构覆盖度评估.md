> 评估日期：2026-08-12
> 评估对象（"方案"）：[ADR-016 EDGE 退役与 RUNTIME 边缘执行边界](../架构决策/电力运维云平台/ADR-016-EDGE退役与RUNTIME边缘执行边界.md) + 架构设计文档 V9.18.0

## 1. 评估背景

2026-08-11 完成了一次重大重构（删 EDGE / Ceph→NFS / 告警 HTTP→MQTT 总线），并由 ADR-016（Accepted）+ 架构文档 V9.18.0（10 份）正式记录。本评估回答：**这套方案是否完整覆盖了重构涉及的所有功能点和代码修改，有没有落在方案盲区的改动？**

评估方法：用两个独立视角交叉核对——
- **代码盘点**：逐个功能性 commit 读取 diff，按模块/配置/脚本/验收/迁移/MQTT 契约/前端 7 类提取功能点
- **方案核对**：读 ADR-016 决策 + 架构文档 V9.18.0 章节，盘点方案明确覆盖的功能点与覆盖边界
- **差异分析**：前者 − 后者 = gap

## 4. 5 个真正的 gap（方案应覆盖却未覆盖）

### G1 🔴 `ALGO_BUS_TRANSPORT` 三端降级行为不一致（契约级）

- **代码事实**：
  - VIDEO：`ALGO_BUS_TRANSPORT=http/off/0/false/no` 时回退废弃的 HTTP hook（`alert_hook_service` 标 `[DEPRECATED]` 仍可调）
  - RUNTIME：`ALGO_BUS_TRANSPORT=http` 时**直接丢弃告警**（`alert dropped (HTTP hook removed)`），无回退
  - iot-sink：无回退（`PostProcessServiceImpl.postAlertHook` 删 HTTP 回调，直接本地 `AlertService` 落库）
- **方案现状**：ADR-016 D5 只写「`algoBusTransport` 总开关」，**未声明同一开关在三端行为不同**。
- **风险**：运维误以为关闭 MQTT 各端行为一致；实际 RUNTIME 静默丢告警。
- **严重度**：HIGH（契约级不一致）。
- **处置**：ADR-016 1.1.0 显式声明三端降级行为；与 M-02「独立告警 Inbox」协同。

### G2 🟠 Hook 不对称：`on_publish` 留 VIDEO，仅 DVR 迁 iot-sink

- **代码事实**：SRS/ZLM Hook 重定向时，`on_dvr`/`on_record_mp4` 迁到 `/sink/media/hook/...`，但 `on_publish`/`on_unpublish` **仍走 VIDEO**（`c487ff1e`）。
- **方案现状**：文档说「录像委托 sink」，未说明这个 Hook 不对称。
- **处置**：架构文档（中间件部署 3.8 SRS / 3.9 ZLM 或 Java 7.3）补一句说明。

### G3 🟠 MQTT→Kafka 桥接未在 ADR 提及

- **代码事实**：`IotAlgoBusMqttHandler.maybeForwardNotification` 命中通知配置后转发 Kafka topic `iot-alert-notification-send`（key=deviceId），这是 MQTT 总线→下游通知分发的桥接点。
- **方案现状**：ADR-016 未提；Java 微服务文档 7.3 提了（部分覆盖）。
- **处置**：ADR-016 D4 或架构文档显式补「告警经 MQTT 落库后，命中通知配置则转发 Kafka 触发下游通知」。

### G4 🟠 iot-sink → video 库反向耦合

- **代码事实**：`IotAlgoBusMqttHandler.enrichNotificationFromVideoDb` 切 `video` 数据源，查 `algorithm_task JOIN algorithm_task_device` 补 `channels`/`notifyUsers`/`notifyMethods`。依赖动态数据源 `video` 配置存在。
- **方案现状**：ADR-016 D4 只说「来源记录仅作证据，不复制状态」，**未提 sink 反向依赖 video 库读通知配置**这一耦合方向。
- **风险**：动态数据源 `video` 未配置时 enrichment 静默失败（告警仍落库但不通知）。
- **处置**：ADR-016 或告警 TD 显式说明 sink→video 库的只读耦合边界与失败语义。

### G5 🟡 Ceph→NFS 命名兼容无退出路径

- **代码事实**：`NodeCephTopologyRespVO`、`getCephTopology()`、前端 `CephTopologyPanel` 保留 `Ceph` 前缀；`TopologyNodeVO` 含 5 个 `@Deprecated` 旧 Ceph 字段兼容旧前端（`cephMountReady` 等）。
- **方案现状**：代码做了兼容，但**何时迁移到 `Nfs*` 命名、`@Deprecated` 字段何时下线、前端组件是否重命名**——方案未定义。
- **处置**：补充命名迁移计划（兼容窗口 + 下线门禁），或在架构文档注明「命名沿用 Ceph，语义为 NFS」。
