## 2. 总体评价

**ADR-012 决策质量：高。** 这是当前电力运维文档链中**证据最扎实**的架构决策之一：

1. **背景有双重证据**——目标库画像证明 `product_properties.service_id` 不存在；仓库静态调用清单证明 Mapper/VO/Feign/缓存仍依赖旧"服务属性"模型；
2. **决策分三层展开**——§2.1 运行事实 / §2.2 Java 与 API 边界 / §2.3 删除与租户边界，层次分明；
3. **被否决方案覆盖完整**——A 补 `service_id`、B 立即统一 TSL member 表、C 各自选来源、D 无兼容删除，覆盖主要替代路径；
4. **兼容迁移路径合理**——扩展—迁移—收缩 + 至少 6 个月窗口 + legacy adapter + 调用量监控；
5. **状态语义清晰**——§5 明确 "`Accepted` 不表示代码已修复"，把"决策接受"与"实现门禁"拆分，避免了原 Proposed 版本的循环门禁；
6. **与下游技术设计协同**——TD-005-运行模型冻结 Mapper/DO/VO、唯一约束、租户 CRUD 和删除链合同，承接 ADR-012 全部事实归属。

**主要风险集中在**：

- `service_id` 影子列在兼容窗口内仍需一致性校验，收缩时间窗未明确；
- 旧调用者清单（§2.2 第 5、6 条）需代码 owner 复核，清单出处未附；
- `product_event_response`、`product_script`、`device_service_invoke_response`、`ota_packages` 等扩展依赖虽已加入删除图，但扩展画像尚未完成；
- 非空旧格式 round-trip golden 尚未建立；
- 生产环境按画像 Schema 重跑的契约尚未在生产存量环境执行。

上述风险**全部由 TD-005 实现/发布门禁承接**，不影响 ADR-012 本身的事实归属决策。

## 4. 决策质量评估

### 4.1 背景证据

| 证据来源 | 内容 | 是否充分 |
|---|---|---|
| 目标库画像 | `product_properties` 无 `service_id` 列；21 行样本 → 修复后 17 行 | ✅ |
| 孤儿清理 | 4 条过期演示种子按授权精确删除 + 回滚脚本 | ✅ |
| Mapper/VO 调用链清单 | `ProductPropertiesMapper` 漂移、`findAllByServiceId` 注释但 Java 可调用、`ProductPropertyParamVO/ResultVO` 暴露 `serviceId`、`ProductServiceImpl` / `ProductTemplateServiceImpl` / `RemoteProductPropertiesService` / `ProductModelCacheService` 依赖旧模型 | ✅ |
| 替代路径证据 | `ProductServiceThingModelHelper` 已从 command request/response 读取服务入参/出参 | ✅ |
| 循环门禁拆分 | 原 "代码修复 → ADR 接受 → 才允许代码修复" 拆为 "ADR 接受冻结事实归属 + TD-005 阻断实现门禁" | ✅ |

### 4.2 决策清晰度

- §2.1 **运行事实表**：6 行业务成员 × 唯一运行事实 × 关联事实 × 禁止，四列结构清晰；
- §2.2 **Java 与 API 边界**：8 条规则，涵盖"不补列 / DO/VO 分层 / 根属性 DTO 不暴露 serviceId / legacy 废弃期限 / 删除旧调用 / adapter 投影 / 模板绑定关联 / 档位复用"；
- §2.3 **删除与租户边界**：5 条规则，涵盖"单条委托批量 / 下游保护 / 显式删除顺序 / 双层保护 / 跨租户不存在"；
- **`commands_id` 为权威关联**：§2.1 末段明确冻结，`service_id` 为兼容影子列；
- **"扩展—迁移—收缩"模式**：§2.1 末段 / §4 第 6 步；
- **回滚不恢复 `service_id`**：§4 末段，与 ADR-009 / TD-005 §14 / TD-005-运行模型 §11 一致。

### 4.3 被否决方案覆盖

| 方案 | 否决理由 | 评估 |
|---|---|---|
| A 补回 `service_id` | 与 command request/response 形成双写/双读/差异歧义 | ✅ 合理 |
| B M1 立即统一 TSL member 表 | 回归面超过当前里程碑 | ✅ 合理；需独立 ADR |
| C 各自选来源 | 无法定义发布 hash/绑定快照/差异/回滚的唯一事实 | ✅ 合理 |
| D 无兼容删除 | 仓库内仍有缓存/聚合调用者，违反宪法兼容优先 | ✅ 合理 |

### 4.4 兼容迁移路径

- §4 第 1–6 步"扩展—迁移—收缩"完整；
- 第 4 步 legacy adapter 投影 + 调用量监控；
- 第 5 步合同测试先行；
- 第 6 步"至少 6 个月窗口" + "调用量连续一个发布周期为零 + 迁移通知 + 回滚演练"三条件方可下线；
- 回滚只切 adapter，不恢复 `service_id`，不回填双事实。

## 7. 问题清单

### HIGH

无。

### MEDIUM

无。

### LOW

**L-01 · "扩展—迁移—收缩"的"后续主版本"未指明时间窗**

位置：§2.1 "该影子列按'扩展—迁移—收缩'在后续主版本移除"。
问题："后续主版本"未指明是 M2 还是更晚，收缩时间窗可能被无限推延。
建议：补"（候选在 M2 末或 M3 初，需独立 ADR 评估）"，避免兼容窗口变成永久遗留。

**L-02 · "发布周期"未定义**

位置：§4 第 6 步 "调用量连续一个发布周期为零"。
问题："发布周期"未在文档中定义。
建议：补"发布周期 = 平台功能计划规定的正式发版间隔（M1 阶段为每次里程碑 GA）"或"自然月"。

**L-03 · "Accepted 即日起禁止新增 `service_id`"语义未显式说明**

位置：§2.2 第 1 条 "不向 `product_properties` 新增 `service_id`"。
问题：与 §5 "`Accepted` 不表示代码已修复"的关系未显式说明；读者可能误以为"现有残留允许新增"。
建议：补一句："`Accepted` 自即日起禁止任何新增 `service_id` 的代码或 DDL 改动；现有残留由 TD-005 在兼容窗口内清理"。

**L-04 · 调用者清单未附位置**

位置：§5 第 2 项 "仓库调用点、Mapper、VO、缓存和删除链清单已形成"。
问题：未附清单的具体位置。
建议：补清单出处：画像报告 §4 + TD-005-运行模型 §2/§5.2 + TD-005 评审报告 §19；或在本 ADR 末尾附清单摘要。

**L-05 · §2.1 表格"关联事实"列符号风格**

位置：§2.1 "关联事实"列使用 `→`（如 `commands_id → product_commands.id`）。
问题：与其他处下划线命名风格略异。
建议：风格统一即可（如改为 `commands_id → product_commands.id` 维持，或改为 `commands_id 关联 product_commands.id`）。不阻塞。

## 11. 与 ADR 评审报告 §11 的关系

本评审报告是 ADR-012 的**独立复核**，与 ADR 评审报告 §11（追加评审与最终处置）并行存在：

- **ADR 评审报告 §11**：做出 `Accepted` 状态决定，处置 9 项发现（A12-01～A12-09），是状态翻转的依据；
- **本评审报告**：在状态翻转后，独立核对 ADR-012 当前版本与上游 SPEC / 下游 TD-005 / ADR 评审报告 §11 的对齐，识别 5 项 LOW 微调，确认 `Accepted` 状态可维持。

两份报告冲突时，以 ADR 评审报告 §11 的状态决定为准。本评审报告的 LOW 微调建议可在下一次文档维护批次处理，不触发 ADR 状态翻转。

## 12. 结论

ADR-012 当前版本（2026-08-05）与项目宪法、SPEC-001/SPEC-002、TD-005 主文档、TD-005-运行模型、TD-005 评审报告 §19、ADR 评审报告 §11 的协同**全部一致**。

**综合决策：确认 Accepted。**

- 0 HIGH / 0 MEDIUM / 5 LOW；
- 5 LOW 均为文档层面的微调，可在下一次文档维护批次处理；

- 影子列 `service_id` 的收缩需后续独立 ADR 评估（候选 M2 末或 M3 初）。

### 13.2 配套运行模型新增评审的事实纠正

配套运行模型 §13 新增 R1～R10 评审后，需先纠正三个口径问题：

1. 画像 JSON 的 `product_properties.columnCount` 明确为 **20**；“21”是修复前数据行数，不是列数，R1 建议的“18 列”不采纳；
2. 当前公共 `ProductProperties` 已有 `productIdentification/templateIdentification`，缺少的是 `tenantId`，但现有 `BaseResultMap` 对三者均未形成完整显式映射；新 `ProductPropertyDO` 仍必须声明并映射三字段；
3. R6 列出的不是“8 张表”，而是 **8 张核心运行表 + 4 张受保护依赖表，共 12 张**。

R2～R10 的合理部分已写入运行模型 0.1.1：`product_script` 以 tenant + 产品 ID + 产品编码交集删除，XOR 使用 PostgreSQL `num_nonnulls`，建立双 partial unique index，扩展 12 表画像，补历史调用/OTA 保护、双向回滚测试、golden manifest/hash、TEN/DEL 启用证据及 TenantIgnore/SYSTEM owner scope 门禁。

### 13.3 门禁影响

- ADR-012 的事实归属决策保持 PASS；
- `service_id` 影子列一致性仍是实现/兼容门禁，不能因 ADR Accepted 自动关闭；
- Mapper/DO/VO、删除链、数据库约束、租户合同只能由实际代码、DDL、自动测试和目标库结果关闭，不能因技术设计“可采纳”而关闭；

最终结论：**需要修改，合理意见已落地；L-01 部分采纳、L-05 不修改，运行模型 R1 的 18 列判断驳回并纠正为 20 列。**
