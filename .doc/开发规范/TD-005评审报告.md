## 2. 总体评价

**架构设计完备度：高。** TD-005 是当前电力运维文档链中工程化程度最高的一份。从诚实的代码差距核对（§3）、到 canonical/哈希/SemVer 的形式化定义（§5–§7）、到 B/V/N 三方差异的冲突决策（§9）、到产品绑定与回滚的事务性设计（§13–§14）、到完整错误数组（§12）、再到 SPEC-002 追踪矩阵（§21），整体形成"模板 → 版本 → 绑定 → 运行时"四层分离的清晰模型，避免了"把编辑态当成发布事实"的常见陷阱。

**主要亮点**：

1. **差距分析诚实且已用代码核对验证**——§3 的 8 项声明全部经仓库实际代码核对：`ThingModelController.release` 占位成功、`ProductTemplateController` 权限注解被注释、`template_identification` 被主动清空、`ProductServiceThingModelHelper` 的删除重建参数策略、`importProductJson` 仅支持旧格式——五项 **VERIFIED**，三项 **PARTIAL**（Mapper XML 存在 `service_id`、存在租户拦截器、`phsyicalModal.ts` 实际文件名 `physicalModel.ts`），无 **NOT VERIFIED**。
2. **四层事实分离**——模板身份、版本内容、产品绑定、运行时表四层独立，互不可见替代；回滚创建新修订而不修改历史、不删除新版本期间遥测。
3. **canonical/哈希形式化**——`jcs-rfc8785-v1`、`sha256:` 前缀、输入字节明确、哈希不依赖 PostgreSQL `jsonb` 重序列化，直接规避了 TD-001 T01-02 的同类问题。
4. **B/V/N 三方合并算法清晰**——六种冲突条件枚举完整、决策枚举冻结、输入按哈希寻址保证可复现。
5. **稳定错误码 + 完整错误数组**——§12 的 17 个错误码覆盖主要失败路径，一次返回全部可判定错误的契约与 SPEC-002 TM-014 完全一致。
6. **SPEC-002 追踪矩阵完备**——TM-001～TM-014 每条需求均有设计落点和主要证据列。
7. **档位治理严谨**——mini 通过 capability 禁用无独立实现、standard/full 单产物只提配额，符合 ADR-011 和宪法 §2.3。
8. **评审冻结门禁 10 项可操作**——§23 把数据库画像、Schema fixture、JCS 跨语言 golden、行业专家复核、manifest commit 冻结等明确列为门禁。

**主要风险集中在**：
(1) `Idempotency-Key` 契约未定义，与 TD-004 已收敛的解法不一致；
(2) capability 命名 `power.model-template` 与 ADR-011 框架表未对齐，前端/旧端点 capability 门禁缺失；
(3) 导入文件攻击面描述停留在策略层，未冻结解析库与禁用项；
(4) SPEC-002 中"线电压后缀 `-ab/-bc/-ca`"的引用与实际 SPEC-002 文本不符；
(5) 互感器变比字段只有"独立存在"要求，缺乏数据类型、精度与归一化语义。

**与 SPEC-001/SPEC-002/ADR-009/ADR-011 的一致性**：templateCode 正则、SemVer、生命周期、租户派生、required 校验、高风险服务、canonical 哈希、stable error array、SPEC-002 10 类设备枚举全部对齐；但 capability 命名、线电压后缀引用、CT/PT 变比语义、前端门禁需要补齐。

## 7. 问题清单

### HIGH（必须修复才能冻结）

**H-01 · `Idempotency-Key` 契约缺失——与 TD-004 已收敛解法不一致**

位置：§11 "写 API 接受 Idempotency-Key"、§17 "导入和发布使用租户内 Idempotency-Key + requestHash"。  
问题：(1) 幂等记录保存在哪张表、哪些列；(2) TTL 与清理策略；(3) 跨副本一致性（多 iot-device 实例同时接收相同 key）；(4) 相同 key 不同 requestHash 是返回 409 还是覆盖。  
对比：TD-004 评审 H-02 已识别同类问题并在 TD-004 1.0.1 中以 `power_idempotency_record` 表冻结解法；TD-005 不应重新发明。  
风险：实现分叉、清理不及时导致表膨胀、保留期过短破坏业务预期、跨副本双写不一致。  
**建议**：复用 TD-004 的 `power_idempotency_record` 模式——表 Schema、主体作用域、HMAC 派生 request hash、24 小时默认保留、跨副本唯一约束、清理扫描任务；在 §11/§17 引用 TD-004 契约，不在本 TD 重复设计。

**H-02 · Capability key `power.model-template` 未在 ADR-011 框架表登记**

位置：§16 "capability key 固定 `power.model-template`"。  
问题：ADR-011 §4 编码框架表列出 device / alarm / control / video / scada / maintenance / energy 七个域，device 域下示例为 `power.device.model`，未出现 `power.model-template`。语义上，模板管理属于 `power.device.model` 的子能力还是独立能力未澄清。  
风险：(1) CI 的 capability strict-superset 扫描无法识别新 key；(2) 与已有 `power.device.model` 的语义重叠会导致 manifest 消费者困惑；(3) ADR-011 §4 "新增编码必须同时更新 schema、两档 manifest、依赖、门禁和测试"未被触发。  
**建议**：二选一——(A) 重命名为 `power.device.model`，并在 manifest quota 中定义 `maxTemplates / maxImportLines / maxConcurrentPublish`；(B) 保留 `power.model-template`，但同步更新 ADR-011 §4 框架表、`capability.schema.json`、`electric-standard.json`、`electric-full.json` 并在 CI 规则中登记。推荐方案 A，避免 capability 膨胀。

**H-03 · 前端 `physicalModel.ts` 与 `ThingModelController.release` 未 capability 门禁**

位置：§16 "mini 返回统一 CAPABILITY_NOT_SUPPORTED 且不显示入口、不运行 seed/import/publish 任务"。  
问题：(1) 前端 `physicalModel.ts` 的 `releaseThingModel()` 调用 `PUT /thingModel/release` 占位接口，无 capability 判断；(2) `ThingModelController.release` 端点本身也未加 capability 注解；(3) mini 启用后，用户仍可在前端点击"发布"并获得假成功；(4) 已标记电力域的产品调用旧 release 接口时，§19.1 只说"必须转新发布流程或返回稳定迁移错误"，但代码路径未冻结。  
风险：mini 用户看到假"发布成功"；电力域产品继续绕过版本化发布。  
**建议**：(1) `ThingModelController.release` 增加 `@PreAuthorize("@capabilityService.isEnabled('power.model-template')")`，且对电力域产品返回 `MODEL_LEGACY_RELEASE_DENIED`；(2) 前端 `physicalModel.ts` 在入口、按钮和路由层按 `capabilityService.isEnabled` 三态控制（隐藏/禁用/可见）；(3) §16 权限点表增加"旧 release 端点对电力域产品必须拒绝"的架构测试。

**H-04 · 导入文件攻击面描述停留在策略层，未冻结解析库与禁用项**

位置：§11.3、§16 "导入文件限制 MIME、扩展名、大小、压缩展开比、Sheet/行/列和 JSON 深度"。  
问题：(1) 未指定 Excel 解析库（POI / POI-OOXML / EasyExcel），各自安全配置差异大；(2) 未声明 `Workbook.setForceFormulaRecalculation(false)`、禁用 OLE 嵌入、禁用 PivotTable、禁用外部链接（`externalLink.xml`）；(3) JSON 方面未声明禁用 `$ref` / 自定义 resolver、禁用 DTD/XXE；(4) MinIO 上传 key 未声明sanitize（用户文件名可能含 `../`）；(5) 缺负向 fixture（含宏、含 OLE、含 pivot、含 external link 的恶意 Excel）。  
风险：Excel 公式注入 / OLE XXE / 外部链接 SSRF / 路径穿越写 MinIO。  
**建议**：在 §11.3 或 §16 补：(1) 冻结库（建议 EasyExcel 4.x 或 POI-OOXML 5.x + 显式安全配置）；(2) 列出禁用项清单；(3) MinIO key 使用 `secureRandomUUID + 原扩展名`；(4) §20.1 fixture 增加恶意 Excel/JSON 样本。

**H-05 · 互感器变比字段缺乏数据类型、精度与归一化语义**

位置：§5、§20.1 "CT/PT 独立类型与变比必选字段"。  
问题：(1) SPEC-002 §4 只要求"变比字段独立存在"，未定义其数据类型、精度、单位、归一化语义；(2) TD-005 §5 也未补充；(3) 标准点位字典 `standard-point-dictionary-v1.json` 有 `transformation-ratio` 但未给数据类型（INT/DOUBLE/DECIMAL？）和 precision；(4) 归一化规则缺失：一次值 ÷ 二次值 = 倍率，倍率与遥测值的乘积如何保存（十进制字符串？精度？舍入模式？）未定义。  
风险：(1) 10 类模板中 CT/PT 是 M1 SHOULD 交付，若语义不完整会导致互感器产品与电表产品的倍率计算分叉；(2) 违反 TM-012 十进制表达规则。  
**建议**：在 §5 补一小节"互感器变比语义"：(1) 数据类型 `DECIMAL`（STRING 表达）、precision=6、roundingMode=HALF_UP；(2) 归一化语义：遥测值 × 变比 = 归一化值；(3) Schema 中通过点字典而非根 Schema 约束（保持 Schema 通用）；(4) 作为行业专家复核（§23 门禁 4）的重点项。

### MEDIUM（应修复；不阻塞冻结但需跟踪）

**M-01 · SPEC-002 引用 `-ab/-bc/-ca` 线电压后缀无 SPEC 依据**

位置：§5.1 "线电压使用 `-ab/-bc/-ca`"。  
问题：SPEC-002 §5 只定义了三相后缀 `-a/-b/-c`；线电压被归入"无相别语义，按标准字典编码，不强行添加三相后缀"。TD-005 把 `-ab/-bc/-ca` 写进设计，但 SPEC-002 未显式定义这些后缀。  
**建议**：(1) 在资产点位字典中显式枚举线电压 code（如 `voltage-ab`、`voltage-bc`、`voltage-ca`）并由行业专家复核；(2) 或在 §5.1 改为"线电压 code 遵循标准点位字典，不强行添加三相后缀"。

**M-02 · `power_model_member_index` 缺索引建议**

位置：§10.3。  
问题：只给出列和唯一约束，未给出支持差异查询、影响查询、required 校验的辅助索引。  
**建议**：补索引基线：(1) `(template_version_id, member_type, required) WHERE required=true`；(2) `(template_version_id, member_type, semantic_type)`；(3) `(member_fingerprint)` 用于 B/V/N diff。

**M-03 · `power_model_release_outbox.eventId` 生成规则未冻结**

位置：§10.5。  
问题：`event_id` 是幂等消费者去重键，但未说明生成规则（randomUUID? HMAC? 业务键组合?）。  
**建议**：固定 `event_id = randomUUID()`，消费者按 `(event_id)` 唯一约束去重；禁止使用可预测的 `templateId + timestamp`。

**M-04 · draft 过期/TTL 语义缺失**

位置：§7、§10.2。  
问题：`DRAFT` 生命周期仅用 `draftRevision` 做乐观锁，未定义：(1) 草稿最大存活时长（30 天？90 天？）；(2) 过期草稿是否自动关闭；(3) 过期后是否释放 templateCode 占位；(4) 长时间占位草稿会阻止模板退役流程。  
**建议**：补 §7.1 草稿生命周期段：默认 90 天无活动则 `DRAFT → ABANDONED`；ABANDONED 不影响身份但释放校验占位；审计保留。

**M-05 · 影响快照输入哈希失效语义**

位置：§14 "影响快照按 sourceHash + targetHash + currentBindingHash 寻址，任一输入变化后旧计划失效"。  
问题：(1) "失效"后如何提示用户？(2) 失效的 plan 是否可读、可重新激活？(3) 失效后是否允许在旧 plan 上 continue-confirm？  
**建议**：补失效处理：(1) 失效状态 `INVALIDATED`，保留历史记录；(2) 用户必须重新调 preview 生成新 plan；(3) 错误码 `MODEL_UPGRADE_PLAN_INVALIDATED`。

**M-06 · standard/full 配额候选值未列出维度**

位置：§16、§18。  
问题：仅说"full 只能提高模板数、导入行数、并发任务等配额"，未列出具体 quota 维度。与 H-02 关联。  
**建议**：冻结 quota key 清单（即使值待压测）：`maxTemplates`、`maxImportLines`、`maxConcurrentImportJobs`、`maxConcurrentPublish`、`maxRebasesPerDay`、`maxVersionsPerTemplate`。

**M-07 · 三方冲突决策审计记录结构未完整**

位置：§9。  
问题：仅说"保存决策人、时间、理由和决策前后的值哈希"。冲突决策属于关键审计事实，需要完整快照。  
**建议**：补 `power_model_upgrade_conflict` 列：`decision_before_value_json`（原文）、`decision_after_value_json`、`decision_reason`、`decided_by`、`decided_at`；决策前/后值同样纳入哈希链。

**M-08 · PostgreSQL advisory lock 超时与重试未定义**

位置：§17 "发布按 templateId PostgreSQL advisory transaction lock 串行化"。  
问题：未定义锁超时（`lock_timeout`）、持锁最长时长、超时返回的错误码、是否可重试。  
**建议**：补：(1) `SET lock_timeout = '15s'`；(2) 超时返回 `MODEL_TEMPLATE_PUBLISH_LOCK_TIMEOUT`；(3) 客户端可重试，但须使用新的 Idempotency-Key 或相同 key + 相同 requestHash。

**M-09 · `binding_snapshot_canonical` 体积与查询成本未评估**

位置：§10.4。  
问题：每个产品每次绑定/升级/回滚都存一份完整 canonical snapshot；大型产品（500+ 属性、50+ 事件、50+ 服务）单行可能 100KB+；历史 N 次绑定累计 MB 级。  
**建议**：补：(1) snapshot 列 `TEXT` 并考虑 TOAST 压缩；(2) 只存 canonical 不存 pretty-printed；(3) 查询 UI 默认只返回最近 N 个修订；(4) 归档策略：绑定 SUPERSEDED 超过 N 天可将 snapshot 迁移到冷存储。

**M-10 · `If-Match` 与 `Idempotency-Key` 的分工边界**

位置：§11。  
问题：修改草稿/计划用 `If-Match`，写 API 用 `Idempotency-Key`，但两者同时出现时的优先级、冲突返回码未说明。  
**建议**：在 §11 顶部补"Header 优先级"：(1) `Idempotency-Key` 校验先于 `If-Match`；(2) 幂等命中时 `If-Match` 不再校验；(3) 错误码顺序 `IDEMPOTENCY_CONFLICT` → `PRECONDITION_FAILED`。

## 12. 复核与最终处置（2026-08-04）

### 12.1 复核结论

对评审意见再次交叉核对 SPEC-002、ADR-011、TD-004、仓库源码和 Maven 依赖后，确认评审方向总体合理，但存在三项事实/方案偏差：

1. 仓库实际文件是 `WEB/src/api/device/phsyicalModal.ts`，原 TD-005 写法正确；本报告第 5 节和 L-01 所称 `physicalModel.ts` 不存在。实际旧发布调用与控制器映射为 `PUT /thingModel/{productIdentification}` 及控制器声明的空路径变体，不是 `/thingModel/release`。

### 13.3 残余问题

处置落地后，TD-005 1.0.2 在设计层面已无 HIGH 缺口；以下为残余细节，不阻塞 §12 处置结论，但建议在实现阶段或下一次文档修订中处理。

**R-01 · 归一化最终输出精度未明确（与点位字典 `precision=6` 的关系）**

位置：TD-005 §5.3 + 点位字典 1.0.1 `normalizationRules`。  
现象：`arithmetic=BASE10_ARBITRARY_PRECISION` + `precision=6` + `roundingMode=HALF_UP`。`precision=6` 描述的是 `transformation-ratio` 字段本身的精度；但归一化输出 `rawSecondaryValue × ratio` 的最终精度未声明。若 `rawSecondaryValue`（precision=3）× `ratio`（precision=6）按数学乘法结果精度为 9，直接按 6 位 HALF_UP 舍入会损失信息。  
建议：在 §5.3 或点位字典补充——中间计算保持任意精度（BASE10_ARBITRARY_PRECISION），输出到 TD-003 envelope 时由属性自身 `precision` 决定舍入（本例 precision=3 → 输出 3 位 HALF_UP），`normalizationRules.precision=6` 只约束 ratio 字段存储。

**R-02 · `:action` 子资源路由冒号兼容性**

位置：§11.1/§11.2/§11.4。  
现象：`:validate`、`:publish`、`:deprecate`、`:retire`、`:derive`、`:preview`、`:apply`、`:confirm`、`:rollback`、`:materialize`、`:rebase-preview` 共 11 个 action。冒号在 RFC 3986 path 中允许，但部分 HTTP 客户端、日志或 Spring 注解映射需要 URL 编码（`%3A`）。  
建议：在 §11 顶部补"路由约定"段：Spring 控制器统一使用 `@PostMapping("{draftId}/validate")` 或 `@PostMapping("{draftId}:validate")` 其中一种风格，并在 OpenAPI 中显式标注；如发现框架或网关对冒号敏感，备选 `/{draftId}/actions/validate` 风格，不得在仓库内混用。

**R-03 · HTTP 409 用于 `MODEL_LEGACY_RELEASE_DENIED` 的语义**

位置：§16 第 2 点。  
现象：电力域产品调用旧 `PUT /thingModel/{productIdentification}` 返回 409。RFC 9110 §15.5.10 定义 409 Conflict 为"请求与资源当前状态冲突"，迁移拒绝更接近 410 Gone 或 403 Forbidden + `migrationTarget` 链接。  
建议：考虑使用 410 `MODEL_LEGACY_RELEASE_DENIED`（资源已迁走）或维持 409 但在 §16 增加说明"本 409 表达请求与平台迁移策略冲突，而非传统资源冲突"。不阻塞冻结。

**R-04 · 评审报告与 TD-005 的版本叙事间隙**

位置：评审报告 §12.1 "本轮将 TD-005 更新为 1.0.1 / In Review"；TD-005 文档头 `版本：1.0.2`。  
现象：中间未见 1.0.1 的独立变更记录。  
建议：在评审报告 §12.3 或 TD-005 变更日志段补一行说明："1.0.1 完成设计整改落地；1.0.2 追加 §24 自动证据状态"。避免读者对版本号跳跃产生疑问。

**R-05 · 点位字典 `propertyName` 中文编码**

位置：`standard-point-dictionary-v1.json` 中 CT/PT 属性 `propertyName`。  
现象：在部分 Windows 终端以 GBK 回显时显示为乱码（如 `欢ǖ纭`），但文件本身为合法 UTF-8，Python 以 `encoding='utf-8'` 读取正确。  
建议：在验证脚本和 `verification/README.md` 中显式注明"所有资产文件均为 UTF-8 无 BOM，消费方必须以 UTF-8 打开"；避免因终端编码差异引起误读。

专项复核另发现：原修复脚本只比较部分文本字段，但回滚脚本保存完整行。如果删除前其他字段已变化，旧回滚快照可能覆盖新值。已新增四行 `row_to_json` 完整快照 MD5 断言；该 MD5 只作为确定性等值检查，不作为密码学安全证明。

### 17.3 验证与门禁

- 只读预检已通过目标行、作用域、父对象、下游引用、12 个动态标识列和 4 个完整快照检查；

- 方案状态转为 `Reviewed / Awaiting Execution Approval`，只代表设计可执行，不代表 TD-005 门禁 1 已 PASS。

最终结论：**需要修改，合理意见已落地；O5 驳回，O1/O2/O3 按实际 Schema 和 COPY 基线纠正。** 获批并真实执行后只能关闭“4 条孤儿属性”子项，ADR-012、Mapper/实体/VO、唯一约束、租户 CRUD 和删除链合同仍保持阻断。

## 19. ADR-012 与运行模型契约复核（2026-08-05）

### 19.1 评估

根据修复后画像、仓库静态调用清单和 [ADR 评审报告 §11](./ADR评审报告.md)，ADR-012 的核心方向合理：根属性与服务参数必须分属 `product_properties` 和 command request/response 链。为属性表补回 `service_id` 会制造双事实，不能作为快速修复。

原 ADR 把决策接受与代码实现证据绑定，造成循环门禁。现已拆分：ADR-012 转 `Accepted`，只冻结事实归属；Mapper/DO/VO、DDL、租户、删除和兼容合同仍由 TD-005 阻断。

### 19.2 新增设计处置

新增 [TD-005 运行模型兼容与删除链技术设计 0.1.0](../技术设计/电力运维云平台/TD-005-运行模型兼容与删除链技术设计.md)，处置以下问题：

- `commands_id` 冻结为服务参数权威关联，request/response 的 `service_id` 仅为服务端派生兼容影子；
- 数据库 DO 与 Request/Response VO 分离，legacy Property DTO 只用于兼容 adapter；
- 列出 Product/Template 聚合、缓存、Feign 和 `ProductServiceThingModelHelper` 的迁移责任；
- unique、XOR scope、tenant composite FK 与 `ON DELETE RESTRICT` 的上线顺序；
- 产品单条删除委托同一批量编排器，禁止把 product code 当 template code；
- 删除依赖扩展到 `product_event_response`、`product_script`、device、历史调用、OTA 和 ACTIVE binding；
- 建立 TEN-001～008、DEL-001～010 合同和逐步骤故障注入。

### 19.3 现场证据补充

目标实例只读核对显示：`product_event_response=0`、`product_script=0`、`product_template=0`、`device=4`；4 个产品均各关联 1 个设备。因此现有产品必须受删除保护，删除成功测试只能创建独立无下游 fixture，不得拿现有演示或历史产品做真实删除演练。

### 19.4 门禁结论

| 子项 | 状态 |
|---|---|
| ADR-012 事实归属 | PASS / Accepted |
| 4 条孤儿属性处置 | PASS |
| 运行模型兼容与删除链设计 | REVIEW CANDIDATE |

| Mapper/DO/VO 生产修复 | OPEN |

最终结论：**需要继续修改，暂不冻结 TD-005。** 下一步先扩展目标画像并建立非空旧格式 round-trip fixture/golden，再按已接受的 ADR-012 实现 Mapper/DO/VO 与数据库迁移。§18 中“ADR-012 仍为 Proposed”的历史结论由本节取代；其他未关闭门禁保持不变。
