## 二、总体评价

PRD 系列整体质量较高，与《平台功能计划》的功能域覆盖一致，各 PRD 均显式声明了部署档位（mini 排除、standard/full 差异），引用了 `TelemetryStore`、`ADR-010`、`ADR-011` 等此前评审建议产出的 ADR，说明上一轮文档评审的整改建议已被吸收。

主要短板集中在三个方面：

1. **PRD-00 总纲的约束力不足**——原评审曾判断基线版本号错误，复核确认该项为误报；量化指标、共享业务口径和 Spec 下游门禁确需补强。
2. **跨 PRD 数据契约未统一**——7 个 PRD 各自定义验收标准，但共享概念（质量码、告警等级、工单状态、冻结值版本、计量点倍率）的口径未在总纲层统一锁定，存在 Spec 阶段分化的风险。
3. **非功能需求缺少量化基准**——多数 PRD 只给出定性描述（"支持"、"可配置"），缺少性能、规模、保留期、并发等量化约束，Spec 阶段可能产生分歧。

## 三、各 PRD 评审

### 3.1 PRD-00 产品总纲

#### 优点

- 用户角色定义完整（8 个角色覆盖企业负责人到平台管理员），诉求清晰。
- 核心业务旅程（无人值守、计划运维、能源管理）覆盖了三大主线。
- 非目标定义明确，避免了范围蔓延（不替代继电保护、不做电力交易等）。
- 部署档位表（§9）与《平台功能计划》§1.2 矩阵一致。
- 总体验收（§12）可操作，包含了 `Capabilities(standard) ⊂ Capabilities(full)` 的自动化验证要求。

#### 发现的问题

| 编号 | 严重度 | 位置 | 问题 |
|---|---|---|---|
| P0-01 | **撤销** | §头部 | **复核后确认为误报**。两份上游基线当前均为 1.4.0，PRD 引用正确；本项不构成整改要求 |
| P0-02 | **HIGH** | §6 | **产品指标缺少量化目标值**。"关键测点月度有效数据率不低于 99%"和"P95 不超过 5 秒"是好的开始，但通知送达率、巡检完成率、抄表成功率、工单 SLA 达标率等指标只有描述无目标值。建议为每个指标设定 MVP 目标值和成熟期目标值 |
| P0-03 | **MEDIUM** | §8 | **全局业务规则缺少数据精度和时间约束**。规则提到"原始遥测不得因人工修正而覆盖"和"幂等标识同步"，但未定义：金额精度（分到厘？）、时间基准（UTC 还是北京时间？）、统计周期边界。这些应在总纲层统一，避免各 PRD 各自定义 |
| P0-04 | **MEDIUM** | §13 | **SDD 下游交付要求过于笼统**。只要求"唯一需求 ID、Given/When/Then 验收场景、状态机、权限矩阵、错误处理、兼容策略和非功能预算"，但缺少：数据字典、事件契约、API 契约、部署能力声明和标准/Full 差异说明。应引用宪法附录 A 的立项模板字段 |
| P0-05 | **LOW** | §4 | **用户角色缺少"系统管理员"与"实施工程师"的区分**。PRD-01 提到"实施工程师"角色，但总纲角色表中未列出。建议补充 |
| P0-06 | **LOW** | §11 | **里程碑缺少时间维度**。与《平台功能计划》§10 同样的问题——只有产品结果描述，缺少预估工期或阶段间依赖关系 |

### 3.2 PRD-01 站点设备与数据采集

#### 优点

- "建设分类"表（直接复用/修改增强/新增）非常清晰，便于开发团队理解工作量分布。
- 数据质量（§4）设计到位，质量码区分正常、超时、无效、越界、人工修正和补传。
- 明确引用 `TelemetryStore` 作为存储抽象，standard/full 不感知后端差异。
- 异常与边界（§5）考虑了串口冲突、幂等补传、时间漂移、模板升级失败和边缘存储溢出。

#### 发现的问题

| 编号 | 严重度 | 位置 | 问题 |
|---|---|---|---|
| P1-01 | **HIGH** | §4.2 | **物模型模板版本化策略不完整**。"模板发布后生成版本；已绑定设备不会被未确认升级自动改变"——但缺少：模板回滚策略、厂家模板与标准模板差异的合并规则、跨租户模板共享与隔离策略 |
| P1-02 | **HIGH** | §4.3 | **RS485 采集配置缺少并发与冲突检测**。同一串口可能有多个从站设备，但未说明：串口独占锁策略、轮询周期冲突检测、总线负载估算和告警。当轮询总时间超过业务要求时如何处理 |
| P1-03 | **MEDIUM** | §4.5 | **历史查询缺少分页与资源约束**。"支持多设备、多测点曲线对比"但未限制：单次查询最大测点数、最大时间跨度、聚合粒度自动选择规则。大量测点长周期查询可能打垮数据库 |
| P1-04 | **MEDIUM** | §4.3 | **倍率定义位置不明确**。寄存器配置中有"倍率"（§4.3 第2项），能源计量点也有倍率（PRD-05 §3），两处倍率的关系和优先级未说明——采集层倍率与业务层倍率是否叠加？变更审批流程是否相同？ |
| P1-05 | **LOW** | §8 | **非功能要求"采集任务数量、轮询周期和缓存大小可配置"缺少参考范围**。建议给出默认值和上限，例如：单 collector 最大测点数、最小轮询周期、最大缓存天数 |

### 3.3 PRD-02 监控告警与安全控制

#### 优点

- 告警状态机已吸收上一轮评审建议，增加了 `IGNORED`（临时抑制通知）和 `FALSE_ALARM`（不可逆终态），并明确了条件和约束。
- 安全遥控流程（§5.2）完整覆盖了申请→预检→复核→执行→回执→审计全链路。
- §5.3 第9项明确了 `iot-device` 是遥控的唯一责任模块，解决了上一轮评审 C1 的问题。
- 事故追忆（§4.4）要求统一事件时间线和不可修改的证据导出。
- 非功能要求明确了 standard 若未满足完整遥控依赖必须整体关闭 capability。

#### 发现的问题

| 编号 | 严重度 | 位置 | 问题 |
|---|---|---|---|
| P2-01 | **HIGH** | §4.2 | **`IGNORED` 状态的到期恢复行为存在歧义**。状态图显示 `IGNORED → ACTIVE: 到期恢复`，但恢复到 ACTIVE 后是否重新触发通知？是否重新评估规则？如果数据已恢复则直接 RECOVERED？需要明确到期后的处理逻辑 |
| P2-02 | **HIGH** | §4.1 | **复合规则的条件组合缺少约束定义**。"支持多测点复合条件"但未说明：最大条件数、支持的逻辑运算符（AND/OR/NOT）、条件嵌套深度、规则表达式语法。过于灵活的规则引擎可能导致性能问题 |
| P2-03 | **MEDIUM** | §4.3 | **通知渠道故障的处理策略不完整**。"渠道故障不能阻止告警本身创建"——但渠道故障期间的通知是否缓存？渠道恢复后是否补发？补发是否有时间窗口限制？ |
| P2-04 | **MEDIUM** | §5.2 | **安全遥控"有效执行窗口"缺少默认值和安全约束**。批准有效期多长？窗口内是否允许多次执行？窗口过期后申请自动作废还是保留草稿？ |
| P2-05 | **MEDIUM** | §4.4 | **事故追忆数据窗口缺少资源约束**。"关联告警前后可配置时间窗内的遥测数据"——窗口最大多大？是否受 TelemetryStore 查询限制？大窗口追溯是否需要异步任务？ |
| P2-06 | **LOW** | §4.2 | **告警等级只有四级（信息、一般、重要、紧急）**。电力行业常见"危机"等级（如设备起火、人身安全事故），建议确认是否需要扩展或映射 |

### 3.4 PRD-03 可视化 SCADA 与视频联动

#### 优点

- 信息架构（§3）层次清晰：集团总览→区域/园区→站点看板→各子模块。
- 一次系统图（§4.2）明确要求颜色和动画表达状态时"必须同时提供文字或图标"，符合无障碍设计原则。
- 发布版本与草稿隔离，编辑错误不影响生产展示。
- 控制操作必须跳转安全遥控流程，不允许图元直接绕过审批——与 PRD-02 安全遥控一致。

#### 发现的问题

| 编号 | 严重度 | 位置 | 问题 |
|---|---|---|---|
| P3-01 | **HIGH** | §4.2 | **一次图"在线编辑"的并发控制未说明**。多人同时编辑同一站点一次图时如何处理？是否需要锁？冲突如何解决？发布回滚是否影响其他编辑者的草稿？ |
| P3-02 | **HIGH** | §7 非功能 | **画面数据刷新频率"可配置"但缺少性能基准**。高频轮询（如每秒刷新 100+ 测点）对 WebSocket 和服务端的压力未评估。建议定义：单画面最大订阅测点数、推荐刷新频率范围、断线重连后的数据恢复策略 |
| P3-03 | **MEDIUM** | §4.4 | **视频联动的触发策略不完整**。"告警发生时可触发预置位、抓拍或指定时长录像"——同一告警同时触发多个摄像机时的并发限制？联动失败是否影响告警本身？联动配置是否需要权限控制？ |
| P3-04 | **MEDIUM** | §4.1 | **站点看板指标"点击可进入来源页面"的钻取深度未定义**。是只钻取到设备列表？还是可以到测点历史？跨域钻取（如从看板的用能指标钻取到 PRD-05 能源详情）的权限如何处理？ |
| P3-05 | **LOW** | §7 | **standard 的"基础一次图查看"与 full 的"FUXA Web SCADA"差异边界不够清晰**。"基础查看"是否包含拓扑交互（如点击开关查看详情）？是否包含控制入口？建议明确功能清单 |

### 3.5 PRD-04 设备档案与运维闭环

#### 优点

- 核心闭环（§8）清晰：巡检计划→任务→执行→缺陷→工单→处理→验收→关闭→统计。
- 人员位置（§7）的隐私设计完善：用户明确授权、工作时段采集、可查看采集状态、历史自动删除。
- 工单历史采用追加式记录不覆盖原动作，满足审计要求。
- 验收标准覆盖了幂等同步、权限隔离、轨迹清理等关键场景。

#### 发现的问题

| 编号 | 严重度 | 位置 | 问题 |
|---|---|---|---|
| P4-01 | **HIGH** | §4.2 | **APP 离线执行的数据同步协议缺失**。"支持弱网离线执行和联网同步"和§11"APP 离线数据加密保存，成功同步后清理"——但缺少：离线数据格式、同步协议（HTTP/MQTT）、幂等键生成规则、冲突解决策略（服务端优先？客户端优先？）、附件分片重传机制。这些应在 Spec 前定义 |
| P4-02 | **HIGH** | §6 | **工单状态机缺少与 PRD-02 告警状态机的关联映射**。工单可由告警自动创建（重大缺陷"自动创建抢修工单"），但告警关闭/恢复时工单是否联动？工单关闭时是否回写告警状态？ |
| P4-03 | **MEDIUM** | §5 | **缺陷定级标准未定义**。缺陷有"等级"但未说明等级划分（如一般/严重/危急）、各等级对应的响应时限和升级策略。建议至少给出默认等级定义和可配置扩展 |
| P4-04 | **MEDIUM** | §4.2 | **到场证据方式"由站点配置"但缺少降级策略**。GPS、站点围栏或蓝牙——若站点无蓝牙信标或 GPS 信号弱，是否允许降级为手动签到？降级是否影响巡检记录的可信度标记？ |
| P4-05 | **LOW** | §12 | **部署档位表中 standard 的"简化闭环"与 full 的"完整 SLA"差异缺少具体功能清单**。例如：standard 是否有暂停/转派？是否有评价？建议补充功能对照表 |

### 3.6 PRD-05 能源管理与电能质量

#### 优点

- 计量拓扑校验（§3）要求"校验循环关系和重复计量"，避免数据重复计算。
- 冻结值版本化（§4）"一经确认不可直接覆盖，修正必须产生新版本和原因"，满足审计要求。
- 最大需量（§6）"缺失数据时不得静默生成完整结果，必须标记可信度"——数据诚信设计到位。
- 电能质量（§8）"不满足采样条件时显示'不具备计算条件'"——避免了误导性结果。
- 费用可重算（§7）"保留使用的价格方案版本"，满足账期回溯需求。

#### 发现的问题

| 编号 | 严重度 | 位置 | 问题 |
|---|---|---|---|
| P5-01 | **HIGH** | §3 | **计量点倍率的定义与 PRD-01 采集层倍率的关系未明确**。PRD-01 §4.3 在寄存器配置中定义了"倍率"，PRD-05 §3 在计量点中定义了"倍率"。两个倍率是同一概念的不同表达？还是采集层做硬件倍率换算、业务层再做 CT/PT 倍率换算？若两层都有倍率，计算公式和变更审批流程是否相同？这是上一轮评审 H4 的延伸，PRD 层面仍未闭合 |
| P5-02 | **HIGH** | §3 | **组织和计量关系"按有效期管理"的时区与精度未定义**。历史统计"使用当时有效关系"——有效期精确到天？小时？变更的生效时刻是以配置时间还是审批通过时间为准？跨时区站点的组织关系如何处理？ |
| P5-03 | **MEDIUM** | §4 | **自动抄表的"计划"与 PRD-04 巡检"计划"的关系未说明**。两者都是定时任务，是否有统一的调度框架？抄表失败重试与巡检超期通知是否复用同一套任务调度基础设施？ |
| P5-04 | **MEDIUM** | §6 | **需量计算窗口"滑动方式"缺少默认值和标准参考**。电力行业需量计算通常有 15 分钟/30 分钟滑差窗口，但 PRD 未指定默认值。不同窗口会产生不同结果，影响电费计算 |
| P5-05 | **MEDIUM** | §8 | **电能质量指标的采样率要求未定义**。THD 和谐波分析需要较高的采样率（通常 ≥ 256 点/周期），但 PRD 未说明最低采样率要求和数据不足时的处理 |
| P5-06 | **LOW** | §12 | **standard 的"基础台账"与 full 的"更大规模与集中治理"差异模糊**。"更大规模"是测点数量？站点数量？数据保留期？建议量化 |

### 3.7 PRD-06 报表与经营分析

#### 优点

- 报告审批流程完整：草稿→待审批→已批准→已发布→已作废，支持退回和修订版。
- "指标引用统一口径，不允许模板自行编写不可审计 SQL"——避免了数据不一致风险。
- "数据完整率不足时显示警告，不静默输出确定性结论"——数据诚信设计。
- 非目标明确（不建设通用 BI、不允许任意 SQL、报告建议不触发控制），避免范围蔓延。

#### 发现的问题

| 编号 | 严重度 | 位置 | 问题 |
|---|---|---|---|
| P6-01 | **HIGH** | §5.2 | **报告生成"冻结"机制的实现约束未说明**。"生成时冻结统计范围、数据版本、计算口径和模板版本"——冻结是快照还是引用？如果源数据修正后需要重算，如何保证"同一数据版本"的幂等性？大报告冻结数据的存储成本如何控制？ |

## 十、整改复核与采纳裁决

### 10.1 对评审报告本身的判断

评审对共享口径、跨域状态、倍率、离线同步和非功能预算的识别是合理的，但存在以下需要纠正之处：

1. `P0-01` 的事实前提错误。当前两份上游文档均为 1.4.0，PRD 引用正确，不应回退到 1.3.0。
2. 原“HIGH（9 项）”实际列出 16 个条目，数量统计错误；整改以问题 ID 为准，不以该数量为准。
3. 部分建议要求在 PRD 固定 API 语法、附件分片字节数、规则表达式实现和统一电能质量采样率，超出产品需求层级，应由 Feature Spec/Technical Design 在样本与压测证据基础上冻结。
4. `P2-06` 建议增加“危机”告警等级会破坏已经统一的四级告警口径。火灾、人身和重大设备风险应映射为“紧急”并通过告警类型、升级和不可忽略策略表达。
5. `P5-05` 所举固定采样率不适用于“设备已计算指标”和“平台由波形计算”两种不同输入，不能直接作为全局产品约束。

### 10.4 复核结论

- 六项原批准条件中，基线版本问题经核查为误报；其余五类合理问题均已在 PRD 1.2.0 中关闭或明确下沉到对应 Spec。
- PRD 只冻结产品语义、边界和验收结果；实现协议、字段、表达式语法和精确资源预算仍须由 Feature Spec/Technical Design 评审，不得把“下沉”解释为无需处理。
- 文档整改门禁已通过。各 PRD 保持 `In Review`，待产品负责人确认指标和业务口径后改为 `Approved`；未经批准不自动形成新增开发承诺。
