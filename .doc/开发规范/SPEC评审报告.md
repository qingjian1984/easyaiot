## 二、总体评价

M1 基线 4 份 SPEC 质量很高，体现了从代码事实出发的工程务实风格。每份 Spec 都引用了现有代码资产（`IotModbusRtuPollingProtocol`、`PROPERTY_DOWNSTREAM_REPORT_ACK` 等），明确标注了实现差距，避免了"规格与实现脱节"的常见陷阱。

主要亮点：

1. **PRD 评审 HIGH 问题全部闭环**——倍率分层（SPEC-003 §7 RTU-015）、历史查询配额（SPEC-004 DQ-015）、物模板三方合并（SPEC-002 §6）、RS485 总线负载准入（SPEC-003 §5 RTU-014）均已给出精确规范。
2. **冻结记录诚实标注实现差距**——SPEC-004 §13 明确指出 `needReply=false`、TDengine 异常被吞掉等现有代码缺陷，要求改造通过验收前不得宣称已实现。
3. **后续 Spec 编写约束完备**——14 项 Spec 的必含约束和已冻结产品规则已锁定，跨 Spec 事实流通过 Mermaid 图表达清晰。

主要短板：

1. **tenantId 类型存在精度隐患**——SPEC-001 示例中 `tenantId: 1001` 使用 JSON 数字类型，但大租户 ID 在 JavaScript 生态中可能丢失精度。
2. **SPEC-001 与 SPEC-004 的跨域引用格式不完全对齐**——SPEC-001 §8 示例包含 `siteCode`，但 SPEC-004 数据信封中也有 `siteCode`，两者对 `siteCode` 缺失场景（旧设备未绑定站点）的处理规则未统一。
3. **后续约束中 SPEC-011 离线同步协议的关键参数仍待 TD 阶段确定**——约束文件已列出必含项，但离线信封格式、幂等键规则、附件分片大小等核心参数未给参考值。

## 三、各 SPEC 评审

### 3.1 SPEC-001 电力对象与测点编码规范

#### 优点

- 编码原则严格：ASCII 小写 + 数字 + 连字符，正则明确，区分大小写但写入统一小写。
- 唯一范围表清晰，每个对象的唯一约束一目了然。
- 空间树与回路树分离，设备可同时绑定两个维度，符合电力一次接线逻辑。
- 二维码设计安全：短码不可枚举、不暴露内部 ID、撤销后不可复用、统一返回不可解析防枚举。
- 跨域 deep link 必须重新鉴权，链接不携带令牌或租户授权结论。
- 兼容策略务实：存量 `deviceIdentification` 原值保留，新编码只约束新建数据。

#### 发现的问题

| 编号 | 严重度 | 位置 | 问题 |
|---|---|---|---|
| S1-01 | **HIGH** | §8 示例 | **`tenantId` 类型存在精度隐患**。示例中 `"tenantId": 1001` 使用 JSON 数字类型。Java 后端若使用 `Long`，JavaScript 前端在 `tenantId > 2^53 - 1` 时丢失精度。建议：① schema 明确 `tenantId` 为整数且范围不超过 `Number.MAX_SAFE_INTEGER`；或 ② 在跨系统交换（事件、二维码、API）中使用字符串类型 |
| S1-02 | **MEDIUM** | §8 vs SPEC-004 §2 | **跨域引用格式未统一处理 `siteCode` 缺失场景**。SPEC-001 §8 示例要求 `siteCode` 必填，但旧设备可能未绑定站点。SPEC-004 数据信封也包含 `siteCode`。当旧设备尚无 `siteCode` 时，两份 Spec 应统一规定：信封中 `siteCode` 是否可为空？为空时如何处理权限校验？ |
| S1-03 | **MEDIUM** | §4.2 | **`propertyCode` 的唯一范围表述可能引起歧义**。表中写"产品属性：`productId + propertyCode`"，但 `productId` 是内部数值主键。建议明确：对外交换时 `propertyCode` 的唯一性应通过 `productCode + propertyCode` 还是 `productId + propertyCode` 表达？后者在跨系统引用中不可用 |
| S1-04 | **LOW** | §6 | **标准对象类型中缺少"断路器"和"隔离开关"的独立类型**。`incoming-cabinet` 和 `feeder-cabinet` 是柜级对象，但实际一次图中断路器和隔离开关是独立图元。建议确认是否需要补充 `circuit-breaker` 和 `disconnector` 类型，或确认这些由图元层而非对象类型层处理 |
| S1-05 | **LOW** | §11 | **别名映射"禁止循环映射"的校验时机未说明**。创建别名时校验？还是定期扫描？如果 A→B 已存在，创建 B→A 时是实时拒绝还是异步检测？ |

### 3.2 SPEC-002 电力设备物模型模板

#### 优点

- 三方差异合并（旧标准基线、厂家当前、新标准基线）设计精确，冲突必须人工逐项处理。
- 模板回滚恢复精确版本和绑定快照，不删除新版本期间的数据。
- 高风险服务强制标记 `HIGH_RISK` 并进入安全遥控流程。
- 必选属性校验贯穿产品实例化和模板升级全流程，不得因旧版本已运行而绕过。
- 互感器模板标记为 SHOULD 项，允许排期裁剪但保留独立模板类型和变比字段契约。
- 明确禁止将寄存器地址写入标准物模型模板，内部按两段校验但分别版本化。

#### 发现的问题

| 编号 | 严重度 | 位置 | 问题 |
|---|---|---|---|
| S2-01 | **MEDIUM** | §3.1 | **`dataType` 中 FLOAT 和 DOUBLE 的精度语义未定义**。SPEC-004 §2 要求"数值解析与持久化使用十进制定点语义"，但 SPEC-002 属性定义中仍允许 FLOAT/DOUBLE 类型。需要明确：属性定义的 `precision` 字段是否覆盖 FLOAT/DOUBLE 的持久化精度？还是所有 FLOAT/DOUBLE 值在上报时必须转为十进制字符串？ |
| S2-02 | **MEDIUM** | §6 | **模板版本 DRAFT→PUBLISHED→DEPRECATED→RETIRED 的触发条件未定义**。什么情况下自动或手动进入 DEPRECATED？RETIRED 后已绑定产品是否强制迁移？DEPRECATED 是否仍可用于新建产品？ |
| S2-03 | **MEDIUM** | §7.1 | **产品实例化校验的错误返回格式未定义**。TM-009 要求"校验失败不得发布"并"返回模板属性、产品属性和错误原因"，但具体的错误结构（是否支持批量错误、是否可下载）未给出。建议对齐 SPEC-003 的导入错误格式（逐行定位 + 可下载） |
| S2-04 | **LOW** | §5 | **三相数据后缀 `-a`/`-b`/`-c` 使用 SHOULD 而非 MUST**。如果允许例外，应说明什么情况可不使用后缀（如单相设备、直流设备） |
| S2-05 | **LOW** | §4 | **标准模板目录中互感器的点位字典"在 Technical Design 阶段以版本化 JSON/Excel 资产维护"未指定存放位置**。建议明确存放目录和版本管理方式 |

### 3.3 SPEC-003 RS485/Modbus RTU 采集产品化

#### 优点

- 从现有代码出发，明确"产品化而非重写"，降低了实施风险。
- 总线负载准入（RTU-014）：发布前估算最坏情况占用，超限拒绝发布——这是 PRD 评审中识别的关键风险的系统性解决方案。
- 采集换算与计量倍率分层（§7、RTU-015）：明确 `normalizedValue = decodedRaw × scale + offset` 只用于协议解码，CT/PT 倍率由计量点版本管理。直接闭环了 PRD 评审 P5-01 的倍率分裂问题。
- 降频探测策略精确：连续失败 3 周期后 `2x → 5x → 10x` 递增，最大 5 分钟，一次成功即恢复。
- 串口枚举安全：只返回候选项，不自动打开、修改权限或写入；热插拔后保留已发布配置。
- 合并读取上限 120 个 16 位寄存器，可按设备模板下调，不得超过协议和厂家上限。

#### 发现的问题

| 编号 | 严重度 | 位置 | 问题 |
|---|---|---|---|
| S3-01 | **MEDIUM** | §4.1 | **串口枚举在容器环境中的可行性未充分说明**。Docker 中 `/dev/ttyUSB*` 需要 `--device` 映射，但 §9 只要求"显式映射串口设备"。如果目标节点运行在 Kubernetes 或资源受限容器中，USB 设备热插拔可能需要额外的 device plugin 或 operator 支持。建议补充容器编排环境下的已知限制 |
| S3-02 | **MEDIUM** | §5 | **配置发布状态机中 VALIDATED→PUBLISHED 的触发条件未说明**。静态校验通过后是自动发布还是需要人工确认？PUBLISHED→APPLIED 的回报超时如何处理？ |
| S3-03 | **MEDIUM** | §6 | **寄存器合并读取的"数据类型兼容"判断规则未定义**。"SHOULD 合并连续且数据类型兼容的寄存器读取"——什么算"数据类型兼容"？INT16 和 UINT16 是否兼容？FLOAT32 跨两个寄存器时如何处理对齐？ |
| S3-04 | **LOW** | §13 | **测试资产复用 `.scripts/modbus-rtu-virtual-serial` 和 `.scripts/modbus-rtu-demo` 的版本未锁定**。如果这些脚本在 M1 实施期间被修改，可能导致验收基准漂移。建议标记测试资产的版本或 commit |
| S3-05 | **LOW** | §4.2 | **`scale` 和 `offset` 的数据类型未定义**。是整数？浮点？十进制字符串？与 SPEC-004 的十进制精度要求如何对齐？ |

### 3.4 SPEC-004 遥测质量与断点补传

#### 优点

- 数据信封设计完备：`messageId` 全局唯一、`sequence` 单调递增、`collectedAt`/`sentAt` 双时间、`configVersion` 关联配置版本。
- 质量码体系完整（10 种），每种质量码是否参与业务计算有明确定义。
- 数据完整率公式精确定义：左闭右开、应采集数按采样策略分段计算、`应采集数=0` 返回 `N/A` 而非 100%。
- UTC 归一化 + 站点时区保留的双时间策略，解决了跨时区统计的歧义。
- 十进制精度要求明确："累计量、倍率换算和费用上游值不得经二进制浮点舍入后成为事实"。
- 历史查询配额量化：standard 默认 10 测点、31 天、100,000 条；超限必须聚合或异步导出。
- 冻结决策诚实标注实现差距：`needReply=false`、TDengine 异常被吞掉等，要求改造通过验收前不得宣称已实现。

#### 发现的问题

| 编号 | 严重度 | 位置 | 问题 |
|---|---|---|---|
| S4-01 | **HIGH** | §2 vs SPEC-001 §8 | **数据信封中 `tenantId` 类型与 SPEC-001 存在同样的精度隐患**。信封示例 `"tenantId": 1001` 为 JSON 数字。SPEC-004 是核心数据契约，所有遥测都经过此信封，若 `tenantId` 在 JavaScript 前端或网关中被解析为 `Number`，大值将丢失精度。建议在信封 schema 中明确：① `tenantId` 为整数且 ≤ `Number.MAX_SAFE_INTEGER`，或 ② 使用字符串类型 |
| S4-02 | **MEDIUM** | §5.3 | **SQLite WAL 的并发写限制未说明**。WAL 模式支持单写多读，但多采集线程并发写入时的锁竞争策略未说明——是单线程写入队列？还是多线程竞争 WAL 写锁？在高点位密度场景下可能成为瓶颈 |
| S4-03 | **MEDIUM** | §7.1 | **数据完整率"封账"概念未定义**。"迟到数据在统计封账前可重算完整率；封账后到达时记录迟到量"——"封账"是什么触发的？时间点？人工操作？自动策略？封账后是否可以人工重开？ |
| S4-04 | **MEDIUM** | §4 | **乱序窗口的默认值未定义**。"乱序数据允许在配置窗口内重排和写入"——窗口默认多大？10 秒？1 分钟？超出窗口的迟到数据"仍可归档"——归档到哪里？是否参与完整率计算？ |
| S4-05 | **LOW** | §5.3 | **`dataPriority` 枚举中 `METERING_TOTAL` 的命名可能引起歧义**。该优先级用于缓存保留策略，`METERING_TOTAL` 容易与能源域的"累计量"概念混淆。建议改为 `METERING` 或 `METERING_ACCUMULATOR` |
| S4-06 | **LOW** | §6.1 | **ACK 状态 `REJECTED_RETRYABLE` 和 `REJECTED_FINAL` 的判定条件未说明**。什么情况下中心判定为可重试 vs 最终拒绝？是否需要在 TD 阶段定义具体的拒绝码？ |

| GW-03 | **MEDIUM** | §2 SPEC-013 | **倍率计算公式 `normalizedValue × currentRatio × voltageRatio × unitFactor` 中 `normalizedValue` 的含义需与 SPEC-003 对齐**。SPEC-003 §7 定义 `normalizedValue = decodedRaw × scale + offset`，这里直接作为倍率计算的输入。如果 `normalizedValue` 已经经过了 scale/offset 换算，再乘以 `currentRatio` 等倍率——这是期望行为还是可能导致重复计算？建议显式确认：collector 上报的 `normalizedValue` 不包含 CT/PT 倍率，能源域在此基础上应用业务倍率 |
| GW-04 | **MEDIUM** | §2 SPEC-011 | **离线同步的"附件分片/续传预算"缺少参考值**。建议给出最低约束：分片大小（如 256KB）、最大重试次数（如 5 次）、离线数据最大保留天数（如 7 天） |
| GW-05 | **MEDIUM** | §1 | **通用门禁第 7 条"事件升级采用 consumer-first、双发布至少一个发布周期"缺少具体操作定义**。"双发布"是同时发送 v1 和 v2？还是新版消费者同时监听新旧 Topic？"至少一个发布周期"是多长？ |
| GW-06 | **LOW** | §2 SPEC-017 | **电能质量"不从普通低频遥测推导谐波/THD"是正确的约束，但缺少最低采样率的量化定义**。建议补充：谐波分析要求 ≥ 256 点/周期（50Hz 系统即 ≥ 12,800 采样/秒），THD 计算要求至少基波 + 前 50 次谐波 |
| GW-07 | **LOW** | §4 | **"standard/full capability 差异表和 strict-superset 自动校验方案"——自动校验方案的技术实现未说明**。是通过 CI 脚本比对 capability manifest JSON？还是通过集成测试验证？建议给出参考实现方式 |

## 九、综合改进建议

### 9.1 立即行动（M1 基线修订）

#### 1. 统一 `tenantId` 类型

在 SPEC-001 和 SPEC-004 中统一修正 `tenantId` 的类型定义。建议两种方案之一：

- **方案 A**（推荐）：在 JSON schema 中声明 `tenantId` 为 `string`，跨系统交换时一律使用字符串，后端内部仍可使用 `Long`。
- **方案 B**：声明 `tenantId` 为 `integer`，同时约束最大值 ≤ `Number.MAX_SAFE_INTEGER`（即 9,007,199,254,740,991），并在文档中注明此约束。

#### 2. 补充 SPEC-009 性能基准推导

为"500 点/1 秒"给出推导依据：典型站点测点规模、浏览器 WebSocket 处理能力、服务端推送资源预算。如果 500 点是保守估计，标注"首期默认值，可按站点调整"。

## 十一、整改复核与采纳裁决

### 11.1 总体判断

评审对跨系统标识精度、站点权限、模板数值语义、collector 发布/并发、迟到数据和 TD 门禁的判断成立。以下建议不宜按原文直接落地：

- M1 collector 的既定编排是 NODE + Docker Compose；为 Kubernetes/device plugin 增加实现属于范围扩张，只记录未来 ADR 门禁。
- 缺陷响应时限与 APP 分片/重试值依赖站点风险、终端限制、附件类型和弱网测试，不能在无证据时写死统一常数。
- 电能质量最低采样率和谐波阶次取决于采用标准、算法及设备是否已计算指标，不能用单一“256 点/周期、前 50 次”覆盖所有输入。
- `METERING_TOTAL` 已进入冻结契约，当前重命名收益小于兼容成本；通过语义说明和 UI 显示名消除歧义。

### 11.2 逐组裁决

| 问题 | 裁决 | 整改结果 |
|---|---|---|
| S1-01 / S4-01 / X-01 | 采纳，兼容迁移 | 新生产者发送字符串 tenantId；消费者兼容安全范围旧整数；未直接破坏旧消息 |
| S1-02 / X-02 | 采纳 | 电力事件/遥测 siteCode 强制非空并校验设备关系；历史未绑定设备先迁移，禁止降级权限 |
