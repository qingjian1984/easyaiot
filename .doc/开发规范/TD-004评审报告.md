## 2. 总体评价

**架构设计完备度：高。** TD-004 是对象模型/二维码/历史兼容三份合一的综合性 TD，覆盖了站点、空间树、回路树、设备归属、alias、二维码短码、deep link、legacy VO 修复、对象导入、capability 与迁移回滚全链路。文档对现有仓库的 Device/DeviceInfo/DeviceLocation 现状做了细致核对，避免了"新模型吞噬旧事实"的常见陷阱。

**主要风险集中在**：(1) owner_dept_id 缓存/撤销与 iot-system 解耦的具体化不足；(2) parse audit schema 未完整定义；(3) 解析审计不可用时的"全失败"语义在运维上过于严苛。

**与 SPEC-001/ADR-004/ADR-008/ADR-011 的一致性**：编码正则、唯一范围、两棵树分离、canonical 不可改、alias direct-to-target、二维码 HMAC-SHA-256 + keyVersion、128-bit CSPRNG、power.device.model capability 全部对齐。

## 6. 问题清单

### HIGH（必须修复才能冻结）

**H-01 · `owner_dept_id` 缓存撤销与 iot-system 解耦设计未具体化**

位置：§7.1 末段"已缓存的只读授权必须有短 TTL、版本/撤销失效和 tenant 键"。  
问题：(1) 缓存的 TTL 建议值未给出；(2) iot-system 部门/授权变更时的事件传播机制（MQTT？本地 event？Redis pub/sub？）未定义；(3) 跨服务撤销一致性在 iot-system 短暂不可用时如何保证；(4) 缓存的"tenant 键"语义不清。  
风险：若 iot-system 部门变更或显式 site grant 撤销后，缓存未能及时失效，可能导致越权访问持续数分钟至数小时，违反 §9 第 4 步的权限判定顺序。  
**建议**：补一节"站点授权缓存与撤销契约"：(1) 默认 TTL（如 30s 读缓存、5min 授权集合缓存）；(2) 撤销事件传播（建议 Redis pub/sub + DB 版本号双保险）；(3) iot-system 不可用时写关闭但读可继续用缓存（TTL 内）；(4) 架构测试验证任何授权变更 ≤ TTL+epsilon 后失效。

**H-02 · `Idempotency-Key` 存储与清理契约缺失**

位置：§16 "创建对象、alias、归属变更、二维码签发/轮换和导入应用均接受 Idempotency-Key"。  
问题：(1) request hash 存在哪里（哪张表？哪个 schema？）；(2) 保留期多长（默认 24h？7d？按 capability 配额？）；(3) 何时清理（定时任务？手动？）；(4) key 相同但 payload 不同的冲突语义是否返回 409 还是覆盖；(5) 跨副本一致性（多个 ingress 实例同时接收相同 Idempotency-Key）。  
风险：没有存储契约，实现容易按各团队理解分叉；清理不及时可能导致幂等表膨胀；保留期过短会破坏业务预期。  
**建议**：补一节"Idempotency-Key 契约"：表 Schema（idempotency_key, tenant_id, operation, request_hash, response_payload, created_at, expires_at）、TTL（如 24h）、清理策略（定时扫描 + 按 capability）、跨副本一致性（数据库唯一约束）。

**H-03 · 解析审计 `asset_qr_parse_audit` Schema 未定义**

位置：§7.8 "append-only：request_id、请求租户、认证主体类型/ID、token 指纹、目标类型/ID、内部结果码、站点 ID、来源渠道、客户端摘要、发生时间和 trace ID"。  
问题：只列出了字段清单，未给出列类型、索引、保留期、清理策略。尤其：(1) `request_id` 是 UUID 还是字符串？(2) `token 指纹` 保存 HMAC 短前缀还是独立审计 HMAC？(3) 索引如何支持"按 token 查询历史解析"和"按时间范围审计"两种高频查询；(4) 保留期（30d？90d？合规 hold 可延长？）。  
风险：实现时 Schema 分叉；审计表无法支持后续安全调查。  
**建议**：补 §7.8 完整 Schema（类似 §7.7 的表结构），包括列类型、索引（建议按 token_fingerprint + occurred_at、tenant_id + occurred_at 两类）、保留期（如 90d，安全 hold 可延长）。

### MEDIUM（应修复；不阻塞冻结但需跟踪）

**M-01 · `space_type` / `circuit_type` 扩展校验缺失**

位置：§7.2 "`space_type` VARCHAR(64) 标准类型或 `x-` 扩展类型"。  
问题：(1) 标准类型枚举未列出（SPEC-001 §6 有清单，TD-004 未引用）；(2) `x-` 扩展类型只校验前缀，未校验长度、字符集、注册机制；(3) 不同租户的 `x-` 扩展可能冲突（租户 A 的 `x-temp-sensor` vs 租户 B 的同名扩展）。  
**建议**：补 `space_type`/`circuit_type` 枚举校验：标准类型使用 SPEC-001 §6 清单；`x-` 扩展使用租户内唯一性校验（建议加 `tenant_id + x_type` 唯一约束或显式注册表）。

**M-02 · 六张新表索引定义缺失**

位置：§7 Schema 段。  
问题：§7.1~7.9 只列出列定义，未给出索引建议（除 §6.2 的唯一约束）。对于高频查询路径（按 site 聚合、按 device 查询 assignment 历史、按 alias 解析、按 token_hash 查 QR）缺少索引指导。  
**建议**：为每张表补索引建议：(1) `power_site` 按 `(tenant_id, status)`；(2) `power_space_node` 按 `(tenant_id, site_id, parent_id)`；(3) `power_device_assignment` 按 `(tenant_id, device_id, valid_to)`、`(tenant_id, site_id)`、`(tenant_id, asset_code) WHERE asset_code IS NOT NULL AND valid_to IS NULL`；(4) `power_object_alias` 按 `(tenant_id, object_type, scope_key, alias_code) WHERE status='ACTIVE'`；(5) `asset_qr_token` 按 `(target_type, target_id) WHERE status='ACTIVE'`、`(token_hash) WHERE status='ACTIVE'`。

**M-03 · deep link 结构与 SPEC-001 §8 不一致**

位置：§12 deep link 契约 vs SPEC-001 §8 示例。  
问题：SPEC-001 §8 示例字段为 `{tenantId, siteCode, deviceIdentification, propertyCode, occurredAt}`；TD-004 §12 字段为 `{resourceType, tenantId, siteCode, businessId, occurredAt}`。`businessId` 替代 `deviceIdentification` 是合理抽象（支持多种资源类型），但与 SPEC-001 字段名不一致。  
**建议**：在 §12 增加"与 SPEC-001 §8 关系"段：说明 §12 是泛化版本（支持 SITE/SPACE/CIRCUIT/DEVICE 多种资源），SPEC-001 §8 示例是 DEVICE 子集；或调整 TD-004 §12 字段名与 SPEC-001 对齐（`businessId` → `deviceIdentification` 对 DEVICE 类型）。

**M-04 · `assetCode` 唯一范围仅限当前记录**

位置：§6.2 设备 `assetCode` 唯一键 `(tenant_id, asset_code) WHERE asset_code IS NOT NULL AND valid_to IS NULL`。  
问题：该约束只保证当前记录的 assetCode 唯一，历史记录（`valid_to IS NOT NULL`）不校验。如果同一设备历史上使用过 assetCode "tr-01"，后来变更后新设备也使用 "tr-01"，会出现两个历史记录的 assetCode 相同。  
风险：历史查询时无法区分"哪个设备曾经拥有 assetCode tr-01"。  
**建议**：考虑扩展唯一约束为 `(tenant_id, asset_code, valid_from, valid_to)` 覆盖历史全周期；或在文档中明确"assetCode 只在当前生效，历史 assetCode 允许重复但需通过 assignment 时间范围区分"。

**M-05 · `power_device_aux_relation` 枚举值未冻结**

位置：§7.5。  
问题：(1) `dimension` 枚举（SPACE/CIRCUIT）列出但缺少其他维度说明；(2) `relation_type` 未定义枚举（如"辅助供电"、"备用回路"、"监控从属"等）；(3) 该表 M1 只用于"展示"，但 collector/联锁/结算不得读取——需要架构测试保证。  
**建议**：补 `dimension`/`relation_type` 枚举值清单；增加架构测试"collector/联锁/结算模块不得注入 `power_device_aux_relation` Mapper"。

**M-06 · collector 发布门禁 API 契约未定义**

位置：§14 `PowerObjectQueryApi` 返回快照。  
问题：(1) API 是 OpenFeign 接口还是 REST？(2) 快照的不可变性如何保证（assignmentVersion 是 assignment 表的 version 列？）；(3) API 失败或延迟时 collector 发布如何处理；(4) 快照与 TD-001 collector 配置版本的关系（configVersion 是 assignmentVersion？）  
**建议**：补 §14.1 "PowerObjectQueryApi 契约"：API 形式（建议 OpenFeign，与现有 `iot-device-api` 一致）、返回 DTO 字段、不可变快照的 version 来源（建议 assignment 表的 version 列）、与 TD-001 configVersion 的映射关系、失败处理（建议返回 RETRYABLE，由 TD-001 重试策略承接）。

**M-07 · 树递归 CTE 深度限制与并发保护**

位置：§7.2 "查询最大深度由 capability 配额限制"。  
问题：(1) 移动节点时的循环检测使用递归 CTE，但未给出最大深度限制（防止递归爆炸）；(2) 并发移动两个节点时的锁顺序（先锁源后锁目标？死锁风险？）；(3) 最大深度的 capability 配额值未候选。  
**建议**：补：(1) 递归 CTE 默认最大深度（如 10，按 capability 可调）；(2) 移动节点时按 `(site_id, id)` 升序锁定路径节点避免死锁；(3) 最大深度 capability 候选值（如 standard 10、full 20）。

**M-08 · 解析审计不可用时的"全失败"语义运维严苛**

位置：§7.8 "成功解析不得返回对象，统一按服务暂不可用失败"。  
问题：解析审计是 append-only 安全要求，审计 DB 不可用时拒绝返回对象。这在安全上是正确的，但运维上过于严苛——审计 DB 短时抖动（如网络切换、连接池耗尽）会导致所有扫码失败，影响用户体验。  
**建议**：考虑分级降级：(1) 审计 DB 不可用时，允许返回对象但标记 `audit_pending=true`，并在恢复后补写（bounded queue + 补写任务）；(2) 或定义最大不可用时长（如 30s），超过后启用降级；(3) 指标必须暴露 `audit_queue_depth` 和 `audit_lag`。这与 TD-003 评审 H-03（审计库不可用处理）是同一类问题，建议统一降级策略模式。

### LOW（建议修复，可推迟）

**L-01 · `site_name` 唯一性未定义**

位置：§7.1。  
问题：`site_name` VARCHAR(128) 是否有租户内唯一约束未说明。如果两个站点同名，用户在 UI 选择时可能混淆。  
**建议**：明确 `site_name` 允许重复（靠 site_code 区分），或增加租户内唯一约束。

**L-02 · `sort_order` 更新语义未定义**

位置：§7.2/§7.3。  
问题：`sort_order` INTEGER 只影响展示，但未定义如何更新（同级移动时的批量重排算法？还是只接受显式值？）。  
**建议**：明确 `sort_order` 更新规则（如接受显式值，同级移动时由客户端计算新顺序）。

**L-03 · `POWER_CODE_INVALID` 错误响应体未定义**

位置：§15。  
问题：HTTP 400 错误但具体违反哪条规则（字符集？长度？唯一范围？）未在响应体说明。  
**建议**：在错误响应体增加 `detail` 字段（如 `{"code": "POWER_CODE_INVALID", "field": "siteCode", "reason": "regex_mismatch"}`）。

**L-04 · `AMBIGUOUS_PARENT_DEVICE_ID` 错误场景未完整说明**

位置：§13.2/§15。  
问题：错误返回条件"同时提交新旧字段时必须一致"，但"一致"的判定（数值相等？字符串化后相等？tenant 范围？）未明确。  
**建议**：补"一致"定义（建议 parentDeviceId 数值与 deviceIdentification 的 Long 值相等，且 tenant 内存在该设备）。

**L-05 · collector 查询快照缓存语义**

位置：§14。  
问题：collector 收到的是版本化快照，但未说明 collector 侧是否缓存、缓存 TTL、归属变化后的通知机制。  
**建议**：明确 collector 侧行为（建议不缓存，每次发布重新查询；或缓存但监听归属变化事件）。

**L-06 · standard/full 配额候选值未给出范围**

位置：§18。  
问题：配额"待压测"是合理的，但连范围估计都没有。  
**建议**：补候选值范围（如站点数 standard ≤100/full ≤1000；QR 数 standard ≤10000/full ≤100000；导入行数 standard ≤1000/full ≤10000）。

**L-07 · 二维码解析 API 响应体字段未完整定义**

位置：§10.3。  
问题：`displayName` 是否必填、`route` 字段的 URL 编码规则（中文如何处理？）未说明。  
**建议**：补响应体 Schema：`resourceType` 必填、`siteCode` 必填、`deviceIdentification` 必填、`displayName` 选填（最长 128 字符）、`route` 必填（percent-encoding 遵循 RFC 3986）。

## 11. 复核与最终处置（2026-08-04）

### 11.1 复核结论

评审对授权撤销、幂等记录、解析审计、索引、deep link、collector 契约和 API 细节的判断总体合理，已更新 [TD-004 1.0.1](../技术设计/电力运维云平台/TD-004-电力对象别名二维码与历史编码兼容.md)。

四项建议不能原样执行：

1. M-04 建议的 `(tenant_id,asset_code,valid_from,valid_to)` 不能阻止不同历史区间复用同一 assetCode，也会让设备每次移站复制资产身份。最终把 `assetCode/objectType` 从 assignment 历史中拆到 `power_device_asset`，对 `(tenant_id,asset_code)` 建永久唯一约束。
2. M-08 建议的 `audit_pending=true` 成功响应会产生没有持久审计证据的授权成功路径，与安全默认开启及 TD-003 已处置原则冲突。M1 维持 fail-closed，并让解析审计与 token/对象使用同一 PostgreSQL 可靠边界，避免另设审计数据库单点。
3. M-01 所称 SPEC-001 §6 清单主要是设备类型，不能直接当成 space/circuit 枚举；已分别冻结 M1 空间/回路类型和 `x-` 校验，但不同 tenant 使用同名扩展是有意隔离，不构成冲突，也不为无附加属性的类型创建冗余注册表。
4. M-07/L-06 提议的 standard/full 树深和规模示例缺少压测依据。仅冻结 64 层硬安全上限、30 秒授权撤销缓存上限等正确性/安全边界；产品配额仍由 manifest 和真实压测证据冻结，不采用 `100/1000` 等猜测值。
