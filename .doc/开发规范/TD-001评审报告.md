## 一、总体评价

TD-001 质量很高，是目前文档链中工程化程度最高的技术设计。从代码基线差距分析（§2）到实现任务排序（§18），形成了完整的设计→实施→验收链路。类型化 WorkloadSpec 和配置快照设计精确，安全边界清晰，失败处理和回滚策略完整。

主要亮点：

1. **代码基线差距分析诚实**——明确列出 7 项现有资产的可复用能力和必须修改的差距，避免"假装复用"或"全部重写"两个极端。
2. **类型化 WorkloadSpec 杜绝命令注入**——`iot-sink-collector` 固定 workloadType，Agent 只接受白名单 schema，通用 `/workload/deploy` 对该类型返回 `UNSUPPORTED_GENERIC_DEPLOY`。
3. **配置快照原子写入**——同目录临时文件 + `fsync` + 原子 rename，保留最近两个已应用版本。
4. **三层串口冲突防护**——控制面预占 → Agent 本地 reservation → collector 实际打开。
5. **健康 facet 分级精确**——`center=DEGRADED` 不触发重启，`process=FAILED` 才允许有界重启。
6. **SPEC-003 追踪矩阵完整**——15 个 RTU 需求均有设计落点和验证方式。
7. **测试资产锁定 git blob**——解决了评审中识别的版本漂移风险。
8. **资源冻结方案务实**——384 MiB 明确标注"首轮候选"，需压测冻结，不能修改代码形成分叉。

主要短板：

1. **配置快照示例中 `tenantId`/`siteId` 使用字符串，但 `deviceId` 使用数值字符串**——与 SPEC-001/ADR-004 的稳定业务标识体系需要对齐确认。
2. **更新期间的数据缺口处理与 SPEC-004 数据完整率的衔接需显式确认**——`stage=COLLECTOR_DOWNTIME` 是好起点，但"计划窗口"的计算规则未定义。
3. **TD-002/003 的依赖接口（`TelemetryOutboxPort`）契约足够清晰，但 inbox 清理职责归属未在本 TD 中显式提及**——ADR 评审 A06-01 识别的 `TelemetryStore` 缺少清理操作问题，本 TD 未涉及。

### 2.2 §3-4 拓扑、职责与持久模型

#### 优点

- 职责表精确到"禁止事项"，避免职责越界。
- 发布单表设计完整：版本、SHA-256、状态机、乐观锁、审计字段齐备。
- 回滚创建新版本（不回退版本号），保护版本序列连续性。
- `iot-node` 扩展字段覆盖期望/观察版本、健康 facet、串口绑定。

#### 发现的问题

| 编号 | 严重度 | 问题 |
|---|---|---|
| T01-02 | **HIGH** | **`iot_collector_config_release` 表中 `payload` 为 jsonb 但 `payload_sha256` 是对 canonical JSON 计算的**。jsonb 在 PostgreSQL 中不保证序列化顺序一致性——同一 JSON 对象写入后读出再做 `to_jsonb()::text` 可能与写入前的 canonical JSON 字节不同。建议明确：SHA-256 是对写入前的 canonical JSON 字节计算，还是对 PostgreSQL `jsonb` 类型的规范化输出计算？两者必须统一，否则校验会失败 |
| T01-03 | **MEDIUM** | **`tenant_id/site_id` 为 bigint 类型**。SPEC-001/ADR-004 体系下，`siteCode` 是字符串业务标识。本表使用内部数值 ID 作为发布单边界是否合适？如果控制面需要按 `siteCode` 查询发布历史，是否需要额外索引或关联表？建议明确：对外 API 使用 `siteCode` 还是 `site_id`，以及两者的映射方式 |
| T01-04 | **MEDIUM** | **`node_workload_binding` 扩展字段中 `health_facets jsonb` 的结构未在 TD 中定义**。SPEC-003 要求可观测性，§12.1 给出了 facet 枚举，但 jsonb 内部结构（字段名、值类型、嵌套方式）未定义 schema。建议至少给出 JSON schema 示例 |

### 2.3 §5-6 类型化 Workload 契约与配置快照

#### 优点

- WorkloadSpec 设计精确：镜像白名单 + digest 锁定、路径白名单、禁止特权模式、broker secret 独立引用。
- `memoryBytes=384 MiB` 明确标注"首轮压测候选"，不是生产默认值。
- 配置快照使用 canonical JSON + SHA-256 + 原子写入 + 历史保留。
- 应用顺序五步校验（schema → capability → 串口 → 点表/冲突 → 调度图 → 原子切换）。

#### 发现的问题

| 编号 | 严重度 | 问题 |
|---|---|---|
| T01-05 | **HIGH** | **配置快照示例中 `scale` 和 `offset` 使用字符串值 `"1"` 和 `"0"`（§9.2 要求 `BigDecimal` 定点运算），但 `baudRate`、`transmitDelayMs`、`pollIntervalMs` 和 `requestTimeoutMs` 仍为 JSON 数字**。这些时间值在 JavaScript 前端编辑时不会丢失精度（值较小），但在跨语言序列化时可能产生浮点表示差异。建议：① 时间类字段保持整数类型（JSON 整数无精度问题）并明确约束为非负整数；② 在 schema 中显式标注哪些字段是整数、哪些是十进制字符串 |
| T01-06 | **MEDIUM** | **配置快照中 `deviceId: "20001"` 使用字符串，但 §4.1 发布单表中 `tenant_id/site_id` 为 bigint**。配置快照与控制面持久模型的 ID 类型不一致。建议确认：collector 内部消费的是字符串还是数值？如果是字符串，从 bigint 到字符串的转换在哪一层完成？ |
| T01-07 | **MEDIUM** | **§5 中 `resources.memoryBytes: 402653184`（384 MiB）与 §13 "384 MiB 仅是第一轮候选"一致，但 Dockerfile 当前使用 `-Xms512m -Xmx512m`**。如果容器 limit 是 384 MiB 而 JVM heap 是 512 MiB，collector 将在启动时因内存不足被 OOM kill。TD §13 已识别此问题并要求"改为容器感知的百分比堆策略"，但 §5 的示例 spec 未标注这是一个待修复项。建议在 §5 的约束列表中显式标注"当前 Dockerfile JVM 参数与候选 limit 冲突，任务 5 必须修复" |
| T01-08 | **LOW** | **`updatePolicy.healthWindowSeconds: 60` 是否足够**。collector 启动需要：JVM 初始化 → Spring context 加载 → SQLite 打开 → 串口获取 → MQTT 连接 → 首次轮询。在资源受限环境（1 CPU, 384 MiB）下，60 秒可能偏紧。建议标注该值为"首轮候选"或给出冷启动时间预算 |

### 2.4 §7-8 API 与状态机

#### 优点

- Agent API 增加 HMAC 签名 + 时间戳 + nonce + body SHA-256 + 5 分钟防重放。
- 配置发布状态机包含 `APPLY_TIMEOUT`，迟到回报按三元组匹配。
- 工作负载状态机每次转换使用 `stateVersion` CAS + 审计事件。
- 更新顺序固定，不得蓝绿并行。

#### 发现的问题

| 编号 | 严重度 | 问题 |
|---|---|---|
| T01-09 | **MEDIUM** | **`APPLY_TIMEOUT` 默认 60 秒的触发条件未完整定义**。§8.1 说"PUBLISHED 默认 60 秒未得到终态回报进入 APPLY_TIMEOUT"——60 秒是从 PUBLISHED 状态创建时间算起，还是从 Agent 确认收到发布指令算起？如果 Agent 收到指令但 collector 正在执行长耗时串口释放，60 秒可能不够。建议区分：① Agent 收到指令的确认超时；② collector 应用配置的超时 |
| T01-10 | **MEDIUM** | **`/workload/collector/config` PUT 接口的"只接受更高期望版本或明确 rollback 发布"——乱序回报的处理**。§8.1 说"迟到回报仅在完全匹配时更新状态"，但 PUT 接口如果收到低于当前 observed 版本的 config 怎么办？是返回 `CONFIG_VERSION_STALE` 错误还是静默成功？建议明确错误码 |
| T01-11 | **LOW** | **Agent API 的 HMAC 防重放窗口为 5 分钟**——如果 NODE Agent 与 `iot-node` 的时钟偏差超过 5 分钟，所有请求将被拒绝。是否需要在心跳中同步时钟偏差？或放宽窗口到 10 分钟？ |

### 2.5 §9-10 collector Profile 与 NODE Agent 适配

#### 优点

- Spring Profile 明确禁用列表（HTTP/TCP/OPC UA 服务端、VIDEO/AI、Kafka、TDengine、MinIO、Milvus）。
- 解耦接口设计清晰：`PollingConfigProvider`、`PollingStatusReporter`、`TelemetryOutboxPort`。
- `scale/offset` 改为 `BigDecimal` 定点运算，兼容旧 `Double` 只在适配层。
- Agent 状态文件使用文件锁 + fsync + 原子 rename。
- 容器标签对账设计完整：一致则接管、缺失则 FAILED、未知则隔离告警。

#### 发现的问题

| 编号 | 严重度 | 问题 |
|---|---|---|
| T01-12 | **MEDIUM** | **§9.1 禁用列表中包含"Kafka 消费"，但 §2 差距表提到当前 `AbstractIndustrialPollingProtocol` 的上行入口可能依赖 Kafka 或 `messageService`**。解耦后 collector 只通过 `TelemetryOutboxPort` 写入本地 outbox（TD-002），但现有代码中是否存在 Poller 直接调用 Kafka producer 的路径？若有，需要在任务 6 中显式列出并替换 |
| T01-13 | **MEDIUM** | **§10 Windows 适配"只允许固定 `java ... -jar app.jar --spring.profiles.active=collector` 模板"——JVM 参数从哪里来？** §13 要求 JVM 使用容器感知或压测冻结值。Windows 非容器场景下，JVM 堆大小、GC 策略等参数是硬编码在安装脚本中？还是由 NODE Agent 根据主机资源动态生成？建议明确 Windows 场景的 JVM 参数来源 |
| T01-14 | **LOW** | **Agent 对账逻辑中"未知同标签容器隔离并告警，不自动删除"——隔离的具体操作是什么？** 是停止该容器？还是只标记状态但让容器继续运行？如果是停止，可能影响非 easyaiot 管理的合法容器。建议明确隔离策略 |

### 2.6 §11-12 串口与健康

#### 优点

- 串口枚举字段完整（12 个字段），覆盖硬件指纹和占用状态。
- Linux 优先使用 `/dev/serial/by-id/*` 稳定路径。
- 健康 facet 四级分级（process/config/serial/center）合理。
- `center=DEGRADED` 不触发重启的设计避免了网络抖动时的不必要的重启风暴。

#### 发现的问题

| 编号 | 严重度 | 问题 |
|---|---|---|
| T01-15 | **MEDIUM** | **§12.1 `serial=FAILED` 条件为"必需端口缺失、无权限或被占用"。热插拔后端口消失时，§11 说"保留配置并将 serial facet 置 FAILED"。但如果该端口是唯一的采集总线，`serial=FAILED` 是否意味着工作负载总体状态进入 FAILED？这是否会触发自动重启或回滚？** §8.2 的更新顺序在 `HEALTHY/FAILED → STOPPING → STOPPED` 中隐含了 FAILED 可触发停止，但 §12.1 又说只有 `process=FAILED` 才允许重启。建议明确：`serial=FAILED` 时的处置策略（等待人工？自动重试探测？标记 DEGRADED？） |
| T01-16 | **LOW** | **§12.2 首批错误码缺少 `CONFIG_VERSION_STALE`**（低于当前版本的配置发布请求）和 `WORKLOAD_NOT_FOUND`（查询不存在的 workloadId）。建议在实现中补充 |

## 六、综合改进建议

### 6.1 冻结前必须关闭（3 项 HIGH）

1. **T01-02**：明确 `payload_sha256` 的计算基准——建议对写入 PostgreSQL 前的 canonical JSON 字节计算 SHA-256，并在表中增加 `canonical_json_length` 字段辅助校验。读取时不依赖 jsonb 的序列化输出做哈希比对。
2. **T01-05**：在 WorkloadSpec 和 ConfigSnapshot 的 JSON Schema 中为每个字段显式标注类型约束：整数（`type: integer`）、十进制字符串（`type: string, pattern: "^[+-]?\\d+(\\.\\d+)?$"`）、枚举等。
3. **T01-17**：在 §15 中增加规则："collector 更新维护窗口由 `iot-device` 在创建发布单时自动写入 SPEC-004 停运策略表，窗口内的缺失只从应采集数中扣除，不重复惩罚完整率"。或明确替代方案。

### 6.2 实现阶段同步处理

4. T01-03/06：统一控制面和快照的 ID 类型策略（对外 siteCode，对内 bigint，映射在 API 层）。
5. T01-07：在任务 5 完成证据中增加"JVM 参数与容器 limit 一致性验证"。
6. T01-09：区分 Agent 确认超时和 collector 应用超时为两个独立配置。
7. T01-12：在任务 6 中排查并替换所有 Kafka 直接调用路径。
8. T01-15：明确 `serial=FAILED` 时不触发自动重启，进入人工介入队列。

## 八、复核评估与处置结果

### 8.1 总体判断

评审报告总体合理，T01-01～20 均指出了真实的可读性、契约或实施风险，已更新 [TD-001 1.0.1](../技术设计/电力运维云平台/TD-001-collector与NODE部署契约.md)。但以下两点不直接按原建议执行：

1. collector 发布不能“自动写入并批准”SPEC-004 停运策略，否则会把技术发布权限扩大为业务停运审批权限。修订方案为发布单只能引用已由独立流程批准的 `maintenanceWindowId`；无批准窗口时缺失正常计入完整率。
2. 资源压测和 Windows 资格不能在缺少证据时视为“冻结后任务”。它们可以不阻塞设计内容评审，但仍是 TD-001 从 `In Review` 转为 `Approved / Frozen` 的门禁，避免未验证参数进入开发和销售承诺。

### 8.2 逐项处置

| 评审项 | 处置 | TD-001 1.0.1 结果 |
|---|---|---|
| T01-01 | 采纳 | 明确逐点读取是性能/容量缺口，合并读取由 §9.2 覆盖；数据库耦合是站点运行阻断项 |
| T01-02 | 采纳并增强 | 增加 `payload_canonical`、`canonical_length_bytes`；哈希只基于写库前 canonical UTF-8 字节，jsonb 不参与重新哈希 |
| T01-03、T01-06 | 采纳 | 数据库使用 bigint；API/快照中的内部 ID 使用十进制字符串，同时返回/固化 `siteCode` 等业务标识并增加查询索引 |
| T01-04 | 采纳 | 定义 `collector-health/1.0` JSON 结构、必需 facet、状态枚举、时间和兼容规则 |
| T01-05 | 采纳 | 增加 WorkloadSpec/ConfigSnapshot 类型表：时间和计数为有界整数，十进制事实为受限字符串，object 禁止额外字段 |
| T01-07、T01-08 | 采纳 | 显式声明当前 512m JVM 与 384 MiB 候选冲突；三类超时均为压测候选，不构成生产默认值 |
| T01-09 | 采纳 | 拆分 Agent 接单超时与 collector 应用超时，分别从派发与 `agentAcceptedAt` 起算 |
| T01-10、T01-16 | 采纳 | 增加 `CONFIG_VERSION_STALE`、`CONFIG_VERSION_CONFLICT`、`WORKLOAD_NOT_FOUND` 等稳定错误码；回滚也使用更高新版本 |
| T01-11 | 采纳 | 心跳增加时钟偏差观测；超过 60 秒降级告警，超过五分钟拒绝变更，不允许平台远程改系统时间 |
| T01-12 | 采纳并按代码校正 | 当前 Poller 无直接 Kafka producer，但存在 `IotDeviceMessageService` 直发链；任务 6 替换整条路径并验证 collector 无 Kafka Bean |
| T01-13 | 采纳 | Windows JVM 参数来自安装包内签名、版本化 runtime policy；Agent 只能选策略 ID，不能拼接远程参数 |
| T01-14 | 采纳 | 未知同标签容器标记 `ORPHANED/QUARANTINED`，不自动停止/删除，但阻断串口争抢，需审计后接管或停止 |
| T01-15 | 采纳 | 必需串口丢失使总体 FAILED，但不重启进程/不回滚当前配置；原进程有界探测，相同硬件指纹恢复才自愈 |
| T01-17 | 部分采纳 | 只有关联的已批准窗口才扣减应采集槽；无批准、超窗、失败和回滚缺失正常计入，结果按审批版本可追溯重算 |
| T01-18 | 采纳 | 冻结 Trivy CycloneDX/漏洞扫描 + Cosign digest 签名，`iot-node` 与 Agent 双重验证 |
| T01-19 | 采纳并限定 | 增加 0 串口 smoke test；只允许 WAITING_CONFIG，不允许空发布快照回报 APPLIED |
| T01-20 | 采纳 | broker secret 通过版本文件原子轮换并重建 MQTT 连接，失败回退；不重启 JVM，数据继续进入 outbox |
| A06-01 旁支 | 边界确认 | inbox/时序清理归 TD-003 与 `TelemetryLifecycleManager`；不向普通 `TelemetryStore` 增加任意 delete |

### 8.3 评审数量勘误

报告在“主要亮点”“§2.8”“§3.1”和“§7”多处写“15 个 RTU 需求”，但 SPEC-003 1.4.0 实际包含 **RTU-001～RTU-018，共 18 项**。TD-001 §16 已逐项覆盖 18 项，本次复核按 18 项验证，不能以原报告的 15 项作为覆盖基线。

### 8.4 HIGH 问题关闭证据

| HIGH | 状态 | 关闭依据 |
|---|---|---|
| T01-02 canonical hash | 已关闭 | §4.1 固定 canonical 原文、字节长度、SHA-256 和 jsonb 非哈希语义 |
| T01-05 字段类型 | 已关闭 | §6.1 固定整数、十进制字符串、枚举、ID 与 additionalProperties 规则 |
| T01-17 维护窗口 | 已关闭 | §15 固定独立审批引用、范围校验、分母扣减、超窗计入和版本化重算 |

### 8.5 最终结论

TD-001 的设计缺口已完成文档层整改，评审报告提出的 3 项 HIGH 均已关闭，其余 MEDIUM/LOW 不再只是“实现时注意”，已转化为明确契约、错误码、任务和验收场景。TD-001 继续保持 **In Review**：尚需完成联合评审、Linux PTY 证据、资源压测以及 Windows 发布资格判断，达到 §19 门禁后才能标记 `Approved / Frozen`。在冻结前不得进入 collector 业务编码。
