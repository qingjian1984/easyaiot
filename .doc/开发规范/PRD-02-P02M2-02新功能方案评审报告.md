## 二、总体评价

### 2.1 突出优点

1. **切片化授权纪律是本项目至今执行最严格的一轮**。02（Conditional Freeze）→ 02A/02B（两个并行本地任务）→ 02C（不批准接入、只冻结画像）→ C0（唯一批准的下一步），每份文档都显式声明「不自动解锁下一阶段」，且 §6 明确禁止清单与验收记录的事实表述一致（真实 DB=0、DDL=0、transport=0 经 git 提交范围核查属实）。
2. **前轮评审处置的落地质量高**。上轮 12 项处置在代码/资产层的复核结果：
   - H-01 `ignore_generation`：V011:231 落列 + CHECK（IGNORED 时 ≥1）+ TD-006:81 与并发矩阵的 CAS 四条件表述完全一致——这是比上轮建议（比较 `ignored_from_status`）更强的方案，裁决记录中的「不采用弱方案」确实执行了。
   - M-03：`uq_alarm_rule_version_published` 部分唯一索引（V011:84）+ 中文注释明确「回滚先退役当前版本再事务内激活历史版本」——方案 a 完整落地。
   - M-02：`device.alarm.suppression-decided` 正式 Schema 已入 `iot-device-api/src/main/resources/events/`（7 个目录齐全），事件合同附件 0.1.2 的六事件清单同步。
3. **02B 事务编排实现与冻结合同的匹配度高**。抽查确认：`REQUIRES_NEW` + `requireActiveTransaction()` 双保险（[AlarmSourceTransactionService.java:42-44](../../DEVICE/iot-device/iot-device-biz/src/main/java/com/basiclab/iot/device/alarm/application/AlarmSourceTransactionService.java)）；Inbox 争抢失败强制重读（:79-83 `ALARM_INBOX_RACE_LOST_WITHOUT_ROW`）；RECOVERED 后同 cycle raise 先经状态机裁决再 quarantine（:108-114，正确防周期重开）；hash 碰撞比较完整 `cycle_identity` 而非仅 hash（`sameCycle` :204-209）；恢复事件无映射时 quarantine 而非静默丢弃（:157-158）。测试覆盖了「同 hash RECEIVED 崩溃恢复后重试而非误判 DUPLICATE」这类细粒度语义。
4. **02C 来源画像是全链最有决策价值的一份文档**。五类来源逐个给出「身份/时间语义 → 统一告警阻断项 → 裁决」，且 §6 身份决策表把 C1/C2 必须冻结的 `sourceId/cycleIdentity` 候选与缺口显式列表。「不能把算法模型输出静默等同于独立 AI 来源」「跨库不能宣称原子双写」两条裁决直接堵住了最容易犯的实现错误。
5. **02A runner 的防护层次正确**。五重前置（review flag + 审批标识 + 备份目录 + `td006_review_*` 临时库前缀 + `system_identifier` 核对）+ 禁用库名单 + catalog 签名重放校验，58 项假命令验收覆盖了全部拒绝路径；V011 不进默认 `APPLY_STEPS` 的静态断言已验证。

### 2.2 主要短板

1. **02B 实现对 V011 Inbox 模型做了一次未在冻结文档中裁决的简化**（N-01）：丢弃了候选 DDL 早期版本的 `RETRY_WAIT/lease` 设计，改为三态 `RECEIVED/PROCESSED/QUARANTINED`——方向可能是对的（数据库错误走事务回滚、不落 Inbox，transport 重试天然由 `RECEIVED` 承载），但该取舍没有在 02 评审记录 §3「事务与 ACK 冻结边界」中显式裁决，形成实现先行于文档。
2. **`sequence_no = rowVersion + 2` 的隐式耦合**（N-02）：动作序号从乐观锁版本推导，两个本应独立的合同（action log 单调序 vs 乐观锁）被绑定；且 `+2` 这种魔数依赖「INSERT 时 row_version=0、sequence 从 1 起」的初始对齐，一旦中间出现不更新 row_version 的动作（如纯升级 CAS 若不递增 row_version），序号会撞车。
3. **TD-006 主文档落后于资产**（N-03）：§4 表格仍写「保存 payload hash、状态、错误」的旧 Inbox 模型，§5.1 也未提三态；主文档 0.1.2 的其余部分（ignore_generation 等）已更新，唯独 Inbox 行滞后。

## 三、问题清单

### 3.1 NOTE（建议处置，不阻断 C0）

#### N-01｜02B Inbox 三态模型（RECEIVED/PROCESSED/QUARANTINED）与候选 DDL 演进方向的裁决缺口

- **事实**：[AlarmInboxArbiter.java](../../DEVICE/iot-device/iot-device-biz/src/main/java/com/basiclab/iot/device/alarm/infrastructure/event/AlarmInboxArbiter.java) 状态枚举仅三态；V011:473-483 的 `ck_alarm_source_inbox_state_time` 也只允许三态。而上一版候选 DDL（本轮评审输入中 467 行版）的 Inbox 有 `RETRY_WAIT/attempt_count/lease_owner/lease_until`。02 评审记录 §3 只冻结了「同事务处理/提交前不 ACK」，没有裁决「Inbox 是否承担数据库级可重试状态」这一取舍。
- **分析**：当前实现语义自洽——数据库/依赖异常 → 整个事务回滚（Inbox 行不落）→ transport 不 ACK → 重投后走 `RECEIVED` 重试；唯一持久化状态是终态裁决。这实际上是**正确的**设计（Inbox 状态机越简单越难错），但存在两个未闭环点：
  1. **重试风暴无界**：可重试错误没有 attempt 计数与退避记录（那些列被删了），退避完全依赖 transport 层；若 transport（未来 C1 的 Kafka/MQTT adapter）自身重试参数未配置上限，同一毒消息会无限循环 `RECEIVED→回滚`。02B 任务单 §4.9-10 只覆盖 Outbox 侧退避，Inbox 侧重试预算无对应 MUST。
  2. **QUARANTINED 不可再裁决**：`REJECT_UNKNOWN_MAJOR` 等隔离是一次性的；若上游修复后重发同 `messageId` 不同版本，仍命中 `REJECT_FINAL`。这是否是期望语义（隔离后必须人工/新消息 ID 处理）没有文档裁决。
- **建议**：在 02 评审记录或 TD-006 补一段「Inbox 三态裁决」：(a) 确认数据库级重试状态被有意移除，重试预算归属 transport 层并在 C1 任务单中冻结 transport 重试上限/毒消息 DLQ 阈值；(b) 确认 QUARANTINED 终态语义与人工处置入口。**C1 解锁前必须完成**，否则 adapter 实现者会面对合同空白自行发挥。

#### N-02｜`alarm_action_log.sequence_no` 由 `rowVersion + 2` 推导的隐式耦合

- **事实**：[AlarmSourceTransactionService.java:149,178](../../DEVICE/iot-device/iot-device-biz/src/main/java/com/basiclab/iot/device/alarm/application/AlarmSourceTransactionService.java) 对非首次 raise/recover 写 `alarm.rowVersion() + 2` 作为 sequence_no；首次创建写常量 1。
- **分析**：V011 的 `(tenant_id, alarm_id, sequence_no)` UNIQUE 依赖 sequence 单调。当前两条路径（CAS 更新使 row_version+1，动作序号取快照 rowVersion+2）在「每次动作都恰好使 row_version+1」时成立，但：
  1. 这是**巧合对齐而非合同**——没有任何约束保证未来动作（升级 CAS、忽略、人工动作 API）都递增 row_version；升级按矩阵 §2「escalationLevel CAS 递增」若同时递增 row_version，则 sequence=rowVersion+2 的推导在并发交错下可能重复或跳号。重复即 UNIQUE 冲突 → 事务回滚 → 消息重试 → 永久卡死（毒消息）。
  2. `+2` 依赖初始 `row_version=0 ↔ sequence=1` 的映射，该初始条件未写入任何冻结文档。
- **建议**：短期在 02B R 轮补一条注释级说明并把 sequence 改为「读取当前最大 sequence_no + 1」或独立 ID 发号器（同事务内已有 `FOR UPDATE` 语义的行锁保护，无额外成本）；长期在 TD-006 附件一冻结「sequence 与 row_version 无推导关系」。属并发正确性隐患，**建议在 02A 临时库合同（真实并发集成测试）执行前修复**，否则并发用例可能首次暴露即为生产级缺陷。

#### N-03｜TD-006 §4/§5.1 的 Inbox 模型表述未同步三态简化

- **事实**：TD-006 0.1.2:54 仍写「`alarm_source_inbox` …保存 payload hash、状态、错误」；§5.1 步骤 2 已更新为 envelopeHash/QUARANTINED 表述，但表级描述未更新；且 467 行旧版 DDL 的 Inbox 列（RETRY_WAIT 等）虽已从 596 行新版移除，主文档没有记录这次模型变更的裁决。
- **建议**：TD-006 0.1.3 更新 §4 表格，并在修订记录补「Inbox 三态裁决」条目（与 N-01 同一动作关闭）。

#### N-04｜02C0 完成定义与 02C §5 C1 门禁的「C0 通过」衔接缺口

- **事实**：02C §5 中 C1 的解锁门禁最后一项是「C0 通过」；但 02C0 任务单 §6 完成定义只写了「不自动解锁 C1」，没有要求 C0 验收记录显式输出「C1 门禁表逐项现状」。
- **分析**：C1 门禁其余各项（M1 identity/route 稳定、tenant/site 权威、阈值 cycle 规则、原子/补偿 ADR）分散在 M1 与 02C 文档中；若 C0 验收不产出一张 C1 门禁 checklist，下一轮 C1 评审需重新人工拼装，且「哪项已具备、哪项仍缺」无单一事实源——这正是进度文档类项目最常见的续作断层。
- **建议**：02C0 执行时在验收记录中附一张 C1 门禁现状表（引用 02C §5 第一行逐项给 CLOSED/OPEN 状态）；或把该要求补进 02C0 任务单 §6。

#### N-05｜防漂移脚本置于 `WEB/scripts/` 的归属疑点

- **事实**：02C0 允许边界把校验脚本放在 `WEB/scripts/verify-alarm-source-migration-boundaries.mjs` 并修改 `WEB/package.json`——与 02B 的 `verify-alarm-event-contracts.mjs` 同一先例。
- **分析**：脚本校验的是 `.doc`/`DEVICE`/`AI/`/`RUNTIME` 的告警源边界，与 WEB 前端无语义关系；放 WEB 仅为复用 Node 环境。风险：(a) 未来有人重构 WEB 构建脚本时可能误删；(b) 校验「仓库根可运行」的要求（任务单 §4.11）在 WEB 外执行时依赖 `node WEB/scripts/...` 的相对路径解析，Windows/CI 路径分隔符需测试覆盖。
- **建议**：可接受现状（先例一致），但脚本头部注释应声明「此脚本属 PRD-02 迁移门禁，与 WEB 构建无关，移动需评审」；若后续脚本数量增长，考虑收敛到 `.scripts/alarm-guards/`。
