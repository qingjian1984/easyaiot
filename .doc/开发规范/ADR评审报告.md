## 二、总体评价

11 份 ADR 整体质量高，决策过程基于代码实证分析，理由充分，被否决方案均有记录。与《平台功能计划》和《开发宪法》的合规性好，所有 ADR 均显式声明了 mini 排除和 standard/full 单一实现原则。

主要亮点：

1. **决策链完整**——从 RTU Poller 归属（ADR-001）→ 边缘队列（ADR-002）→ ACK 机制（ADR-003）→ 时序存储（ADR-006）→ collector 打包（ADR-007）形成 M1 数据链路的完整架构决策闭环。
2. **安全设计到位**——二维码采用 CSPRNG + 哈希存储 + 统一错误响应（ADR-008），Capability Manifest 要求后端门禁而非前端隐藏（ADR-011）。
3. **回滚方案齐备**——每份 ADR 都有明确的回滚策略，且多数支持版本化回退。
4. **整改闭环诚实**——M1 第一批评审报告（ADR-001～004）记录了原始问题和整改关闭证据，包括 ADR-005 从 Accepted 变为 Superseded 的演变过程。

主要短板：

1. **ADR-010（告警迁移）和 ADR-011（Capability Manifest）缺少量化约束**——告警迁移的对账窗口、Capability 编码全集和 CI 校验脚本的技术规范尚未锁定。
2. **部分 ADR 之间的交叉引用不完整**——ADR-002 和 ADR-003 对 `telemetry_gap` 的写入职责分工需要显式对齐。
3. **ADR-007 的资源预算与 ADR-006 的准入基线之间缺少联合校验**——collector 384 MiB 内存限制是否能支撑 ADR-006 的 100 条/秒持续写入未被验证。

## 三、各 ADR 评审

### 3.1 ADR-001：RTU Poller 运行位置

#### 优点

- 最大化复用现有 Java 协议实现，避免 EDGE/SINK 双栈漂移。
- NODE 负责工作负载生命周期，不承载轮询业务，职责边界清晰。
- 明确 EDGE 延至 M2 评估，且必须通过新 ADR 并证明不形成双栈。
- 同一物理串口同一时刻只能由一个 collector 实例持有。

#### 发现的问题

| 编号 | 严重度 | 问题 |
|---|---|---|
| A01-01 | LOW | 中心 `iot-sink` 在"物理串口直接连接中心主机时才可作为 Poller"——此场景在生产中极少出现，建议标注为受控例外并记录启用条件 |

### 3.2 ADR-002：边缘持久队列

#### 优点

- SQLite WAL 无需独立服务，具备事务、唯一约束和崩溃恢复。
- 状态机清晰：`PENDING → IN_FLIGHT → ACKED / DEAD_LETTER`。
- 死信与 `telemetry_gap` 记录在同一事务中写入，保证缺口不丢失。
- ACKED 批量清理（10 秒/1000 条）避免逐条 vacuum。
- 导出工具使用稳定 JSONL 格式，保留迁移路径。

#### 发现的问题

| 编号 | 严重度 | 问题 |
|---|---|---|
| A02-01 | **MEDIUM** | **`IN_FLIGHT` 超时恢复阈值（默认 5 分钟）与 ADR-003 ACK 超时的关系未显式对齐**。ADR-002 说"不得小于一次网络请求超时"，但 ADR-003 的退避重试策略可能使单次请求耗时超过 5 分钟（极端退避场景）。建议明确：当 ADR-003 退避间隔超过 ADR-002 IN_FLIGHT 阈值时，以哪个为准 |
| A02-02 | LOW | `telemetry_gap` 写入失败时"本条不得完成死信状态迁移"——此时数据处于什么状态？是否重新回到 PENDING 等待下次重试？ |

### 3.3 ADR-003：遥测 ACK 机制

#### 优点

- 两级确认设计精确：MQTT QoS 1 保证传输，应用 ACK 保证业务持久化。
- ACK 语义为 `ACCEPTED_DURABLE`（inbox 已提交），不是"所有派生视图已完成"。
- 两层幂等：PostgreSQL inbox 唯一约束 + 投影状态机确定性样本键。
- 死信保留完整 inbox 载荷，支持人工按范围重新投影。
- 对账补偿任务每小时扫描"已 ACK 但未 COMPLETED"记录。
- 诚实标注现有代码缺陷：`needReply=false`、TDengine 异常被吞掉。

#### 发现的问题

| 编号 | 严重度 | 问题 |
|---|---|---|
| A03-01 | **MEDIUM** | **投影死信告警的"高优先级"未定义级别**。是信息、一般、重要还是紧急？不同级别触发不同的通知和升级策略。建议在 TD-003 中明确 |
| A03-02 | **MEDIUM** | **历史查询 API "存在投影积压时不得把'暂未可查'表述为'原始数据丢失'"**——具体的返回格式和状态码未定义。建议定义标准的"投影滞后"响应结构（如 HTTP 206 + `projectionLag` 字段） |
| A03-03 | LOW | 回滚方案中"新节点在未协商到应用 ACK 时保留 outbox 到容量策略触发"——若中心长期不支持 ACK，outbox 会增长到硬上限并触发数据淘汰。建议补充长期不协商时的运维处置流程 |

### 3.4 ADR-004：历史设备编码兼容策略

#### 优点

- "存量原值保留、新增严格校验、可选别名映射"策略务实，避免一次性破坏既有链路。
- 明确禁止对存量值执行 trim、小写化、数值化或重新生成。
- 读写规则清晰：精确查询优先，别名只在声明支持时启用。
- `Long deviceIdentification` VO 修复有明确截止门禁（TD-004 评审前）。
- 回归测试覆盖全面：认证、MQTT、Redis、双 TelemetryStore 适配器、设备影子、告警、工单和二维码。

#### 发现的问题

| 编号 | 严重度 | 问题 |
|---|---|---|
| A04-01 | LOW | "删除设备前必须检查 alias 和历史引用"——但检查的具体实现（API 拦截？定时扫描？删除前触发校验任务？）未说明 |

### 3.5 ADR-005：mini 采集通信方案

#### 状态说明

已标记 `Superseded`。《平台功能计划》1.4.0 与《开发宪法》1.4.0 明确电力运维平台不支持 mini，本 ADR 不再构成开发门禁。文档保留历史决策过程供追溯。

#### 评审结论

无需评审。当前有效决策为 ADR-001（standard/full collector）+ ADR-006（standard/full 时序存储）。

### 3.6 ADR-006：standard/full 时序存储抽象与迁移方案

#### 优点

- `TelemetryStore` 接口定义清晰，5 个方法覆盖写入、最新值查询、原始查询、聚合和水位。
- `appendBatch` 按 `(tenantId, messageId)` 幂等，部分失败返回逐条结果。
- PostgreSQL 与 TDengine 适配器必须通过同一合同测试。
- standard 准入基线量化：500 万条/天、100 条/秒持续、500 条/秒峰值、30 天保留。
- standard→full 迁移方案完整：双写→回灌→对账→切换→观察期。
- 明确 standard 不提供 TDengine 例外配置，超过准入上限必须升级 full。

#### 发现的问题

| 编号 | 严重度 | 问题 |
|---|---|---|
| A06-01 | **HIGH** | **`TelemetryStore` 接口缺少删除/清理操作**。inbox 投影 COMPLETED 后需要清理载荷（默认保留 7 天），分区过期后需要删除旧分区。接口中没有 `delete` 或 `purge` 方法。若清理逻辑直接操作 JDBC/TDengine 客户端，将违反"业务层不依赖具体后端"的原则 |
| A06-02 | **MEDIUM** | **standard 准入基线的"500 万条/天"推导依据未说明**。该值是经验估计还是基于典型站点规模计算？若一个 standard 中心接入 200 个设备、每设备 50 个测点、5 秒周期，日样本量为 `200 × 50 × 86400/5 = 1.728 亿条`，远超 500 万。建议说明该值适用的典型场景和计算公式 |
| A06-03 | **MEDIUM** | **迁移步骤 3"按月分区和原 messageId 回灌历史"的并发策略未定义**。回灌是否影响在线写入？是否需要限速？回灌过程中 standard 的 PostgreSQL 继续接收新数据，如何保证回灌水位与在线写入不冲突？ |
| A06-04 | LOW | "投影 COMPLETED 后 inbox 载荷默认保留 7 天用于对账"——7 天是硬编码还是可配置？若对账任务异常延迟，7 天内未处理完怎么办？ |

### 3.7 ADR-007：collector 打包与 NODE 管理契约

#### 优点

- 同一 iot-sink 构建产物 + 独立 Spring Profile，避免代码分叉。
- NODE 只接受结构化白名单字段生成 Compose 配置，不接受任意 shell 命令。
- 生命周期状态机完整：`REQUESTED → PULLING → STARTING → HEALTHY`。
- 新版本在健康窗口内失败时自动恢复上一镜像和配置。
- SQLite 数据卷不随容器删除，保护未 ACK 数据。
- NODE 重启后从容器标签和本地状态文件恢复工作负载清单。

#### 发现的问题

| 编号 | 严重度 | 问题 |
|---|---|---|
| A07-01 | **HIGH** | **内存限制 384 MiB 对 Java + SQLite + MQTT client 可能偏紧**。JVM 基础内存占用（C heap + metaspace + thread stacks）通常在 150-250 MiB，留给业务堆的空间有限。若 collector 需要缓存大量点位数据和 SQLite WAL 缓冲，可能频繁触发 GC 甚至 OOM。建议：① 标注该值为"初始默认值，以 TD-001 压测结果为准"；② 给出压测时的内存分布监控要求 |
| A07-02 | **MEDIUM** | **单端口更新策略（先停旧→释放串口→启新）在更新失败时的数据缺口处理未说明**。若新实例启动失败、旧实例已停止，串口在回滚期间无数据采集。这个缺口是否记录到 `telemetry_gap`？回滚期间的数据丢失是否影响数据完整率统计？ |
| A07-03 | **MEDIUM** | **Windows 非容器场景属于"受控例外"但约束不足**。只说"必须由 NODE 以固定 Java 命令模板管理服务，但必须保持相同规格、状态和日志契约"。建议明确：Windows 场景下串口枚举、SQLite 路径、日志格式和健康检查是否与 Linux 容器完全一致？ |
| A07-04 | LOW | 健康检查"区分进程存活、配置已应用、串口可访问和中心连接"——四项检查的失败是否分级处理？中心离线不得判为死亡（已明确），但串口不可访问是否应判为 FAILED？ |

### 3.8 ADR-008：二维码安全解析方案

#### 优点

- CSPRNG 128 bit 随机熵，不可枚举。
- 数据库只保存短码哈希，明文只在签发响应中返回一次。
- 不存在、过期、撤销、无权限统一返回同一外部错误，防枚举。
- 每次解析记录审计日志，日志不记录完整短码。
- 已撤销短码永不复用。
- 协议按路径版本路由，支持向前演进。

#### 发现的问题

| 编号 | 严重度 | 问题 |
|---|---|---|
| A08-01 | **MEDIUM** | **解析接口限流阈值未定义**。"按主体和来源限流，异常扫描触发安全告警"——具体阈值（如每用户每分钟 60 次）未给出。建议至少在 ADR 中给出默认参考值，TD 阶段可调整 |
| A08-02 | **MEDIUM** | **"数据库只保存短码哈希"对批量运维操作的影响未说明**。租户迁移、批量撤销或短码审计查询需要遍历哈希表匹配。若使用确定性哈希（如 SHA-256），可通过重新计算查找；但若加盐哈希，批量操作将无法高效执行。建议明确哈希方式和对运维操作的影响 |
| A08-03 | LOW | M1 不提供离线解析——若现场无网络，巡检人员无法通过扫码查看设备信息。建议确认 APP 离线巡检场景中二维码的角色（是否必须在扫码前联网鉴权？） |

### 3.9 ADR-009：物模型模板版本策略

#### 优点

- SemVer 变更级别定义精确，MAJOR/MINOR/PATCH 触发条件清晰。
- 新增 `required=true` 属性视为 MAJOR，保护现有产品实例。
- 厂家模板记录标准模板精确版本（不使用浮动范围），标准升级不自动改变厂家模板。
- 内容哈希确保同版本不可被篡改。
- 回滚恢复精确版本和绑定快照，已产生的数据按 configVersion 保持可解释。

#### 发现的问题

| 编号 | 严重度 | 问题 |
|---|---|---|
| A09-01 | **MEDIUM** | **"同一模板版本内容哈希不同必须拒绝发布"——哈希算法未指定**。SHA-256？SHA-512？不同算法产生的哈希不可比较。建议明确算法并在 schema 中记录算法版本 |
| A09-02 | **MEDIUM** | **"不同租户派生模板拥有独立版本线"的隔离机制未说明**。租户 A 的厂家模板和租户 B 的厂家模板是否共享同一个 `templateId`？如果是，版本线如何分离？如果不是，大量租户各自维护版本线是否会造成管理负担？ |
| A09-03 | LOW | 预发布标签（如 `-rc1`、`-beta`）"MAY 用于草稿/试点"但生产产品只允许绑定正式版本——预发布版本的数据清理策略未说明 |

### 3.10 ADR-010：统一告警模型与存量迁移

#### 优点

- 唯一告警主记录 `alarm_record` 作为状态、确认、处置、关闭和审计的唯一事实源。
- 状态机完整：ACTIVE → ACKNOWLEDGED → PROCESSING → RECOVERED → CLOSED，含 ESCALATED、IGNORED（有截止时间）和 FALSE_ALARM（不可逆终态）。
- 各来源（阈值/VIDEO/AI/设备事件）通过版本化事件进入统一告警服务，来源表只保留证据。
- 迁移 5 步骤：扩展新表→存量映射→双写对账→切换查询→停止旧写入。
- 回滚只切换读路径，不删除新主记录。

#### 发现的问题

| 编号 | 严重度 | 问题 |
|---|---|---|
| A10-01 | **HIGH** | **`IGNORED` 到期恢复的目标状态存在歧义**。状态图显示 `IGNORED → ACTIVE/ACKNOWLEDGED`，但恢复到哪个状态取决于忽略前的状态。若忽略前是 ACTIVE，恢复到 ACTIVE；若忽略前是 ACKNOWLEDGED，恢复到 ACKNOWLEDGED——这个"忽略前状态"是否作为字段保存在 `alarm_record` 中？若否，到期后如何确定恢复目标？ |
| A10-02 | **HIGH** | **存量迁移的映射规则未定义**。OPEN/CLEARED 和 VIDEO Alert 如何映射到新的 `alarmId`？一个 VIDEO Alert 对应一个 alarmId？还是一个视频事件序列对应一个告警周期？迁移任务"可重跑"但对账标准（数量、等级、来源证据的匹配精度）未说明 |
| A10-03 | **MEDIUM** | **"同一来源重复事件只生成一个逻辑告警周期"的判定规则未定义**。同一设备、同一测点、同一规则在恢复后再次发生——"创建新周期或按规则重开，策略必须版本化"。但"同一"的判定维度（设备+测点+规则？还是设备+规则？还是来源 ID？）未明确 |
| A10-04 | LOW | "紧急等级默认禁止忽略"——是否允许通过配置放开？若允许，需要额外的审批流程吗？ |

### 3.11 ADR-011：Capability Manifest 规范

#### 优点

- JSON Schema 校验 + CI 门禁 + 运行时 API 三层保障。
- `enabled(standard) ⊂ enabled(full)` 由 CI 自动验证。
- 后端通过统一 `CapabilityService` 实施门禁，前端只用 API 结果控制展示。
- 灰度只能在已部署能力上收窄，不得绕过安全门禁。
- manifest、权限点和开放 API 生成一致性报告，不一致阻断合并。

#### 发现的问题

| 编号 | 严重度 | 问题 |
|---|---|---|
| A11-01 | **HIGH** | **capability 编码全集未定义**。ADR 只给出示例编码 `power.device.monitor` 和 `power.scada.editor`，但 PRD 覆盖的功能域有 6 个（站点设备、监控告警、可视化、运维、能源、报表）。每个域需要多少个 capability 编码？编码命名空间如何组织？这是后续所有 Spec 和 TD 的基础依赖，建议在 ADR 中至少给出编码全集的框架（如按域分组），详细清单在 TD 阶段冻结 |
| A11-02 | **MEDIUM** | **"扫描禁止散落的档位业务判断"的实现方式未说明**。是通过 SonarQube 规则？自定义 grep 脚本？CI 阶段静态分析？建议明确检测工具和规则定义方式 |

## 十、复核评估与处置结果

### 10.1 评估原则

- 影响模块职责、事实归属、状态机、跨档位一致性、安全边界、迁移/回滚语义的问题，必须修改 ADR。
- 线程数、内存 limit、限流数值、观察窗口等依赖负载或安全基线的参数，只在 ADR 固定决策方法和发布门禁，由 TD 用证据冻结数值。
- API 必须表达投影滞后，但不采纳“使用 HTTP 206”的示例；206 是 Range 请求的部分内容语义，不适合普通业务投影延迟。
- `TelemetryStore` 不增加供普通业务调用的任意删除方法；清理由独立受控生命周期契约承担，以免扩大误删事实数据的风险。

### 10.2 逐项处置

| 处置 | 评审项 | 结果 |
|---|---|---|
| 已修改 ADR | A01-01、A02-01、A02-02、A03-01、A03-03、A04-01 | 补充中心 Poller 例外审批、单次发送/退避边界、gap 事务回滚、死信等级、ACK 不兼容处置和删除同步校验 |
| 已修改 ADR | A06-01～A06-04 | 增加 `TelemetryLifecycleManager` 管理契约、容量公式与适用样例、快照水位+限速回灌、可配置并受对账水位保护的 inbox 保留策略 |
| 已修改 ADR | A07-02～A07-04 | 明确升级缺口统计、Windows 同契约适配、四类健康 facet 及聚合规则 |
| 已修改 ADR | A08-02、A08-03、A09-01～A09-03 | 冻结短码 HMAC 与轮换、离线任务包边界、模板 canonical JSON/SHA-256、租户版本线和预发布清理 |

### 10.3 数量勘误

第七章原文写“LOW（7 项）”，但表内实际列出 A01-01、A02-02、A03-03、A04-01、A06-04、A07-04、A08-03、A09-03、A10-04、A11-04，共 **10 项**。本次按表内 10 项全部评估，不因标题计数错误遗漏。

### 10.4 修订后的门禁

1. TD-001 必须联合验证 collector 资源预算与 ADR-006 standard 准入基线；未形成内存分布、GC、SQLite WAL、持续/峰值吞吐和 24 小时断网补传证据，不得冻结生产 limit。
2. 安全 TD 必须给出二维码按主体/租户/来源的限流默认值、告警阈值和误伤验证结果。
3. API TD 必须冻结投影滞后响应字段、业务错误码和 HTTP 状态码，并覆盖积压、死信、恢复后的合同测试。
4. 告警迁移 TD 必须冻结双写观察窗口和批次参数，但不得改变 ADR-010 已明确的存量映射、幂等键和零缺失/零重复对账门禁。
5. capability Spec/TD 可以细分编码，但必须落在 ADR-011 的稳定业务域内，并同步更新 schema、standard/full manifest、后端门禁、前端声明和 CI 测试。

### 10.5 最终结论

评审报告总体合理，识别出的职责、状态和跨 ADR 一致性问题应当修改，现已完成。两处建议不按原建议直接实施：不把清理能力暴露为普通 `TelemetryStore.delete`，也不使用 HTTP 206 表示投影滞后。ADR-001～004、006～011 继续保持 **Accepted**，ADR-005 继续保持 **Superseded**；剩余事项是有明确验收标准的 TD 参数冻结，不再是未决架构决策。
