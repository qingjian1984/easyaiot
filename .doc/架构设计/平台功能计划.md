# EasyAIoT 电力运维云平台功能计划

> 文档版本：1.5.0
> 编制日期：2026-08-12
> 需求来源：`电力运维云平台价值.pdf`  
> 适用基线：EasyAIoT 当前仓库  
> 结论口径：基于代码与架构文档静态核对；“满足”表示平台已有可复用实现，不代表具体现场设备、网关和通知渠道已经完成联调。

## 1. 建设目标

在不破坏 EasyAIoT 云边端一体化架构的前提下，将现有通用 AIoT 平台扩展为覆盖以下业务闭环的电力运维云平台：

1. 电气设备与配电房环境的实时监控。
2. 异常检测、告警通知、事故追忆和安全控制。
3. 站点看板、电力一次图、历史曲线和业务报表。
4. 表计采集、能耗统计、需量、电费和电能质量分析。
5. 设备档案、巡检、缺陷、工单、人员和绩效闭环。

目标产品不是重新建设一套独立系统，而是在现有 DEVICE、WEB、VISUALIZE、APP、NODE、RUNTIME、VIDEO 和消息体系之上新增电力领域能力。`EDGE/` 已退役，`TASK/` 已迁移为 `RUNTIME/`；电力采集、边缘推理和媒体归档边界以 [ADR-016](../架构决策/电力运维云平台/ADR-016-EDGE退役与RUNTIME边缘执行边界.md) 为准。

### 1.1 部署档位边界

电力运维云平台功能仅面向 `standard` 和 `full`，`mini` 不在本计划的建设、交付和验收范围内。

| 档位 | 电力运维平台定位 | 功能边界 |
|---|---|---|
| `mini` | 不支持 | 不部署或启用电力物模型模板、RS485 电力采集、遥测质量与补传、告警闭环、SCADA、能源管理、运维管理、报表和电力移动端功能 |
| `standard` | 核心运维版 | 面向单站点或园区，提供监测、告警、安全控制、基础能源和基础运维闭环 |
| `full` | 完整版 | 支持本计划全部电力监控、SCADA、视频联动、能源、运维和报表能力 |

- 电力功能不得为了适配 `mini` 新增轻量替代实现、双协议、双数据模型或 mini 专用业务分支。
- `mini` 安装、升级和运行时必须保持电力能力关闭；菜单、任务和服务不得以启动异常的方式暴露不可用能力。
- 从 `mini` 升级为 `standard/full` 后，才可按正式迁移流程启用电力模块；降级到 `mini` 前必须导出或迁移电力业务数据。
- 本边界替代此前“mini 支持电力采集/缓存/时序”的假设；相关 Spec、ADR 和评审记录在进入 Technical Design 前必须按本边界修订，不能继续以旧结论拆分 mini 开发任务。

### 1.2 standard 与 full 功能矩阵

`full` 包含 `standard` 的全部能力。档位差异不得通过降低安全、权限、审计或数据完整性要求实现。

| 功能域 | `standard` 核心运维版 | `full` 完整版 |
|---|---|---|
| 适用场景 | 单站点、配电房或园区级日常运维 | 多站点、集团级集中监控与经营分析 |
| 站点与设备 | 站点、空间、回路、设备、测点、物模型模板和二维码 | standard 全部能力 + 多站点统一视图、跨站点权限与集中配置治理 |
| 协议采集 | MQTT、TCP、Modbus TCP/RTU、OPC UA 等核心接入；SQLite 断点缓存和应用 ACK | standard 全部能力 + 更大规模并发、集中节点编排和高级协议接入扩展 |
| 时序存储 | PostgreSQL 分区时序表，限制点数、采样频率、保留期和查询跨度 | TDengine 高频时序、长期保留、大规模聚合与多测点分析 |
| 实时监控 | WEB 站点设备树、实时值、基础趋势和设备状态 | standard 全部能力 + 多站点指挥中心、综合态势与大屏发布 |
| 告警 | 阈值、持续时间、迟滞、恢复、确认、关闭、值班通知和基础升级 | standard 全部能力 + 复合规则、告警抑制、维护模式、跨站升级和集中策略治理 |
| 安全遥控 | 可选启用；一旦启用，必须具备权限、二次确认、操作票、双人复核、联锁、超时、回执和完整审计 | standard 全部安全要求 + 集中审批、跨站操作票治理和控制策略统管 |
| 视频联动 | 实时视频、基础抓拍及告警关联 | standard 全部能力 + 事故前后录像冻结、预置位联动、证据归档和事故追忆 |
| 可视化/SCADA | WEB 内置站点总览和基础一次图查看；不包含 VISUALIZE 编辑器与 FUXA | VISUALIZE 大屏编辑发布、FUXA Web SCADA、完整一次图图元和交互组态 |
| 能源管理 | 计量点、自动抄表、冻结值、基础分类分项和用量统计 | standard 全部能力 + 最大需量、尖峰平谷、电费、目标偏差、同比环比和电能质量 |
| 运维管理 | 设备档案、二维码、基础巡检、缺陷和简化工单闭环 | standard 全部能力 + 完整工单 SLA、转派/暂停/验收、人员轨迹、评价、备件和绩效分析 |
| 移动端 | 告警查看确认、扫码档案、基础巡检和工单处理 | standard 全部能力 + 完整离线作业、轨迹、签名、多媒体证据和管理审批 |
| 报表 | 预置运行/告警/用量报表和手工导出 | 自定义报表、定时生成、综合月报、多站点经营分析和管理驾驶舱 |
| AI 与诊断 | 基础设备状态和规则诊断；按资源启用单点算法 | 健康评分、预测诊断、视觉联动和模型服务的完整集成 |
| 可用性与规模 | 单实例或基础冗余，资源上限通过配置发布门禁控制 | 集群化中间件、水平扩展、长周期存储和企业级备份恢复 |

### 1.3 部署实现约束

- `standard` 电力版目标部署必须包含 `iot-device`、`iot-sink`、电力 API 所需控制面、PostgreSQL、Redis 和 EMQX；不得沿用缺少 `iot-device` 的现有 standard 裁剪结果直接宣称支持电力平台。
- `standard` 默认不部署 TDengine、`iot-visualize`、VISUALIZE 编辑器和 FUXA；对应 full 专属入口必须隐藏且 API 返回能力不可用。
- `full` 启用 TDengine、可视化/SCADA 及完整领域模块；重型能力仍须支持独立开关和资源预算。
- 安装脚本、能力清单、菜单、许可证和前端路由必须由同一部署能力描述驱动，禁止各自维护互相冲突的档位判断。
- 功能规模上限、数据保留期和并发预算在 Technical Design 与容量测试后冻结；未冻结前不得用未经验证的数量作为销售承诺。

### 1.4 standard/full 单一实现原则

`standard` 与 `full` 是同一产品的能力组合，不是两套独立产品代码。`full` 必须复用 standard 的全部核心实现，只增加或启用高级能力。

```mermaid
flowchart LR
  CORE["共享核心实现\n采集/设备/监控/告警/安全/基础运维"]
  CORE --> STANDARD["standard\n核心能力 + 标准配额"]
  CORE --> FULL["full\n核心能力 + 更高配额"]
  ADV["full 可选高级模块\nSCADA/高级能源/事故追忆/经营分析"] --> FULL
```

- 禁止分别创建 `standard-*` 与 `full-*` 两套同语义 Controller、Service、页面、数据库表、消息 Topic 或设备协议实现。
- 两个档位共有的功能必须使用相同 API、DTO、权限点、状态机、事件契约、数据模型和测试基线。
- 档位差异必须由统一 capability manifest 表达，至少包含能力编码、是否启用、配额、依赖和不可用原因；后端、前端、安装脚本和许可证读取同一来源，具体遵循 [ADR-011](../架构决策/电力运维云平台/ADR-011-Capability-Manifest规范.md)。
- full 高级功能应作为独立领域模块或共享核心上的扩展策略实现，不得复制后再修改 standard 代码。
- 数据规模差异通过存储适配器、资源配置、分区、保留期和集群部署处理；不得让业务层维护 PostgreSQL 版与 TDengine 版两套业务逻辑。
- standard 升级 full 只允许启用高级模块、提高配额和执行向前兼容迁移；不得替换核心设备身份、API、Topic 或历史数据。
- full 降级 standard 必须先检查 full 专属数据和任务，执行停用/导出流程；共享核心数据不得重复迁移或重建。
- 测试必须证明 `Capabilities(standard) ⊂ Capabilities(full)`，并对全部共享能力运行同一套合同测试。

## 2. 总体判断

当前系统已具备电力平台约 60%～70% 的通用技术底座：

- 设备、产品与物模型。
- MQTT、Modbus、OPC UA 等设备接入基础。
- TDengine 时序数据。
- 属性阈值、告警策略、健康评分和预测诊断。
- 物模型服务调用、属性下发和设备操作日志。
- 视频接入、实时查看、抓拍与录像回放。
- 消息模板和通知配置。
- 低代码大屏与 FUXA SCADA/HMI。
- WEB 管理端和 APP 基础框架。

主要缺口集中在两个领域：

- **能源管理域**：表计、回路、抄表、能源组织、需量、尖峰平谷、电费和电能质量。
- **运维管理域**：档案、二维码、巡检、缺陷、工单、人员轨迹、评价和月报。

### 2.1 电力术语

| 术语 | 本计划定义 | 平台通用模型映射 |
|---|---|---|
| 遥测 | 连续或周期数值，如电压、电流、功率、温度 | 物模型只读/可读属性上报 |
| 遥信 | 离散状态或事件，如开关位、保护动作、通信状态 | 枚举/布尔属性或设备事件 |
| 遥控 | 平台向设备发出的控制操作，如分闸、合闸、复归 | 高风险物模型服务或受控属性下发 |
| 遥调 | 平台下发连续设定值，如阈值、目标功率 | 受控可写属性/服务 |
| 冻结值 | 在计划时间点形成、用于核算且不可原地覆盖的计量读数 | `ReadingFreeze` 与修正记录 |

## 4. 功能对比与建设分类

### 4.1 已满足或基本满足的功能

以下功能可直接复用现有平台，主要工作是配置电力物模型、制作行业模板和完成现场联调。

| 功能 | 当前基础 | 后续工作 | 目标模块 |
|---|---|---|---|
| 产品与设备管理 | 产品、设备、子设备、拓扑、在线状态 | 建立高压柜、变压器、低压柜、环境传感器等产品模板 | `iot-device`、WEB |
| 通用遥测采集 | MQTT、Modbus、OPC UA、物模型属性上报 | 对接现场网关并统一电力测点编码 | `iot-device`、站点 `iot-sink collector` |
| 时序数据存储 | standard 固定使用 PostgreSQL 分区时序表；full 使用 TDengine | 按 ADR-006 统一接口、准入配额、质量码、保留策略和升级迁移 | `iot-sink`、`iot-tdengine` |
| 历史运行曲线 | 设备属性历史查询与 ECharts 曲线 | 增加多测点对比和常用时间范围 | WEB |
| 属性阈值告警 | 阈值、等级、策略、未恢复告警 | 提供电力默认阈值模板和迟滞/持续时间规则 | `iot-device`、WEB |
| 设备健康评分 | 已有设备健康评分与预测诊断 | 增加电力设备评分因子 | `iot-device` |
| 远程设备服务调用 | 物模型属性设置、服务调用、操作日志 | 对接分合闸等具体服务模型 | `iot-device`、WEB |
| 视频实时查看 | RTSP、GB28181、SRS/ZLMediaKit | 配电房摄像头绑定站点和设备 | VIDEO、WEB、APP |
| 抓拍和录像回放 | 已有抓拍、录像、存储空间和回放 | 告警事件与对应录像片段关联 | VIDEO、`iot-sink` |
| 可视化大屏 | 大屏项目、模板、数据源、发布 | 制作电力站点模板 | `iot-visualize`、VISUALIZE |
| Web SCADA | 已集成 FUXA SCADA/HMI | 制作电力一次图图元和点位绑定规范 | `iot-visualize`、FUXA |
| 用户、角色和权限 | 用户、角色、菜单、数据权限、多租户 | 增加电力运维岗位和操作权限点 | `iot-system` |
| 文件存储 | 文件服务和 MinIO | 用于图纸、手册和试验报告 | `iot-file` |

### 4.2 需要修改和增强的功能

这些能力已有基础，但现有语义、交互或安全性不足以直接满足电力业务。

| 功能 | 现状问题 | 修改计划 | 优先级 |
|---|---|---|---:|
| 电力设备物模型 | 仅有通用产品物模型，没有标准电力模板 | 增加设备类型、标准属性、事件、服务、单位、枚举和默认告警模板 | P0 |
| RS485 设备接入 | 系统以网络协议为主，未形成串口采集配置闭环 | M1 由 NODE 部署 `iot-sink collector profile`，增加串口、波特率、校验位、站号、寄存器映射；不再评估 EDGE 双栈 | P0 |
| 阈值告警 | 主要是单值比较 | 增加持续时间、迟滞区间、恢复阈值、复合条件、告警抑制、维护模式和规则版本 | P0 |
| 告警通知 | 已有模板和推送，但现场渠道未核验 | 增加值班表、升级策略、确认/关闭、短信/电话/企业微信适配和送达状态 | P0 |
| 事故追忆 | 告警、时序、操作日志彼此分散 | 建立事件时间线，冻结事故前后遥测、告警、操作、图片和录像证据 | P1 |
| 远程分合闸 | 通用属性/服务调用可执行，但不具备电力安全闭环 | 增加二次确认、操作票、双人复核、联锁校验、超时、回执和审计 | P0 |
| 定时控制 | 有任务调度基础，缺少设备控制计划 | 新增控制计划、有效期、审批、冲突检测、取消和执行记录 | P1 |
| 历史曲线 | 以单设备单属性查看为主 | 增加多回路、多测点、日周月聚合、最大最小平均值和数据导出 | P1 |
| 自定义报表 | 存在通用 Excel 能力，但没有领域报表 | 增加指标选择、分组、时间粒度、模板保存、定时生成和导出 | P1 |
| 站点看板 | 可视化平台通用，没有站点业务聚合 API | 新增站点容量、负荷、设备状态、告警、用能和运维指标接口 | P0 |
| 一次系统图 | FUXA 可画图，但缺少电力图元与拓扑语义 | 增加母线、开关、刀闸、变压器、电容器图元及遥信/遥测/遥控绑定 | P0 |
| 视频联动 | 视频和设备告警是两套入口 | 告警触发预置位、抓拍/录像，告警详情可直接回看 | P1 |
| APP | 当前以设备、告警和算法为主 | 增加扫码、档案、巡检、工单、缺陷和位置上报页面 | P1 |
| 设备档案 | 有设备台账和文件服务，字段和分类不足 | 扩展厂家、型号、投运、质保、联系人、附件分类和档案版本 | P1 |

### 4.3 需要新增加的功能

#### 4.3.1 能源管理域

| 新功能 | 核心内容 | 建议归属 |
|---|---|---|
| 能源组织模型 | 企业、园区、站点、楼栋、楼层、车间、产线、回路、计量点 | 新模块 `iot-energy` |
| 表计管理 | 电表、水表、气表、倍率、读数类型、结算周期和数据质量 | `iot-energy` |
| 自动抄表 | 定时采集、补抄、人工补录、复核、冻结值和抄表台账 | `iot-energy` + 站点 collector |
| 分类分项统计 | 按组织、区域、能源类型、设备和回路聚合 | `iot-energy` |
| 最大需量 | 滑动窗口、需量峰值、发生时间和越限告警 | `iot-energy` |
| 目标与偏差 | 目标值、预算值、实际值和偏差率 | `iot-energy` |
| 尖峰平谷策略 | 电价方案、时段日历、节假日和阶梯价格 | `iot-energy` |
| 电费分析 | 尖峰平谷电量、基本电费、力调电费和费用趋势 | `iot-energy` |
| 同比环比 | 日、周、月、年同比环比与基线对比 | `iot-energy` |
| 电能质量 | 三相不平衡、谐波、THD、频率、电压偏差和功率因数 | `iot-energy` |

#### 4.3.2 运维管理域

#### 4.3.3 综合报告域

月度报告可先作为 `iot-energy` 与 `iot-maintenance` 的组合应用，不建议首期单独拆微服务。

报告至少包含：

- 设备运行情况。

## 7. 建议开发模块顺序

模块顺序遵循“先打通数据，再形成安全闭环，再建设运维闭环，最后做高级分析”。

```mermaid
flowchart LR
  P0["阶段 0\n标准与原型"] --> P1["阶段 1\n采集监控底座"]
  P1 --> P2["阶段 2\n安全告警与 SCADA"]
  P2 --> P3["阶段 3\n档案巡检工单"]
  P3 --> P4["阶段 4\n能源统计与抄表"]
  P4 --> P5["阶段 5\n电费与电能质量"]
  P5 --> P6["阶段 6\n综合月报与优化"]
```

### 阶段 0：标准、模型与可验证原型

目标：冻结电力领域统一语言，避免各模块重复定义。

交付：

- 站点、配电房、回路、设备、测点、计量点编码规范。
- 高压柜、变压器、低压柜、直流屏、电容柜及环境传感器物模型模板。
- 告警等级和状态机。
- 一次图图元及点位绑定规范。
- 选取一个真实配电房完成端到端原型。

### 阶段 1：采集与监控底座

目标：先实现“数据进得来、存得住、看得到”。

开发顺序：

1. NODE 按 ADR-007 部署同一 `iot-sink` 构建产物的 `collector` profile，增加 RS485/Modbus RTU 采集配置；不创建独立协议实现。
2. DEVICE 增加电力产品模板和测点标准。
3. 按 ADR-006 建立 `TelemetryStore`：standard 固定使用 PostgreSQL 分区表，full 使用 TDengine，并完成配额门禁、合同测试和升级迁移工具。
4. WEB 完善实时状态、多曲线和站点设备树。
5. 接入温湿度、烟雾、水浸、SF6 和摄像机。

### 阶段 2：安全告警、控制与 SCADA

目标：形成配电房无人值守的最小可用产品。

开发顺序：

1. 增强阈值、复合规则、恢复和告警抑制。
2. 建立值班表、通知升级和告警确认闭环。
3. 建设事故追忆和视频联动。
4. 增加安全遥控、操作票、双人复核和联锁。
5. 制作站点看板和电力一次图模板。

### 阶段 3：档案、巡检、缺陷与工单

目标：形成运维业务闭环。

开发顺序：

1. 创建 `iot-maintenance` 模块和数据库。
2. 建设设备档案、附件分类和二维码。
3. 建设巡检标准、计划、任务和记录。
4. 建设缺陷状态机。
5. 建设工单状态机、派单和 SLA。
6. APP 增加扫码、离线巡检、缺陷和工单。
7. 增加工作量、及时率和评价统计。

### 阶段 4：表计与基础能源管理

目标：形成经过倍率、时间边界、质量码和人工样本对账验证的用能数据与自动抄表闭环。

开发顺序：

1. 创建 `iot-energy` 模块和数据库。
2. 建设能源组织、回路、计量点和表计。
3. 建设自动抄表、补抄、复核和冻结值。
4. 建设分类分项、同比环比和目标偏差。
5. 输出能源日报和基础月报。
6. 使用独立人工样本验证原始值、倍率、冻结值、分类分项和统计结果；误差超出批准容差时不得宣称“可信”。

### 阶段 5：高级能源与电能质量

目标：形成节能和电力质量分析能力。

开发顺序：

1. 最大需量和需量越限。
2. 电价时段日历和尖峰平谷计费。
3. 功率因数及力调费用。
4. 三相不平衡、谐波和 THD。
5. 电费模拟、节能建议和异常能耗识别。

### 阶段 6：综合报告和持续优化

目标：把监测、能源和运维数据转化为经营价值。

交付：

- 电力运行月报。
- 告警和事故分析。
- 运维质量分析。
- 能源成本分析。
- 多站点对标与能效排行。
- 报告定时生成、审批、归档和发送。

## 8. 大致概要设计

### 8.1 新增 Java 模块

建议遵循 DEVICE 现有 API/BIZ 分层：

```text
DEVICE/
├── iot-energy/
│   ├── iot-energy-api/
│   └── iot-energy-biz/
└── iot-maintenance/
    ├── iot-maintenance-api/
    └── iot-maintenance-biz/
```

`iot-energy` 负责能源领域，不直接操作 `iot-device` 或时序后端数据库；通过 OpenFeign API 获取设备、产品和测点信息，通过 Kafka 消费遥测事件，并通过 ADR-006 的 `TelemetryStore` 查询契约获取时序数据。

`iot-maintenance` 负责档案和运维流程；通过设备 API 关联设备，通过系统 API 关联用户、班组，通过文件 API 保存附件，通过消息服务发送任务和工单通知。

### 8.2 核心领域模型

#### 能源模型

| 聚合 | 主要对象 |
|---|---|
| 能源组织 | `EnergyNode`、`EnergyNodeRelation` |
| 计量点 | `MeteringPoint`、`MeterBinding`、`MeterReading` |
| 抄表 | `ReadingPlan`、`ReadingTask`、`ReadingFreeze`、`ReadingCorrection` |
| 价格 | `TariffPlan`、`TariffPeriod`、`HolidayCalendar` |
| 指标 | `EnergyAggregate`、`DemandResult`、`EnergyTarget`、`EnergyCost` |
| 电能质量 | `PowerQualitySample`、`PowerQualityEvent`、`PowerQualityReport` |

#### 运维模型

| 聚合 | 主要对象 |
|---|---|
| 设备档案 | `AssetArchive`、`ArchiveDocument`、`WarrantyRecord`、`AssetQrCode` |
| 巡检标准 | `InspectionTemplate`、`InspectionItem`、`InspectionRoute` |
| 巡检执行 | `InspectionPlan`、`InspectionTask`、`InspectionRecord` |
| 缺陷 | `Defect`、`DefectAssignment`、`DefectAcceptance` |
| 工单 | `WorkOrder`、`WorkOrderAction`、`WorkOrderMaterial`、`WorkOrderEvaluation` |
| 人员位置 | `WorkerLocation`、`WorkerTrack`、`AttendanceEvent` |

聚合引用关系：

```mermaid
flowchart LR
  DEVICE["Device/Property\niot-device"] --> BIND["MeterBinding"]
  NODE["EnergyNode"] --> POINT["MeteringPoint"]
  POINT --> BIND
  POINT --> PLAN["ReadingPlan"]
  PLAN --> TASK["ReadingTask"]
  TASK --> READING["MeterReading"]
  READING --> FREEZE["ReadingFreeze"]
  FREEZE --> AGG["EnergyAggregate"]
  TARIFF["TariffPlan"] --> COST["EnergyCost"]
  AGG --> COST
  ARCHIVE["AssetArchive"] --> DEVICE
  INSPECTION["InspectionTask"] --> ARCHIVE
  INSPECTION --> DEFECT["Defect"]
  DEFECT --> WORK["WorkOrder"]
```

- 跨领域只保存稳定业务标识，不建立跨服务数据库外键；引用有效性通过 API 和事件校验。
- `MeteringPoint` 必须保存 `currentRatio`、`voltageRatio`、`calculationFormula` 和有效版本。倍率必须大于 0；只有经确认的直连表计才允许显式填 `1`，不得用空值暗示 1。
- 计算公式固定基线为 `calculatedValue = rawValue × currentRatio × voltageRatio × unitFactor`；累计量按相邻有效冻结值差额计算，回绕/换表按版本化策略处理。
- 倍率变更通过 `MeterRatioHistory` 创建带 `effectiveFrom` 的新版本，不覆盖历史。`MeterReading` 必须固化 `rawValue`、`appliedCurrentRatio`、`appliedVoltageRatio`、`formulaVersion` 和 `calculatedValue`，确保可重算与审计。

### 8.3 状态机

#### 告警状态

```text
ACTIVE → ACKNOWLEDGED → PROCESSING → RECOVERED → CLOSED
   ├──────────────→ ESCALATED
   ├──────────────→ IGNORED(until, reason) → ACTIVE/ACKNOWLEDGED
   └──────────────→ FALSE_ALARM(reason, reviewer)
```

- 告警恢复不等同于业务关闭。
- 同设备、同测点、同规则的重复告警应聚合计数。
- 维护模式可抑制通知，但必须保留事件记录。
- `IGNORED` 只能临时抑制通知，必须有原因、操作者和截止时间；到期恢复原状态，紧急告警默认不可忽略。
- `FALSE_ALARM` 为不可逆终态，必须记录判定人、复核人和原因；不得删除原始告警和证据。
- 统一告警主记录、存量迁移和旧“未恢复告警”兼容遵循 ADR-010，不新增第三套告警事实表。

#### 巡检任务状态

```text
PENDING → ASSIGNED → ACCEPTED → EXECUTING → SUBMITTED → REVIEWED → CLOSED
                     └──────────────→ ABNORMAL/OVERDUE
```

#### 缺陷状态

```text
DISCOVERED → CONFIRMED → ASSIGNED → RECTIFYING → TO_ACCEPT → CLOSED
                  └────────→ REJECTED ←──────────────┘
```

#### 工单状态

```text
DRAFT → APPROVED → DISPATCHED → ACCEPTED → IN_PROGRESS → TO_ACCEPT → COMPLETED
                           ├→ TRANSFERRED
                           ├→ PAUSED
                           └→ CANCELLED
```

### 8.4 API 概要

建议统一经 `iot-gateway` 暴露：

下表前缀为领域相对路径；对外统一映射到 `/api/v1`，例如 `/api/v1/device/control/request`。

| 业务 | API 前缀 | 示例 |
|---|---|---|
| 站点看板 | `/energy/dashboard` | `/energy/dashboard/site/{siteId}` |
| 能源组织 | `/energy/node` | `/energy/node/tree` |
| 表计与抄表 | `/energy/meter`、`/energy/reading` | `/energy/reading/task/page` |
| 能耗统计 | `/energy/statistics` | `/energy/statistics/trend` |
| 需量与电费 | `/energy/demand`、`/energy/cost` | `/energy/cost/period` |
| 电能质量 | `/energy/power-quality` | `/energy/power-quality/event/page` |
| 设备档案 | `/maintenance/archive` | `/maintenance/archive/device/{id}` |
| 巡检 | `/maintenance/inspection` | `/maintenance/inspection/task/{id}/submit` |
| 缺陷 | `/maintenance/defect` | `/maintenance/defect/{id}/assign` |
| 工单 | `/maintenance/work-order` | `/maintenance/work-order/{id}/action` |
| 人员轨迹 | `/maintenance/worker-track` | `/maintenance/worker-track/history` |
| 综合报告 | `/energy/report` | `/energy/report/monthly/generate` |
| 设备遥控 | `/device/control` | `/device/control/request`、`/device/control/{id}/approve`、`/device/control/{id}/execute` |

公共 API 不直接返回数据库实体；使用 ReqVO/RespVO，并包含权限、租户和数据范围校验。

#### 遥控统一入口

- `iot-device` 是遥控申请、审批状态机、联锁校验、命令执行、回执和审计的唯一责任模块；统一 API 为 `/device/control/**`。
- `iot-energy`、`iot-maintenance`、WEB、APP 和 SCADA 只能创建带业务关联 ID 的控制申请或查询结果，不得直接发布设备命令、写设备影子或调用 `iot-sink` 内部接口。
- `iot-device` 审批通过后调用既有物模型服务/属性下发机制，由 `iot-sink` 完成协议发送并返回设备回执。
- `device:control:switch`、`device:control:approve` 权限归属 `iot-device`；申请人与审批人必须分离，服务端强制校验。
- 同一 `controlRequestId` 全链路幂等；任何模块超时都不得绕过原申请重新生成无关联命令。

### 8.5 事件概要

建议新增 Kafka 事件：

| 事件 | 生产者 | 消费者 |
|---|---|---|
| `device.telemetry.reported.v1` | `iot-sink` | `iot-energy`、告警服务 |
| `device.alarm.created.v1` | `iot-device` | 通知、VIDEO、运维模块 |
| `device.alarm.recovered.v1` | `iot-device` | 通知、事故追忆 |
| `meter.reading.frozen.v1` | `iot-energy` | 统计、费用、报表 |
| `inspection.task.overdue.v1` | `iot-maintenance` | 通知、看板 |
| `defect.created.v1` | `iot-maintenance` | 工单、通知 |
| `work-order.status.changed.v1` | `iot-maintenance` | 通知、统计、月报 |

事件必须携带 `eventId`、`eventVersion`、`tenantId`、`occurredAt`、`source` 和业务关联 ID；消费者必须幂等。

事件版本升级规则：

- 事件 JSON Schema 存放于生产者 `iot-*-api/src/main/resources/events/{event-name}/vN.json`，Topic/事件名后缀与主版本一致。
- 新增可选字段、放宽枚举等向后兼容变化保留原主版本；删除字段、改类型/语义、收紧必填或枚举属于破坏性变化，必须发布 `v2`。
- 破坏性升级遵循“消费者先兼容 → 生产者双发 v1/v2 → 对账 → 消费者切换 → 停止 v1”，双发至少跨一个完整发布周期。
- 消费者必须忽略未知可选字段，并以合同测试验证可读取当前版本和上一个主版本；CI 对 Schema 执行向后兼容检查。
- 停止旧版本前必须确认消费者清单、积压为零、死信已处置并具有回滚开关；不得原地改变 v1 语义。

### 8.6 数据存储概要

- standard 原始遥测按 ADR-006 进入 PostgreSQL 分区表并执行准入配额；full 高频遥测进入 TDengine。
- 分钟、小时、日、月聚合结果可以进入 PostgreSQL 或独立 TDengine 聚合表。
- 表计冻结值、修正记录、电价、工单、缺陷和档案元数据进入 PostgreSQL。
- 图纸、手册、报告、巡检照片和工单附件进入 MinIO。
- APP 离线巡检数据进入本地临时存储，联网后按幂等键同步；服务端成功后清除。
- 时间事实统一保存 UTC 毫秒时间戳并同时记录来源时区；业务统计使用站点 IANA 时区，周期统一采用左闭右开 `[start, end)`。冻结任务精确到秒，禁止依赖服务器默认时区。
- 人员轨迹仅在明确的巡检/工单任务和工作时段采集；授权按人员、用途、时间段和任务类型记录，可随时撤回。默认仅保存完成任务所需的最低频率和精度，原始轨迹默认保留 90 天后删除或匿名化；导出、延长保留和管理查看必须单独授权并审计。具体法律依据由部署地区的数据合规责任人确认并写入上线清单。

### 8.7 权限概要

建议新增权限域：

- `energy:dashboard:view`
- `energy:meter:manage`
- `energy:reading:review`
- `energy:tariff:manage`
- `energy:report:export`
- `maintenance:archive:manage`
- `maintenance:inspection:execute`
- `maintenance:defect:assign`
- `maintenance:work-order:dispatch`
- `maintenance:work-order:accept`
- `device:control:switch`
- `device:control:approve`

远程分合闸必须将“申请/执行”和“审核”权限分离，并保存完整审计记录。

### 8.8 APP 概要

APP 建议新增一级业务入口“运维”：

“运维”作为现有首页/TabBar 的 capability 驱动入口，不替换现有首页；standard/full 启用时展示，mini 和无权限用户不创建空白入口。现有设备、告警和算法页面继续复用，通过路由参数进入电力对象上下文。

```text
运维首页
├── 扫一扫
├── 我的巡检
├── 我的工单
├── 缺陷上报
├── 设备档案
├── 告警处置
├── 位置签到
└── 消息中心
```

关键移动能力：

- 扫码进入设备详情。
- 查看设备实时状态、历史告警、巡检和工单。
- 离线巡检与断点续传。
- 拍照、录像、语音和签名证据。
- 定位授权、签到和轨迹上传。
- 工单接单、转派、暂停、处理和提交验收。

### 8.9 非功能设计

| 方向 | 要求 |
|---|---|
| 安全 | 遥控双人复核、操作票、联锁、最小权限、审计和凭据加密 |
| 可靠性 | 采集断点续传、消息幂等、有限重试、死信和任务补偿 |
| 性能 | full 高频遥测写 TDengine；standard 关系库时序表必须限流、分区和保留期治理；聚合查询预计算；列表分页 |
| 可观测性 | 采集成功率、数据延迟、告警延迟、通知送达率、工单 SLA、队列积压 |
| 部署适配 | 电力运维能力仅适用于 `standard/full`；`mini` 不启用电力采集、告警、控制、能源、运维和报表能力 |
| 数据质量 | 无效值、跳变、断点、时间漂移、倍率变化和人工修正均需留痕 |
| 隐私 | 人员定位必须授权、可关闭、限定用途并设置保留周期 |

## 9. MVP 范围建议

首个可交付版本建议聚焦“单站点配电房无人值守”，不同时启动全部能源和运维功能。

### MVP 必须包含

MVP 的最低部署档位为 `standard`，不以 `mini` 作为开发、演示或验收环境。

- 一个站点和一套配电房设备树。
- 高压柜、变压器、低压柜、环境监测产品模板。
- RS485/Modbus RTU 至平台的采集链路。
- 实时状态、历史曲线和阈值告警。
- 值班通知、告警确认和关闭。
- 一次系统图与站点看板。
- 视频实时查看、告警抓拍和回放。
- 安全远程控制的申请、审核、执行和回执。
- 设备档案与二维码。
- 简化版巡检任务和缺陷上报。

### MVP 暂不包含

- 复杂电价结算和力调电费。
- 高级谐波诊断算法。
- 完整备品备件库存。
- 多级外包商结算。
- AI 自动生成运维决策。

## 10. 里程碑、参考工期与验收建议

以下工期按“1 个具备后端、前端、测试和实施能力的稳定跨职能小组、上游需求及时确认”估算，仅用于排期参考；Technical Design 完成后必须基于任务拆分重估，不构成销售承诺。

| 里程碑 | 参考工期 | 依赖 | 核心验收 |
|---|---:|---|---|
| M1 数据接入 | 6～8 周 | Spec/ADR 冻结、现场点表和测试设备 | 连续采集不少于 7 天；断网补传；无重复和明显丢点 |
| M2 无人值守 | 6～8 周 | M1、统一告警 ADR-010、通知/视频联调 | 告警产生、通知、确认、恢复、关闭和视频证据全链路完成 |
| M3 安全控制 | 4～6 周 | M2、现场联锁条件和安全评审 | 分合闸申请、双人复核、联锁、回执和审计可验证 |
| M4 运维闭环 | 8～10 周 | M2、APP 与档案模型 | 扫码巡检发现缺陷，生成工单并完成验收关闭 |
| M5 能源基础 | 8～10 周 | M1、倍率/冻结值样本和人工对账基线 | 自动抄表、分类分项、同比环比和基础月报正确 |
| M6 高级分析 | 8～12 周 | M5、电价和电能质量样本 | 需量、尖峰平谷、电费及电能质量与人工样本核算一致 |

## 11. 主要风险

| 风险 | 影响 | 控制措施 |
|---|---|---|
| 不同厂家寄存器和协议差异 | 接入周期不可控 | 建立驱动模板、点表导入和模拟器 |
| 远程分合闸误操作 | 人身及设备安全 | 双人复核、联锁、操作票、超时和现场可禁用 |
| 原始电能数据质量不稳定 | 报表与电费不可信 | 质量码、校验、补抄、修正审批和冻结值 |
| 高频数据查询压力 | 看板和报表变慢 | TDengine 聚合、预计算和缓存 |
| APP 弱网 | 巡检数据丢失 | 离线存储、幂等同步和附件分片重传 |
| 人员定位合规 | 隐私争议 | 明示授权、工作时段采集、用途限制和自动清理 |
| 现有告警与新告警模型分裂 | 多入口、难追踪 | 统一告警 ID、状态机和事件总线 |

## 12. 实施结论

EasyAIoT 适合作为电力运维云平台的技术底座，推荐采用“增强现有通用能力 + 新增能源和运维两个领域模块”的方式建设：

1. 不重写设备、时序、告警、视频、可视化和权限基础设施。
2. 优先补齐电力物模型、RS485 采集、安全告警、一次图和遥控安全闭环。
3. 第二步建设 `iot-maintenance`，尽快形成可感知的运维业务价值。
4. 第三步建设 `iot-energy`，先保证抄表与统计可信，再增加费用和电能质量分析。
5. 综合月报建立在监测、能源和运维数据稳定之后，避免先做展示后补数据。

本计划后续进入开发前，应为每个阶段分别产出需求说明、数据字典、接口契约、迁移脚本、测试方案和发布回滚方案，并遵守《EasyAIoT 项目开发宪法》。
